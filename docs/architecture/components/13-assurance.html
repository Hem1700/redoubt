Assurance: TCB, Verification & Roadmap

Abstract. A security claim is only as good as the reason you have to believe it. This closing chapter gathers those reasons. It defines exactly what must be trusted — the trusted computing base, which in Redoubt is the Monitor, the boot ROM, and the PMP configuration and nothing else — and states the line budget that keeps it small enough for one person to read. It lays out the complete-mediation argument in full: why every effect must pass the Monitor's checks, and why that holds even when the Warden is compromised. It maps Redoubt honestly against the OWASP Top 10 for Agentic Applications, marking what is contained, what is merely mitigated, and what is not covered at all. It sets out the test and verification plan, from laptop unit tests to a Verilator assertion that the hardware wall really faults; sketches the performance and resource budget on the target FPGA; and ends with the roadmap from this v1 to a version with a hardware mediation gate, wired egress, a formal model, and remote attestation. Where the design is honest about a gap, this chapter is where the gap is written down.

Note to first-time readers.

This chapter is about assurance — the grounds for trusting the system — so a few evaluation terms recur.

Trusted computing base (TCB)
The set of components that must be correct for the security guarantee to hold. Anything inside it, if buggy, can break the guarantee; anything outside it can be wholly hostile without doing so. The smaller the TCB, the less there is to get wrong. Shrinking it is Redoubt's central move.
Complete mediation
One of the three classic reference-monitor properties: every attempt to perform a protected action is checked, with no way around the checker. The other two are that the checker is tamper-proof and that it is small enough to verify.
Lines of code (LoC)
A rough proxy for how much there is to audit and how many places a bug can hide. Redoubt puts a hard ceiling on the TCB's line count and fails the build if it is exceeded.
Formal verification
Proving, with mathematics rather than testing, that code meets a specification. It is expensive and total; Redoubt does not claim it for v1, but the design is shaped to make a future proof feasible.
Attestation
A way for an outside party to check what software is actually running on the device, so that a tampered or downgraded system can be detected remotely.

13.1What must be trusted, and how small it is

Every security architecture has a set of things that simply must be correct. Call it the trusted computing base. The honest way to describe a system is to name that set precisely and then make it as small as you can, because everything in it is a place a bug becomes a breach, and everything outside it is free to misbehave.

Redoubt's TCB is three things:

  1. the Monitor — the M-mode reference monitor that makes every decision (Chapter 9);
  2. the boot ROM (BROM) — the tiny code that measures the Monitor at power-on and refuses to run a tampered one (Chapter 5); and
  3. the PMP configuration — the specific set of hardware protection entries that wall the Monitor, the secrets, and the egress hardware off from everything else (Chapter 3).

That is the whole list. Note what is not on it. The Warden is not trusted (Chapter 11); the compartments are not; the host, the LLM, and every tool are not; the ESP32 firmware, though it sits in the egress path, is not trusted for the security property (it is an honest caveat, addressed in the roadmap below). Millions of lines of software can be as hostile as they like without touching the guarantee, because the guarantee rests entirely on those three items.

And those three are deliberately tiny. The budget is a hard engineering constraint, not an aspiration:

The continuous-integration pipeline counts the trusted lines with tokei on every change and fails the build if the Monitor crosses 2,500 or the BROM crosses 300. The current number is published in the README, so the claim "small enough to audit" is not a slogan but a figure anyone can check. A second gate refuses unsafe Rust anywhere outside the one documented module that must touch CSRs, PMP, and MMIO.

The scale, drawn to compare

Numbers like "2,500 lines" mean little in isolation. The point of a small TCB is relative: it is small against the things people trust today. A general-purpose OS kernel is millions of lines; a hardened compartmentalised system like Qubes still trusts a hypervisor and dom0 in the millions; seL4, the smallest formally verified kernel, is roughly 8,700 lines of C.1 Redoubt's decision-bearing code aims to come in below even that.

13.2The complete-mediation argument

The security property (Chapter 2) says that for every external effect the agent causes, there exists a capability in the active session that binds the tool, whose predicate accepts the arguments, and whose flow rule accepts the labels — and that this holds for arbitrary behaviour of the host, the compartments, and even a compromised Warden. This section is the argument that it does. It is a sketch, not a proof; a formal model is on the roadmap. But the sketch is short, which is itself the point.

The argument has three joints.

1 — Every effect must go through the egress hardware.

An "external effect" means something reaching the network or storage: a packet sent, a block written. Both happen only through the egress MMIO region (network via the ESP32 link, storage via the SD controller, Chapter 12). There is no other physical path off the chip for these effects. So to cause an effect at all, some code must touch that MMIO region.

2 — Only the Monitor can touch the egress hardware.

The egress MMIO region and the secrets region are covered by PMP entries that grant access to machine mode only, and those entries are written and locked at boot, before any supervisor- or user-mode code runs (Chapters 3 and 5). A locked entry cannot be changed until the hart resets. Any access to egress MMIO from the Warden or a compartment faults. Therefore the only code that can actually drive egress is the Monitor, running in machine mode.

3 — The only way into the Monitor is the checked entry.

The Monitor is entered exactly one way: an ecall that traps to machine mode and lands on the trap vector, which dispatches on the opcode in a7. The mediation opcode runs the six checks (Chapter 9); the session opcodes manage lifecycle; anything else is refused as malformed. There is no ecall that reads a secret or drives egress as a side effect — those actions live only inside the performing step, after the checks have passed. So the only route to an egress-driving instruction is through the checks.

Chain the three: an effect requires egress MMIO (1); egress MMIO is reachable only from the Monitor (2); the Monitor is reachable only through the checked entry (3). Therefore no effect can occur without passing the checks. The reference-monitor triad holds — the checker is always invoked (no side door), tamper-proof (locked machine-only regions)4, and small enough to verify (§13.1).2

The crucial move is that not one link in this chain rests on software above the Monitor behaving well. Link 2 is a hardware fault, not a software check. That is what lets the argument survive a compromised Warden: a hostile Warden can relay any request it likes into the mailbox, but the request still arrives at link 3 and faces the checks, and the Warden still cannot execute link 2 itself. A Warden compromise buys an attacker a louder knock on the door, not a way around it. (Chapter 11, §11.9, walks each Warden avenue and shows it dead-ends here.)

13.3Coverage against the OWASP Agentic Top 10

The OWASP Top 10 for Agentic Applications (2026) is the community's current catalogue of the ways agent systems get hurt.3 Any honest security claim has to say where it lands against that list — including the entries it does not address. The table below uses three verdicts. Contained means the attack can happen inside the agent but cannot produce an unauthorised effect. Mitigated means Redoubt meaningfully reduces the risk but does not eliminate it. Not covered means v1 offers no defence, by stated scope.

ThreatVerdictMechanism (or why not)
Agent goal / prompt-injection hijackContainedThe agent may be fully hijacked; every tool call still meets capability + predicate + flow checks (Ch. 9). Authority does not follow the hijack.
Tool misuse / poisoned tools & MCP serversMitigatedCapabilities bind one tool; predicates constrain arguments; no ambient authority. A poisoned tool can only request within what was granted (Ch. 7-8).
Data exfiltrationMitigatedHost allowlists in predicates plus boundary IFC: a SECRET-labelled value cannot enter a public sink (Ch. 10). Bounded by what the labels see.
Excessive agency / privilege abuseMitigatedLeast privilege by construction: empty cspace, attenuation-only derivation, per-session quotas (Ch. 7, 11).
Secret / credential theftContainedSecrets are inject-only, machine-only, never returned on any ABI path (Ch. 9, 12). Use of a key, never the key.
Unexpected / unauthorised actionsContainedComplete mediation (§13.2): no effect without a passing check. Instant O(1) revocation to cut a run (Ch. 11).
Insecure output handling downstreamMitigatedEgress results are labelled UNTRUSTED and that label propagates to the host, flagging attacker-controlled data (Ch. 10).
Microarchitectural / timing side channelsNot coveredOut of scope, v1 (Ch. 2). No constant-time guarantee; a timing-based leak is possible in principle.
Physical / fault-injection attacksNot coveredOut of scope, v1. Glitching the hart or probing the board is not defended.
Host-side memory poisoning · multi-agent collusion · availability/self-DoSNot coveredOut of scope, v1 (Ch. 2). Redoubt does not police the agent's own memory, collusion between agents, or a Warden that simply refuses to make progress.

The pattern is deliberate and worth naming. Redoubt is strong exactly where its mechanism bites — the authority-bearing boundary of a tool call — and makes no pretence elsewhere. The "not covered" rows are not oversights; they are the honest edge of a v1 whose scope was drawn narrowly on purpose (Chapter 2), and several of them are the subject of the roadmap below.

13.4Verification and test plan

The Monitor chapter listed how its own logic is tested (Chapter 9, §9.13); here is the whole-system plan, organised by the kind of confidence each layer buys. No single technique is sufficient, and the plan is honest that testing is not proof.

Host unit tests

The fiddly, self-contained logic — the parser's bounds arithmetic, the epoch comparison, the predicate operators, the capability attenuation checks, the quota counters — runs as ordinary Rust unit tests on a development machine, fast and on every commit. This catches the everyday bugs cheaply and keeps the feedback loop tight.

Verilator PMP-fault assertion

The one promise that cannot be tested in software alone is that the hardware wall truly faults. We simulate the actual SoC in Verilator and assert it: a load or store from supervisor or user mode into the secrets or egress regions must raise an access fault, not silently succeed or read zeros. This is the electrical ground truth under link 2 of the mediation argument, so it gets its own gate.

QEMU containment suite

Each attack from the threat model is scripted end to end against the system running under emulation, and each asserts two things: the exact expected denial code and that nothing left the device. The exfil demo from the specification — a prompt-injected agent posting an API key — is the canonical case: it must yield DENY_ARG for the wrong host, or DENY_FLOW for the secret in the body, and the egress trace must be empty. A denial that returns the right code but still sent the packet is a failure.

Fuzzing the attack surface

The parts that read attacker-controlled bytes — the COBS/CRC framing in the Endpoint, the TypedArg TLV parser, the request header validation — are fuzzed with memory-error detection enabled, so a malformed frame that would corrupt memory is caught rather than trusted to good luck. Because the trusted parser is no_std Rust with no allocator, the surface is small and bounded, which makes fuzzing tractable.

CI gates

Several build-failing gates encode the invariants as continuous checks rather than good intentions:

  • the tokei line-count gate on the Monitor (≤ 2,500) and BROM (≤ 300);
  • a gate refusing unsafe Rust outside the one permitted CSR/PMP/MMIO module;
  • the containment suite, which must pass with an empty egress trace on every attack case;
  • the Verilator PMP assertion, run in the pipeline so a hardware-config regression breaks the build.

The Monitor's own work is bounded and small by construction, so the security check is never the bottleneck — the network or the SD card is. That is the comfortable position to be in: correctness costs almost nothing against the physics of getting bytes off the board.

13.6Roadmap

v1 is a first, honest cut. Several of its stated limitations have a planned answer, and naming them as a roadmap is part of being straight about where the design is today.

A hardware mediation gate (v2)

Today mediation is enforced by software in machine mode behind a hardware wall. v2 moves a mediation check into the RTL itself — a gate in the fabric between the CPU and egress that cannot issue a send without a token the Monitor set, shrinking even the machine-mode software's role in the critical path.

Wired-Ethernet egress

The frankest caveat in v1 is that the ESP32 firmware sits in the egress path, so the network module is a closed component the Monitor does not fully own (Chapter 12). v2 moves to a board with a wired-Ethernet MAC the Monitor drives directly (ECPIX-5 / Colorlight class), removing the ESP32 from the trusted path.

A formal model

The mediation argument in §13.2 is a sketch. The design was kept small and loop-free specifically so a machine-checked model of the decision pipeline and the PMP invariants is feasible. The aim is to turn the sketch into a proof of the security property against a model of the hardware.

Remote attestation

v1 measures the Monitor at boot and exposes an audit hash-chain head via ATTEST_READ5 (Chapters 5 and 9). v2 extends this to a proper remote attestation: an outside verifier can challenge the device and get a signed statement of what is running, so a tampered or downgraded Redoubt is detectable off the box.

Bitstream root of trust

v1 does not verify the FPGA bitstream's authenticity (Chapter 2, out of scope). A future revision adds a root of trust for the bitstream itself, closing the gap beneath the measured-boot chain so the measurement starts from silicon rather than from an assumed-good configuration.

13.7What we deliberately do not claim

An assurance chapter earns its trust as much by its disclaimers as by its claims. Some tempting stronger statements were considered and turned down.

"Formally verified." We do not say it, because we have not done it. seL4 earned that phrase over person-years; v1 has a test plan and a proof sketch. Claiming the word before the work is done would be the exact dishonesty this chapter exists to avoid.

"Immune to prompt injection." The agent can be injected completely — we assume it will be. What we claim is narrower and defensible: injection cannot produce an unauthorised effect. Conflating "we contain it" with "we prevent it" would oversell the mechanism.

"Side-channel resistant." Timing and microarchitectural leaks are explicitly out of scope for v1. Splicing a secret is not yet constant-time (Chapter 9's open question), and we would rather name that than paper over it.

"End-to-end information-flow secure." Redoubt tracks labels only at the mediation boundary; it does not follow data through the host LLM's reasoning (Chapter 10). We claim boundary IFC, which is the checkable part, and say plainly that full end-to-end IFC is not on offer.

13.8Open questions

The loose ends that bear on assurance specifically:

  • Which properties a first formal model should target — the mediation chain of §13.2 is the obvious candidate, but the PMP-lock invariant and the attenuation-only capability rule are also within reach.
  • How to attest the ESP32's presence in the path honestly until wired egress lands: should the audit log record that egress went through the closed module?
  • Whether the containment suite's "empty egress trace" oracle is strong enough, or whether a hardware egress tap is needed to be sure nothing left during a denied request.
  • The real LUT/BRAM/latency figures once the design is placed and routed and run on the board, replacing the estimates in §13.5.
  • Whether the CI can also gate on a measured Monitor line count trend, so the TCB is watched for creep, not just for the ceiling.
