Capabilities

Abstract. A capability is Redoubt's unit of permission: a small, unforgeable record that is the authority to perform one specific kind of action, and nothing wider. The agent on the untrusted host never holds one. It holds only a number — an opaque handle — that the Monitor turns into a real capability, or refuses to. This chapter builds the idea from the ground up for a reader who has never met it: what a capability is and why permission is better carried as a token than looked up in a list; the exact sixteen bytes of a Redoubt capability, field by field; the per-session table they live in; how a handle is resolved, how a capability is narrowed but never widened, and how a whole session's worth of them is cancelled in a single instruction. It closes by setting our design beside seL4's, whose discipline we borrow and whose machinery we deliberately leave out.

Note to first-time readers.

This chapter leans on a few words that have precise meanings here. None require a background in operating systems.

Capability
An unforgeable token that is a permission. Holding it grants exactly the authority it names; you cannot obtain more by asking louder, and you cannot invent one. The coat-check tag from the Monitor chapter: tag 14 fetches coat 14, and calling out a number you never received fetches nothing.
Handle
The number the host actually holds — a slot index, like the paper stub the coat-check gives you. It is not the permission; it merely points at where the permission is kept, on the safe side of the wall.
Ambient authority
Permission you have simply by existing, without presenting anything — the way any program you run can normally open any file you can. Redoubt has none of this. Nothing is permitted by default; authority is only ever what a capability names.
Attenuation
Making a permission weaker — narrowing it to fewer hosts, fewer rights, a smaller range. Redoubt can attenuate a capability but has no operation that strengthens one.
Session
One run of one agent. Each session gets its own private set of capabilities and can be torn down independently; the Warden & Sessions chapter (11) covers their lifecycle.

7.1Permission as a thing you hold

There are two ways to answer the question "may this action happen?" The familiar one is to keep a list somewhere — a table of who is allowed to do what — and consult it each time. That is how the file permissions on your laptop work. When a program opens a file, the system knows which user is behind the program, looks the file up, and checks whether that user is on the list. The permission lives with the resource, and identity is the key that unlocks it.

The other way is to hand out tokens. Instead of asking "who are you, and are you allowed?", the system asks "what did you bring, and does it authorise this?" The permission travels with whoever holds it, the way a ticket to a concert admits its bearer without the box office needing to remember your name. A token like this is a capability, and the whole of Redoubt's authority model is built from them.

Why the second way? Because the first quietly assumes something we have thrown out. A list-and-identity scheme grants authority to a principal — a user, a process — and then trusts that principal to ask only for what it should. But our principal is a prompt-injected AI agent that will ask for anything at all, in any order, the moment an attacker tells it to. Identity buys us nothing when the identity is hijacked. What we want is for the agent to be unable to name an action it was not given, no matter how it is manipulated. Capabilities give us exactly that: if you were not handed the token, the action does not have a name you can utter.

This is an old idea, older than most of the systems that ignore it, and it has a precise modern form in the seL4 microkernel, whose capability discipline we follow closely.1 Where we depart from seL4 — and we depart a lot — is covered in §7.9; the departures are all in the service of keeping the trusted code small enough to read.

7.2The agent never holds the ticket

Here is the move that makes the whole scheme safe against a host we do not trust at all. A real capability — the sixteen bytes that actually confer authority — lives only inside the Monitor's private memory, in the machine-only region no code outside the Monitor can read.2 What crosses the wire to the agent is not the capability. It is a handle: a small integer that names a slot in a table the Monitor keeps.

Think again of the coat-check. You do not walk off holding the mechanism that decides which coats you may claim; you hold a numbered stub. The stub is useless to steal in bulk and impossible to escalate — tag 14 is tag 14, and scribbling a bigger number on it does not get you the fur coat. The authority stays behind the counter. All the stub does is point at a row.

So when the agent asks the Monitor to do something, it says, in effect, "act on the authority in slot 3." It cannot describe the authority; it can only cite a slot. If the slot holds a capability, the Monitor reads it and proceeds. If the slot is empty, or the number is out of range, or the number is one the agent simply made up, the answer is the same: there is no authority there, so the request is denied.3 A forged handle is not a security event to be caught and alarmed over; it is just a citation of an empty slot, and empty slots grant nothing.

This is why we can be relaxed about the host reading, copying, or fabricating handles at will. A handle is not a secret and not a key. It is a coat-check number on the wrong side of a wall it cannot climb.

7.3The sixteen bytes

A capability is a fixed record of exactly sixteen bytes — the same width as an seL4 capability slot, which is not a coincidence.1 Fixed width matters more than it looks: because every capability is the same size, the table that holds them is a plain array, resolution is a single indexed read with no pointer-chasing, and there is no allocator anywhere on the path. Nothing about a capability is dynamic. Here is the whole of it.

struct Cap {                      // 128 bits, 16 bytes
  u8   ctype;      // 0=Empty 1=Net 2=File 3=Secret 4=Tool
  u8   rights;     // per-type permission bits (attenuation-only)
  u16  tool_id;    // the tool this cap is bound to (0 if N/A)
  u16  pred_ref;   // index into predicate_table (0xFFFF = none)
  u16  flow_ref;   // index into flow_table
  u16  secret_ref; // index into secret store (0xFFFF = none; inject-only)
  u16  aux;        // type-specific (e.g. allowlist_ref)
  u16  epoch;      // must equal session.epoch, else stale (revocation)
}

Let us take the fields one at a time, because each is there for a reason and the reasons are the design.

ctype — what kind of authority this is

One byte naming the type of the capability. There are exactly five kinds, and the first is the one that matters most for safety:

ctypeNameConfers
0EmptyNothing. An unfilled slot. This is the default for every slot in a fresh session.
1NetThe authority to make a network call through a bound tool (e.g. http.request), subject to its predicate and flow rule.
2FileThe authority to read or write storage through a bound file tool, subject to a path predicate and mode.
3SecretThe authority to have a named secret injected into an effect — never to receive its bytes (§7.7).
4ToolThe authority to invoke a tool that is neither network nor storage — a local, non-egress action mediated for uniformity.

That Empty = 0 is deliberate and load-bearing. Memory that has been zeroed — a fresh session's capability table, a slot that was cleared on revocation — reads back as ctype 0, which is no authority. The safe state is the state you fall into by accident. There is no way for a zeroed or garbled slot to accidentally mean "network access."

rights — the dial within the type

One byte of permission bits whose meaning depends on ctype. For a File capability the bits distinguish read from write; for a Net capability they might gate which methods are allowed at the coarsest level, before the finer predicate runs. The single rule that governs rights everywhere is that derivation may only clear bits, never set them (§7.6). A child capability is always as weak as its parent or weaker. You cannot manufacture write access out of a read-only ticket.

tool_id — the one tool this is for

A capability is bound to exactly one tool, named by a sixteen-bit identifier. The web capability is for http.request and nothing else; presenting it at the file tool fails immediately, at check 3 of the Monitor's pipeline, before any argument work happens. Binding authority to a single tool is what stops a capability from being a skeleton key. Where a capability names no tool (some Secret capabilities), this field is zero.

pred_ref — which argument rules apply

Authority in Redoubt is rarely "you may call this tool." It is almost always "you may call this tool with arguments that satisfy these conditions": only HTTPS, only to these hosts, only paths under /corpus/. Those conditions are compiled ahead of time into a table of predicates — the subject of the next chapter — and pred_ref is the index of this capability's row in that table. The sentinel 0xFFFF means "no predicate," which is rare and deliberate. The capability does not carry the rules inline; it points at them, so many capabilities can share one compiled rule set and the sixteen bytes stay sixteen bytes.

flow_ref — the information-flow rule

A second, independent index, into the flow table this time. Even a call whose arguments are all permitted may still be forbidden if it would carry a secret out to a public sink. That is a different question from "are the arguments allowed," and it is asked by a different check with its own table. flow_ref selects which flow rule this capability is judged against. Information-flow control is Chapter 10's subject; here it is enough to know the capability names its rule rather than embedding it.

secret_ref — the key to be used, never seen

If this capability's action needs a credential spliced in — an API key placed in an Authorization header, say — secret_ref is the index of that credential in the Monitor's secret store. It is an index and only an index. The secret bytes live in the machine-only secret region; the capability points at them so the Monitor can inject them at the performing step, but nothing in the capability, and no operation on it, ever moves those bytes toward the host. 0xFFFF means "no secret." §7.7 is entirely about this field, because it is the field most worth getting exactly right.

aux — the type-specific corner

Sixteen bits whose meaning is set by ctype: an allowlist reference for one type, a mode or a small bound for another. It is the one deliberately flexible field, and we keep it small on purpose. A wide, general-purpose "extra data" field is an invitation to grow the capability into something no one can reason about; two bytes with a per-type meaning is enough for the cases we have and too small to be abused into a side channel of authority.

epoch — the field that enables instant revocation

The last two bytes are a generation counter. Every capability carries the epoch it was minted under; the session it belongs to carries a current epoch of its own. A capability is valid only while the two agree. To revoke every capability in a session at once, the Monitor increments the session's epoch — one addition — and in the same instant every ticket it ever issued fails a one-line comparison. No lists are walked, no slots are cleared, no tree is traversed. §7.8 dwells on why this tiny mechanism is worth a field of its own.

7.4Where capabilities live: the cspace

Each session owns a private array of capabilities, called its capability space, or cspace:

cspace: [Cap; 32]     // per session; v1 N = 32
sessions:  up to 8 concurrent, each with its own cspace and epoch

The handle the host holds is nothing more than an index into this array: cap_handle is a number from 0 to 31. There is no global namespace of capabilities and no way for one session to name another's — session 2 citing "slot 3" reaches into session 2's cspace, never session 1's. Sessions are sealed off from one another by construction, because the only way to reach a capability is through the cspace of the session you are in.

A fresh cspace is entirely Empty. This is the concrete meaning of "no ambient authority": a new agent starts able to do nothing. It gains authority only as the policy manifest (Chapter 8) installs capabilities into named slots at session open, and it can never gain more than what was installed plus whatever narrower children it derives from them. There is no primordial "root" capability lying around, no super-slot, no back door. What the manifest did not grant does not exist for that agent.

Thirty-two slots is a design choice, not a law of nature; it is sized to the manifests we expect and flagged as tunable once the FPGA's real memory budget is known. Eight concurrent sessions is likewise a starting figure. Both live in the machine-only data region alongside the policy tables and the audit log.

7.5Resolve: from a number to authority

Resolution is the first thing the Monitor does with a request once it has confirmed the request is well-formed. It is the second check of the pipeline described in the Monitor chapter (§9.7), and it is deliberately boring:

fn resolve(session_id, cap_handle) -> Result<&Cap, Deny> {
    let s = sessions.get(session_id)?;           // bounds-checked; bad id -> DENY_NO_CAP
    let cap = s.cspace.get(cap_handle)?;          // bounds-checked; out of range -> DENY_NO_CAP
    if cap.ctype == Empty       { return DENY_NO_CAP; }
    if cap.epoch  != s.epoch    { return DENY_REVOKED; }   // stale ticket (§7.8)
    Ok(cap)
}

Every failure mode collapses to a short, deterministic path. An out-of-range session id or handle is caught by the bounds check — no read ever strays outside the array. An Empty slot is no authority. A slot whose epoch no longer matches the session's is a ticket that has been revoked, and says so with a distinct reason code so the audit log can tell "you never had this" apart from "you had this and it was cancelled." There is no search, no hashing, no allocation. Resolution of a valid handle is two indexed reads and two comparisons, and it takes the same time whether the answer is yes or no.

Notice what resolution does not do. It does not check the arguments, the tool binding, or the flow rule; those are the checks that follow. Resolution answers exactly one question — "is there a live capability behind this number?" — and hands the capability, or a denial, to the next stage. Keeping each stage to one question is what makes the pipeline auditable.

7.6Derive: narrowing, and only ever narrowing

Sometimes an agent that holds a broad capability should hand a sub-task a narrower one. It holds a web capability good for a set of hosts and wants to give a helper access to just one of them; it holds a file capability for /corpus/ and wants to pass down one for /corpus/public/ alone. This is derivation, and Redoubt supports it with one unbending rule: a derived capability is always weaker than its parent. There is no operation, anywhere, that makes a capability stronger.

cap_derive(src_handle, narrower_pred_ref, cleared_rights) -> new handle
  precondition (checked): predicate(narrower_pred_ref) ⊆ predicate(src.pred_ref)
  precondition (checked): new.rights = src.rights & cleared_rights   // bits only clear
  result: a fresh slot with the same ctype/tool_id, a subset predicate,
          rights no wider than src, same flow_ref or stricter, same epoch

The word "subset" is doing real work, and it is checked, not hoped for. A predicate is a conjunction of clauses over typed fields — "scheme is https AND host in this set." One predicate is a subset of another when every value the narrower one admits, the wider one admits too. For the clause shapes Redoubt uses this is decidable cheaply, and — this is the important part — it is checked at compile time, by the manifest compiler, not at run time inside the Monitor. The Monitor never has to reason about whether one set is contained in another; it is handed pre-checked predicate rows and a table of which rows are legitimate narrowings of which. Derivation at run time is then just installing a row that the compiler already blessed.4

This is the property the Monitor chapter calls out as an invariant: a derived capability is always weaker than its parent, never stronger. Rights amplification — the classic way privilege systems fail, where some sequence of legal operations ends with more authority than you started — is not defended against by careful checking here. It is structurally impossible, because the only operation that creates a capability from another produces a subset, and there is no inverse.

Attenuation-only is a real constraint, and worth being honest about: it means Redoubt cannot express "grant a helper something I myself do not have," which some delegation schemes allow. We consider that a feature. Every capability in a session traces back, by narrowing steps alone, to something the manifest granted — so the manifest remains a complete and readable statement of the session's maximum authority.

7.7Secrets: use without possession

The secret_ref field deserves its own section because it is where a capability system usually springs a leak. The temptation is to let a trusted holder "read" a secret so it can use it. We do not. A Redoubt Secret capability confers the right to have a secret injected into an effect, and confers no way whatever to learn its bytes.

  • The secret bytes live in the machine-only secret store, loaded once at boot. The capability holds only secret_ref, an index into that store.
  • The one place a secret is ever read in plaintext is the Monitor's performing step, when it splices the credential into an outgoing effect — an Authorization header, for instance — exactly where the policy directs. It holds the plaintext for the instant that takes, then wipes its copy.
  • No ABI, no command, and no capability operation copies secret bytes into a response or anywhere the host, the Warden, or a compartment can read. The result of an action carries data back; it never carries the key back.

This is deliberately the same bargain a phone's secure element strikes with the software above it: you are granted the use of a key, not the key.5 A prompt-injected agent may hold a Secret capability and still be structurally unable to exfiltrate the secret, because the only thing the capability lets it do is ask the Monitor to use the secret in a call the Monitor itself performs and checks. Even then, the flow rule (Chapter 10) stands in the way of using an allowed secret in a disallowed direction. Two independent barriers, as everywhere in this design.

7.8Revoke: cancelling everything in one instruction

When a session ends, or when something goes wrong and an agent's authority must be pulled at once, Redoubt has to invalidate every capability that session holds — including any the agent has copied, cited, or squirreled away as handles on the host. Because handles are just numbers, "the agent kept a copy" is not a problem: the number still points at a slot on our side. The problem is invalidating the slots, and doing it fast, without walking a data structure whose size an attacker might influence.

The epoch field solves this. Each session carries a current epoch; each capability records the epoch it was minted under; resolution requires the two to match (§7.5). Revocation is therefore:

fn revoke_session(session_id) {
    sessions[session_id].epoch += 1;    // that is the whole of it
}

One addition, in constant time, and every capability in that session is now stale — its recorded epoch no longer equals the session's, so the very next resolution of any of its handles returns DENY_REVOKED. Thirty-two slots or one, freshly derived or granted at boot, held quietly by the agent or in flight: all of them die together, at once, without being touched individually.

There is a bound worth stating: an epoch is sixteen bits, so a single session that was revoked sixty-five thousand times would wrap. In practice a session is revoked once, at teardown, and its slots are cleared when the session structure is reused, so the counter starts fresh. We note the wrap as a thing to keep honest rather than a live risk, and flag whether a wider counter is warranted once session lifetimes are pinned down.

This is a coarser instrument than seL4's, and we chose the coarseness on purpose — the next section says why.

7.9What we borrowed from seL4, and what we left behind

seL4 is the reference for capability-based protection done rigorously: a formally verified microkernel in which every authority is a capability, capabilities live in slots of a per-thread capability space, and each slot is sixteen bytes.1 We take all of that. What we do not take is the machinery seL4 needs because it is a general-purpose kernel and we are not.

No capability derivation tree (CDT). seL4 records the full genealogy of every capability so that revoking one capability can recursively revoke all descendants derived from it. That tree is powerful and precise, and it is also a mutable, pointer-linked structure inside the trusted kernel — exactly the kind of thing that costs code, invites bugs, and complicates proofs. Redoubt has no CDT. We revoke at the granularity of a whole session, by bumping one counter (§7.8). We give up fine-grained "revoke just this one descendant" and gain a revocation that is one instruction and needs no bookkeeping at all. For per-session agent teardown, which is the case we actually have, the trade is overwhelmingly worth it.

No untyped memory and no retype. In seL4 you build capabilities dynamically by "retyping" untyped memory into kernel objects, which is how a verified kernel lets user space manage its own resources. It is elegant and it is a great deal of mechanism. Redoubt has no untyped capabilities and no retype operation. Every capability that can ever exist is either installed by the manifest at session open or derived — by narrowing — from one that was. The set of authorities is closed and known before the agent runs. That closes off a whole category of dynamic behaviour we would otherwise have to reason about inside the trusted base.

Flat and fixed-size, not a rich object zoo. seL4 has many capability types for its many kernel objects. Redoubt has five, four of which map to the small set of things an agent can actually do at the boundary. Fewer types means a smaller resolver, fewer paths, and a capability whose every field fits on one screen.

The through-line is the TCB budget. The Monitor must stay under roughly 2,500 lines so that one person can read all of it (Chapter 13). A CDT, an untyped allocator, and a dozen object types are each individually reasonable and collectively far more code than that budget allows. We keep seL4's discipline — unforgeable tokens, no ambient authority, attenuation-only — and drop the generality we do not need. seL4 earns its complexity by being a kernel for everything; Redoubt earns its simplicity by being a monitor for one narrow thing.

7.10Failure modes and edge cases

A few situations are worth naming explicitly, because they are where a capability system is most likely to surprise you.

  • A fabricated handle. The host cites slot 47 in a 32-slot cspace, or slot 3 when slot 3 is Empty. Both resolve to no authority and return DENY_NO_CAP. This is expected traffic under a hijacked agent, not an exceptional condition; it is logged and counted like any denial.
  • A stale handle. The host cites a handle that was valid before its session was revoked. Resolution finds the slot filled but the epoch mismatched and returns DENY_REVOKED — a distinct code, so "never had it" and "had it, lost it" are distinguishable in the audit trail.
  • A right type, wrong tool. A valid Net capability presented at the file tool resolves fine at this stage — the capability is live — and then fails the tool-binding check that follows, with DENY_TOOL. Resolution's job is only to confirm the capability exists and is live; binding is a separate question.
  • Cross-session confusion. There is no mechanism by which a handle from one session names a slot in another; resolution always indexes the current session's cspace. Two sessions using the same handle number reach two different capabilities, and neither can reach the other's.
  • A cleared secret_ref. If a Secret capability's secret_ref points at a store slot that has been zeroed, injection has nothing to inject; the performing step treats this as an internal error (ERR_INTERNAL) rather than sending an empty credential, because a silently missing key is worse than a loud failure.

7.11Invariants

These are the properties the capability system must always maintain. The test plan (Chapter 13) probes each, and a future formal model would establish them.

  1. The host never possesses a capability — only a handle, which is a plain index conferring nothing on its own.
  2. A slot grants authority only if the manifest installed it there, or it was derived by narrowing from one that was.
  3. A derived capability is a subset of its parent in every field: same or stricter predicate, rights no wider, same tool, same or stricter flow rule.
  4. Resolution of an out-of-range or Empty handle yields no authority and reads no memory outside the array.
  5. Secret bytes never leave the machine-only store except by injection at the performing step, and never travel toward the host.
  6. Bumping a session's epoch invalidates all of its capabilities in constant time, with no per-slot work.
  7. A fresh session's cspace is entirely Empty: no ambient authority.

7.12Open questions

Honest loose ends, so no one mistakes this for settled:

  • The cspace size (32) and session count (8) are provisional, pending the FPGA's real memory budget — the same open item the Monitor chapter raises about table sizes.
  • Whether the 16-bit epoch is wide enough, or whether long-lived sessions warrant 32 bits to remove any wrap concern (§7.8).
  • The exact bit assignments within rights for each ctype, and the precise per-type meaning of aux, are set by the tool catalogue and are not yet frozen.
  • Whether any capability should ever be derivable across sessions (for a supervised hand-off between agents), or whether the strict per-session sealing of §7.4 should remain absolute. The current answer is absolute; the question is left open pending the multi-agent work that is out of scope for v1.
