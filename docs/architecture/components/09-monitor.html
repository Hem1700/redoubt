The Monitor

Abstract. The Monitor is the only component of Redoubt that is trusted. Every other part — the operating system above it, the drivers, the entire computer the AI runs on — is assumed to be under an attacker's control. This chapter specifies the Monitor in full: what it is responsible for, why it runs in the most privileged mode of the processor, the pieces it is built from, how it executes, the sequence of checks each request passes through, how it guards secrets, the failures it must survive, the invariants it maintains, the alternatives that were rejected, and how the whole thing is tested. It is written to be read start to finish whether or not you have a hardware background.

Note to first-time readers.

A handful of terms recur throughout. Here is what each means in plain language; no prior hardware knowledge is assumed.

AI agent
A program built on a language model that does not merely converse but takes actions in the world: it fetches URLs, reads files, and calls APIs using your credentials. That capacity to act is what makes a compromised agent dangerous.
Prompt injection
Concealing instructions inside material the agent reads — a web page, a document — so that it follows the attacker rather than its operator. No reliable defense exists today, so the design assumes it succeeds.
Tool call
The moment an agent asks to do something: "fetch this URL", "read that file". Redoubt concerns itself with these moments alone, since they are the only means by which an agent can affect anything.
Machine mode
A RISC-V processor executes at one of three privilege levels; machine mode is the highest, comparable to root but enforced by the silicon itself. The Monitor runs here, and the agent's world runs one or two levels beneath it, unable to reach up.
Capability
An unforgeable token that is permission to perform one specific action — like a coat-check tag. Whoever holds tag 14 receives coat 14, and no coat can be obtained by calling out a number one has invented.

9.1Purpose

Consider an embassy in a hostile city. The staff inside may request that a cable be sent or the front gate opened, but they never hold the keys and never operate the radio themselves. A single guard stands at the one door. Every request passes through him; he checks it against his written orders and carries it out on the staff's behalf. One could bribe or replace every person in the building, and that guard would still refuse to transmit a message to the wrong government.

The Monitor is that guard. Here the staff are the AI agent and its tools, running on an ordinary computer we do not trust in the slightest. The Monitor runs on a separate chip and holds what matters: the secret keys and the physical connections to the network and to storage. The agent can never touch those directly. It can only submit a request to the Monitor and await a decision.

The Monitor's role is therefore narrow and exact. It owns five things, and no other component is permitted to:

  1. the decision — whether a requested action occurs at all;
  2. the secrets — credentials it will use on the agent's behalf but never surrender;
  3. the egress — the network and storage hardware, which it alone operates;
  4. the rules — the policy from which the decision is computed; and
  5. the locks — the hardware settings that make the four points above true.

Equally important is what it deliberately cannot do. It contains no task scheduler, no USB stack, no network protocol code, and no memory allocator. Each of those is thousands of lines of the kind of code that harbours bugs, and every bug inside the trusted component is one an attacker may aim at. We push all of it out into the untrusted world and keep the Monitor beneath roughly 2,500 lines — small enough that a single person can read the whole of it.

9.2Why the decision lives in machine mode

The problem to solve is stark. We have chosen to assume the worst: the agent is compromised, the tools are hostile, and even the small operating system that schedules everything (we call it Warden) may be subverted. If all of that can turn against us, where does one place the single piece that must hold? Somewhere the compromised parts cannot physically reach.

RISC-V provides exactly that. The processor executes at three privilege levels — machine, supervisor, user, in descending order of power — and it offers a feature called Physical Memory Protection, or PMP: a set of registers, writable only in machine mode, that declare certain ranges of memory off-limits to supervisor and user code. Supervisor code cannot so much as read those registers, let alone alter them.

That is the whole of the mechanism. The Monitor, running in machine mode, marks the secrets and the network hardware as reachable only from machine mode, then locks that setting until the next reboot. From that instant, should a wholly hijacked Warden attempt to read a key or address the network chip, the load instruction simply faults — not because some software check refused it, but because the silicon rejects the address. There is no code path to bypass, because no code is involved.

This is not a novel idea, which is reassuring. Apple employs it: their SPTM is a small monitor more privileged than the iPhone kernel, so that even a kernel compromise cannot rewrite the page tables.2 The Keystone and Sanctorum research systems do the same on RISC-V.3 We adopt a proven pattern and aim it at one narrow task: the agent's tool calls.

One consequence deserves emphasis, for it is what makes the project tractable. Because the boundary is a hardware privilege boundary, all the large and error-prone code — USB, TLS, filesystems, the entire host computer — may live outside the trusted component without weakening the guarantee. The Monitor need only be correct about the small, authority-bearing step. That is the trade that keeps it small.

9.3Internal structure

The Monitor is a small number of single-purpose parts joined in a fixed order. There is no plugin system and nothing ingenious: a request enters at one end and travels a straight line to the other. That straightness is deliberate. It is what allows us to state precisely how long the worst case takes, and precisely which piece of code may touch the secrets.

The parts, one at a time

the door (trap vector)
When the agent's side makes a request, the processor jumps into the Monitor here. This part saves a little state, checks what kind of event occurred, and — if it is a request, the only thing it should ever be — hands off to the dispatcher. Anything unexpected means the Monitor itself has hit a bug, which is handled separately (§9.9).
dispatcher
Reads which of exactly five commands was asked for. Five. Anything else is turned away at once, without touching a single table. That short list is the entire surface an attacker has to probe.
1 · parser
Confirms the request lies where it should in memory and is not lying about its size, then copies it somewhere the agent's side cannot reach. That copy matters more than it appears: were the request read in place, a fast attacker could alter it after the check but before the action. Copying first defeats the manoeuvre.
2 · resolver
Turns the coat-check tag (a number the host supplied) into an actual capability, or refuses. It also confirms the tag has not gone stale — the subject of the Sessions chapter — which is how an agent's permissions are cancelled instantly.
3–4 · predicate engine
The doorman with the guest list. The capability states, "you may call http.request, but only to these hosts, only over HTTPS, only with GET." This engine checks the request's arguments against those conditions. It is a plain loop over a short list — no regular expressions, no scripting, nothing that can run indefinitely.
5 · flow engine
Even where the call is permitted, this asks a second question: is it carrying data it should not? A secret key may not depart in the body of a request to a public server, for instance. This is a separate net from the doorman, and it catches different quarry.
6 · perform and inject
The only part that touches the outside world. Once all else has passed, it carries out the action, splices in the secret key where the policy directs (the agent never sees it), and labels whatever returns as untrusted.
audit logger
Records every decision, positive or negative, in a form that cannot be quietly altered afterwards — each entry chained to the previous by a hash. The latest hash can be read out to demonstrate the log has not been tampered with.
PMP setup and randomness
Two helpers to the side. One runs once at boot to raise the hardware walls; the other is a source of randomness for keys, with self-tests so that its failure is noticed.

9.4Use of memory

The Monitor's memory is deliberately dull, and dull is the highest praise one can offer memory in a security-critical program. There is no heap: nothing is allocated and freed while a request runs. Every scratch value is a fixed-size slot on a small stack. The Monitor therefore cannot fail for want of memory, and there is no allocator sitting present as a target.

The Monitor's private memory (sizes fixed at boot):
  sessions        a small table of active agent runs (e.g. 8)
  capabilities    each session's set of tickets — 16 bytes each, 32 per session
  policy          the compiled rules; written once at boot, never touched again
  audit log       a ring buffer of decisions
  stack           with a no-access guard region immediately below it

That guard region beneath the stack is a small thing that averts a bad day. Should the Monitor's stack ever grow too far (a bug), it meets a page the hardware forbids it to write, and faults at once rather than quietly overwriting the policy tables.

9.5Execution model

One request at a time, from start to finish, then the next. The Monitor does not juggle. Warden feeds it requests singly, so no two things happen at once inside the trusted component — which means no locks, and none of the maddening race conditions that accompany them. For code this important, that simplicity is worth more than speed.

How long may one request take? It is bounded. The checks are a short loop over a short list, without allocation or open-ended work, so the Monitor always finishes. The single place it may need to wait is the final step, when it addresses the network or storage chip and that chip is slow. Even there it waits against a timer; if the device does not answer in time it abandons the attempt with an error rather than hanging. A stuck peripheral must not be able to freeze the guard.

9.6The moment a request arrives

For those who wish to see the actual handoff: the agent's side executes a special instruction (ecall) that traps into machine mode. The processor records where to resume and jumps to the Monitor's entry point. In rough assembly:

on_trap:
    switch to the Monitor's own stack        # so the caller cannot interfere
    save the argument registers
    read the cause; if it is not "a request", go to the bug handler
    run the dispatcher                        # selects mediate / open / close / …
    place the answer (allow-or-deny, length) in the result registers
    return to the caller

Because the Monitor runs to completion without interruption, the state it must set aside is small and always the same. The caller reads back two things: the verdict, and the length of the response.

9.7The six checks, and why each exists

At the heart of the Monitor is a sequence of six checks. The reference algorithm appears in the main specification; what follows is why each step is present, which is the part easiest to get wrong.

1 — Is the request even well-formed?

All that follows trusts the parsed request, so this is the airlock. It confirms the request sits in the shared mailbox and nowhere more devious, that it does not claim more arguments than we allow, and then copies it somewhere private. Omit the copy and the door is left open to the alter-after-checking manoeuvre of §9.3.

2 — Do you actually hold this permission?

The host supplied a number. This step turns it into a real capability or declines. It also confirms the capability has not been revoked. Revocation is instantaneous: cancelling a session increments a counter, and every ticket it ever issued now fails a one-line comparison. No lists are searched.

3 — Is this ticket for this tool?

A capability is for one tool. We verify this cheaply before the costlier argument work, so that a file-reading ticket presented at the network is turned away immediately.

4 — Are the arguments allowed?

Here most attacks die. The rules run against the structured arguments, not against re-parsed text — which matters more than it sounds. A whole class of real bugs arises when the checker and the doer disagree about how to read a string; the classic case is a URL in which %2e slips a different host past a naive filter.4 We do not re-parse; we read the host field exactly as the action will use it, so there is nothing to disagree about.

5 — Is it smuggling data out?

A call may be entirely permitted and still be a problem if it carries a secret out the door. This is the second, independent net: a secret value is not admitted into a request bound for a public server, even to an allowed host. Two different checks catch two different attacks.

6 — Carry it out.

Only now does anything actually leave the chip. The Monitor performs the action, injects the secret the agent never saw, and stamps the result "untrusted" so that whatever receives the response knows not to believe it. Should the hardware error or time out, the caller receives an error — never a half-finished action.

9.8Handling of secrets

Keys are the thing most worth stealing, so this is the most careful path in the system. In short: the Monitor will use a key on your behalf, but it will never give it to you.

  • At rest, keys reside in the machine-only region, loaded once at boot; the temporary buffer used to load them is wiped immediately afterward.
  • In use, exactly one part reads a key — the injector — and it holds the plaintext only for the instant it takes to splice into an outgoing request, then wipes its copy.
  • There is no command, and no code path, that copies key bytes into a response. This is the principle of the secure element in a phone: one receives the use of a key, not the key itself.5

9.9When something goes wrong

There are three kinds of "wrong," and the Monitor treats them very differently.

  • A denial is normal. The agent asked for something it may not do; we decline, log it, show it on the small display, and continue. Nothing is broken.
  • A hardware fault at the final step (the network chip errors or is slow) returns to the caller as an error. The Monitor does not retry — retrying is the untrusted caller's concern.
  • An impossible fault — the Monitor tripping over a protection it itself set — means the Monitor has a bug, not that it is under attack. In that case it stops. It does not attempt to carry on in a possibly corrupt state. A halted Redoubt is safe, for it does nothing; a confused one is not.

9.10The invariants it maintains

To check our work, these are the things that must always hold. The test plan probes each, and a future formal proof would establish them properly.

  1. Nothing reaches the outbound hardware except the final step, and only after all six checks passed.
  2. Key bytes never appear in a response, nor anywhere the untrusted side can read.
  3. A capability slot is filled only if the policy, or a narrowing of it, placed it there.
  4. A derived capability is always weaker than its parent, never stronger.
  5. Every request finishes in a bounded number of steps.
  6. The rules are written once at boot and never afterward.
  7. The hardware walls are raised before any untrusted code runs.

9.11Alternatives rejected

Several designs looked reasonable and were declined. Knowing why is half the architecture.

Put the decision in the operating system. Simpler — one boundary rather than two. But then a single bug in that OS is a total bypass, and we specifically promised to survive an OS takeover. The premise is that the kernel is not the most trusted thing.

Rely on the MMU rather than PMP. The MMU, the usual virtual-memory hardware, is configured by the operating system, so a compromised OS can reconfigure it; it cannot wall anything off from itself. PMP is machine-only, which is why we rest the real wall on it. (The MMU remains useful one level down, for keeping compartments apart.)

Make it fast with pipelining and queues. That drags concurrency, buffers, and locks into the trusted component — more code and more ways to be wrong. The waiting is dominated by the network in any case. Not worth it for a first version.

Let an AI model assist the decision. That is the very thing we are escaping: a decision that is non-deterministic and can be talked into a "yes." There is no model anywhere on the decision path, by design.

A flexible policy language with loops and callbacks. Powerful, and also an excellent way to build something that can loop forever or that no one can audit. The rules are deliberately a language that can do no more than check conditions.

9.12One request, followed all the way through

Let us watch an attack fail. The agent has been prompt-injected and is attempting to steal an API key by posting it to a server the attacker controls. It holds the web capability, tag 3.

the door    a request arrived; save state; it is a "mediate" → proceed
check 1     it is in the mailbox, of the right size → copy it in
check 2     session 1 is live; tag 3 → the web capability; not revoked → ok
check 3     the ticket is for http.request, and that is what was asked → ok
check 4     rule: scheme must be https → ok
            rule: host must be one of {api.example.com} → but it is "evil.tld" → NO
            → DENY, reason: bad argument (the host)
log         record it; the tamper-evident chain advances
display     the small screen shows "DENIED — host"
return      verdict: denied. Nothing was sent. The key was never touched.

And had the agent been cleverer, aiming at the real api.example.com with the key tucked into the request body? Check 4 would pass, and then check 5 would catch it: a secret may not leave that way. Two nets, both plain, both impossible to sweet-talk.

9.13How it is tested

Claims are cheap; here is how each is checked.

  • Ordinary unit tests on a laptop for the fiddly logic: the parser's bounds, the revocation counter, the argument rules, the memory arithmetic.
  • Simulating the actual chip (Verilator) to confirm the hardware wall truly faults when the untrusted side reaches for the secrets — the one promise that cannot be tested in software alone.
  • A containment suite that runs each attack from the threat model and insists on the exact denial, and, crucially, that nothing left the chip.
  • Fuzzing the parts that read attacker-controlled bytes, with memory-error detection enabled.
  • A build that fails should the trusted code exceed its line budget, or should unsafe code appear outside the one place we permit it.

9.14Open questions

Honest loose ends, so that no one mistakes this for finished:

  • The exact table sizes, once we know how much room the FPGA truly affords.
  • Whether splicing in a secret must be constant-time, to avoid leaking its length through timing — part of the broader side-channel question set aside for now.
  • How long to wait on the network versus the storage chip before giving up.
  • Whether the chosen processor build has the newer PMP feature we would prefer, or the older locking method must be used instead.1
