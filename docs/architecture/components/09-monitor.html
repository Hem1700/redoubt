The Monitor

If you only ever read one chapter of this manual, read this one. The Monitor is the part of Redoubt we actually trust. Everything else — the operating system above it, the drivers, the whole computer the AI runs on — we assume can be taken over by an attacker. The Monitor is the small piece that has to stay honest when nothing else does.

New to this? Start here.

A few words show up constantly below. Here's what they mean, in plain terms — you don't need a hardware background to follow the rest.

An "AI agent"
A program built around a language model that doesn't just chat — it takes actions: fetches URLs, reads files, calls APIs with your keys. That's what makes it dangerous when someone tricks it.
"Prompt injection"
Hiding instructions in something the agent reads (a web page, a file) so the agent obeys the attacker instead of you. Today there's no reliable way to stop the agent from falling for it, so we plan around it happening.
A "tool call"
The moment an agent asks to do something in the world — "HTTP GET this URL", "read that file". Redoubt only cares about these moments, because they're the only way an agent can cause harm.
"M-mode" (machine mode)
A RISC-V chip runs code at one of three privilege levels. Machine mode is the most powerful, like root but enforced by the silicon. The Monitor runs here; the agent's world runs a level or two below it and can't reach up.
A "capability"
An unforgeable ticket that is permission to do one specific thing. Think of a coat-check tag: whoever holds tag #14 gets coat #14, and you can't get a coat by shouting a number you made up.

§9.1What the Monitor is for

Picture an embassy in a hostile city. The people inside can ask to send a cable or open the front gate, but they never hold the keys and they never touch the radio themselves. One guard stands at the one door. Every request goes through him, he checks it against his written orders, and he does it on their behalf. You could bribe or replace every single person inside the building, and that guard still won't transmit a message to the wrong government.

The Monitor is that guard. In our case the "people inside" are the AI agent and its tools, running on a normal computer we don't trust at all. The Monitor runs on a separate chip and holds the things that matter: the secret keys, and the actual wires out to the network and storage. The agent can never touch those directly. It can only send the Monitor a request and wait for a yes or a no.

So the Monitor's job is small and specific. It owns exactly five things, and nothing else is allowed to:

  • the decision — given a request, does this action happen or not;
  • the secrets — API keys and credentials, which it will use on the agent's behalf but never hand over;
  • the way out — the network and storage hardware, which only it can operate;
  • the rules — the policy the decision is computed from;
  • the locks — the hardware settings that make all of the above true.

Just as important is what it deliberately can't do. It has no task scheduler, no USB stack, no network protocol code, no memory allocator. Every one of those is thousands of lines of the kind of code that has bugs, and every bug in the trusted part is a bug an attacker can aim at. So we push all of it out into the untrusted world and keep the Monitor under about 2,500 lines. Small enough that one person can actually sit down and read the whole thing.

§9.2Why it lives in the most privileged corner of the chip

Here's the problem we're solving. We've decided to assume the worst: the agent is compromised, the tools are malicious, and even the little operating system that schedules everything (we call it Warden) might be taken over. If all of that can turn against us, where do you put the one piece that has to hold? You put it somewhere the compromised parts physically can't reach.

RISC-V gives us exactly that. The chip runs code at three privilege levels — Machine, Supervisor, User, most to least powerful. And it has a feature called PMP, Physical Memory Protection. PMP is a set of registers, writable only in Machine mode, that say "this range of memory is off-limits to Supervisor and User code." Supervisor code can't even read those registers, never mind change them.

That's the whole trick. The Monitor, running in Machine mode, marks the secrets and the network hardware as reachable only from Machine mode, and then locks that setting so it can't be undone until the next reboot. From that moment on, if a completely hijacked Warden tries to read a key or poke the network chip, the load instruction simply faults. Not because some software check said no — because the silicon refuses the address. There's no code path to skip, because there's no code involved.

This isn't a new idea, which is a good sign. Apple does it: their "SPTM" is a tiny monitor more privileged than the iPhone kernel, so even a kernel takeover can't rewrite page tables. The Keystone and Sanctorum research projects do the same on RISC-V. We're borrowing a proven pattern and pointing it at one narrow job: the agent's tool calls.

One consequence is worth sitting with, because it's what makes the whole project tractable. Because the boundary is a hardware wall, all the big scary code — USB, TLS, filesystems, the entire host computer — can live outside the trusted part without weakening anything. The Monitor only has to be correct about the small step where a decision gets made. That's the trade that keeps it tiny.

§9.3What's inside it

The Monitor is a handful of small pieces bolted together in a fixed order. There's no plugin system and nothing clever — a request comes in one end and walks a straight line to the other. That straightness is on purpose: it's what lets us say, with a straight face, exactly how long the worst case takes and exactly which piece of code is allowed to touch the secrets.

The pieces, one at a time

the door (trap vector)
When the agent's side makes a request, the chip jumps into the Monitor here. This piece saves a little state, checks what kind of event happened, and — if it's a request, which is the only thing it should ever be — hands off to the dispatcher. Anything unexpected means the Monitor itself hit a bug, and that's handled separately (see §9.9).
dispatcher
Looks at which of exactly five commands was asked for. Five. Anything else gets turned away on the spot without touching a single table. That short list is the entire "surface" an attacker gets to prod at, which is the point.
1 · parser
Checks the request is where it should be in memory and isn't lying about its size, then copies it somewhere the agent's side can't reach. That copy matters more than it looks: if we read the request in place, a fast attacker could change it after we checked it but before we act on it. Copying first closes that trick.
2 · resolver
Turns the coat-check tag (a number the host sent) into an actual capability, or refuses. It also checks the tag hasn't gone stale — more on that when we get to sessions in another chapter — which is how we cancel an agent's permissions instantly.
3–4 · predicate engine
The bouncer with the guest list. The capability says "you may call http.request, but only to these hosts, only over HTTPS, only GET." This engine checks the request's arguments against those rules. It's a plain loop over a short list of conditions — no regex, no scripting, nothing that could run forever.
5 · flow engine
Even if the call itself is allowed, this asks a second question: is it carrying data it shouldn't? A secret key isn't allowed to ride out in the body of a request to a public server, for instance. This is a separate net from the bouncer, and it catches different fish.
6 · do-it-and-inject
The only piece that touches the outside world. Once everything's passed, it performs the action, slips in the secret key where the policy said to (the agent never sees it), and labels whatever comes back as untrusted.
audit logger
Writes down every decision, yes or no, in a way that can't be quietly edited later (each entry is chained to the last with a hash). You can read the latest hash out to prove the log hasn't been tampered with.
PMP setup & randomness
Two helpers off to the side. One runs once at boot to put up the hardware walls; the other is a random-number source used for keys, with self-tests so we notice if it goes bad.

§9.4How it uses memory

The Monitor's memory is boring on purpose, and boring is the highest compliment you can pay memory in a security-critical program. There's no heap — nothing is allocated and freed while a request runs. Every scratch value is a fixed-size slot on a small stack. That means the Monitor can never fail because it "ran out of memory," and there's no allocator sitting there as a target.

What lives in the Monitor's private memory (sizes are fixed at boot):
  sessions        a small table of active agent runs (say, 8)
  capabilities    each session's set of tickets — 16 bytes each, 32 per session
  policy          the compiled rules; written once at boot, never touched again
  audit log       a ring buffer of decisions
  stack           with a "no-access" guard region right below it

That guard region under the stack is a small thing that saves you from a bad day. If the Monitor's stack ever grows too far (a bug), it runs into a page the hardware won't let it write, so it faults immediately instead of quietly scribbling over the policy tables.

§9.5How it runs

One request at a time, start to finish, then the next. The Monitor doesn't juggle. Warden feeds it requests one by one, so there are no two things happening at once inside the trusted core — which means no locks, and none of the maddening race-condition bugs that come with them. For a piece of code this important, that simplicity is worth more than speed.

How long can one request take? Bounded. The checks are a short loop over a short list, no allocation, no open-ended work, so the Monitor always finishes. The one place it might have to wait is the very last step, when it's talking to the network or storage chip and that chip is slow. Even there it waits with a timer running; if the device doesn't answer in time it gives up with an error rather than hanging forever. A stuck peripheral shouldn't be able to freeze the guard.

§9.6The moment a request arrives

For readers who want to see the actual handoff: the agent's side runs a special instruction (ecall) that traps into Machine mode. The chip records where to come back to and jumps to the Monitor's entry point. In rough assembly:

on_trap:
    switch to the Monitor's own stack        # so the caller can't mess with it
    save the argument registers
    read the cause; if it isn't "a request", go to the bug handler
    run the dispatcher                        # picks mediate / open / close / …
    put the answer (allow-or-deny, length) back in the result registers
    return to the caller

Because the Monitor runs to the end without being interrupted, the amount of state it has to stash away is tiny and always the same. The caller reads back two things: the verdict, and how long the response is.

§9.7The six checks, and why each one exists

The heart of the Monitor is a sequence of six checks. The main manual has the exact algorithm; what follows is why each step is there, because that's the part that's easy to get wrong.

1 — Is this request even well-formed?

Everything after this trusts the parsed request, so this is the airlock. It confirms the request sits in the shared mailbox and nowhere sneakier, that it isn't claiming more arguments than we allow, and then copies it somewhere private. Skip the copy and you've left the door open to the change-it- after-the-check trick from §9.3.

2 — Do you actually hold this permission?

The host handed us a number. This step turns it into a real capability or says no. It also checks the capability hasn't been revoked. Revocation is instant here: cancelling a session bumps a counter, and every ticket it ever issued now fails a one-line comparison. No hunting through lists.

3 — Is this ticket for this tool?

A capability is for one tool. We check that cheaply before doing the more expensive argument work, so a file-reading ticket waved at the network gets bounced right away.

4 — Are the arguments allowed?

This is where most attacks die. The rules run against the structured arguments, not re-parsed text. That matters more than it sounds. A whole class of real bugs comes from the checker and the doer disagreeing about how to read a string — the classic one is a URL where %2e sneaks a different host past a naive filter. We don't re-parse; we read the host field the same way the action will use it, so there's nothing to disagree about.

5 — Is it smuggling data out?

A call can be perfectly allowed and still be a problem if it's carrying a secret out the door. This step is the second, independent net: a secret value isn't permitted into a request bound for a public server, even to an allowed host. Two different checks catch two different attacks.

6 — Do it.

Only now does anything actually leave the chip. The Monitor performs the action, injects the secret the agent never saw, and stamps the result "untrusted" so whatever gets the response knows not to believe it. If the hardware errors or times out, the caller gets an error — never a half-finished action.

§9.8How secrets are handled

Keys are the thing most worth stealing, so this is the most careful path in the whole system. The short version: the Monitor will use a key for you, but it will never give it to you.

  • At rest, keys sit in the machine-only region, loaded once at boot; the temporary buffer used to load them is wiped right after.
  • In use, exactly one piece of code reads a key — the injector — and it holds the plaintext only for the instant it takes to splice it into an outgoing request, then wipes its copy.
  • There is no command, and no code path, that copies key bytes into a response. This is the same idea as the secure chip in an iPhone: you get the use of a key, not the key.

§9.9When something goes wrong

There are three flavors of "wrong," and the Monitor treats them very differently.

  • A denial is normal. The agent asked for something it isn't allowed to do; we say no, log it, flash it on the little screen, and carry on. Nothing's broken.
  • A hardware hiccup at the last step (the network chip errors or is slow) comes back to the caller as an error. We don't retry inside the Monitor — retrying is the untrusted caller's problem.
  • An impossible fault — the Monitor itself tripping over a memory protection it set — means the Monitor has a bug, not that it's under attack. In that case it stops. It doesn't try to soldier on in a possibly-corrupt state. A halted Redoubt is safe (it does nothing); a confused one isn't.

§9.10The promises it keeps

If you want to check our work, these are the specific things that must always be true. The test plan pokes at each one, and a future formal proof would nail them down for real.

  • Nothing reaches the outbound hardware except the final step, and only after all six checks passed.
  • Key bytes never end up in a response or anywhere the untrusted side can read.
  • A capability slot is filled only if the policy (or a narrowing of it) put it there — no permissions appear from nowhere.
  • A derived capability is always weaker than its parent, never stronger.
  • Every request finishes in a bounded number of steps.
  • The rules are written once at boot and never change afterward.
  • The hardware walls go up before any untrusted code runs.

§9.11Roads we didn't take

A few designs looked reasonable and we turned them down. Knowing why is half the architecture.

Put the decision in the operating system. Simpler — one boundary instead of two. But then a single bug in that OS is a total bypass, and we specifically promised to survive an OS takeover. The entire premise is that the kernel is not the most trusted thing.

Rely on the MMU instead of PMP. The MMU (the usual virtual-memory hardware) is set up by the operating system, so a compromised OS can reconfigure it. It can't wall anything off from itself. PMP is machine-only, which is exactly why we lean on it for the real wall. (The MMU is still handy one level down, for keeping compartments apart.)

Make it fast with pipelining and queues. That drags concurrency, buffers, and locks into the trusted core — more code and more ways to be wrong. The waiting is dominated by the network anyway. Not worth it for v1.

Let an AI model help decide. That's the exact thing we're trying to escape: a decision that's non-deterministic and can be talked into a "yes." There is no model anywhere in the decision path, on purpose.

A flexible policy language with loops and callbacks. Powerful, and also a great way to build something that can loop forever or that nobody can audit. The rules are deliberately a language that can't do more than check conditions.

§9.12Following one request all the way through

Let's watch an attack fail. The agent has been prompt-injected and is trying to steal an API key by POSTing it to a server the attacker controls. It holds the web capability (tag 3).

the door    a request arrived; save state; it's a "mediate" → go
check 1     it's in the mailbox, right size → copy it in
check 2     session 1 is live; tag 3 → the web capability; not revoked → ok
check 3     the ticket is for http.request, and that's what was asked → ok
check 4     rule: scheme must be https → ok
            rule: host must be one of {api.example.com} → but it's "evil.tld" → NO
            → DENY, reason: bad argument (the host)
log         write it down; the tamper-evident chain moves forward
screen      the little display shows "DENIED — host"
return      verdict: denied. Nothing was sent. The key was never touched.

And if the agent had been cleverer and aimed at the real api.example.com with the key tucked in the request body? Check 4 would pass, and then check 5 would catch it: a secret isn't allowed to leave that way. Two nets, both dumb-simple, both impossible to sweet-talk.

§9.13How we test all this

Claims are cheap; here's how each one gets checked.

  • Ordinary unit tests on a laptop for the fiddly logic: the parser's bounds, the revocation counter, the argument rules, the memory math.
  • Simulating the actual chip (Verilator) to confirm the hardware wall really faults when the untrusted side reaches for the secrets. That's the one promise you can't test in software alone.
  • A "containment" suite that runs each attack from the threat model and insists on the exact denial — and, crucially, checks that nothing went out the door.
  • Fuzzing the parts that read attacker-controlled bytes, with memory-error detection turned on.
  • A build that fails if the trusted code creeps over its line budget, or if unsafe code shows up outside the one place we allow it.

§9.14Still open

Honest loose ends, so nobody thinks this is finished:

  • The exact table sizes, once we know how much room the FPGA really has.
  • Whether splicing in a secret needs to be constant-time to avoid leaking its length through timing (part of the bigger side-channel question we've parked for now).
  • How long to wait on the network vs. the storage chip before giving up.
  • Whether our chosen CPU build has the newer PMP feature we'd prefer, or we use the older locking method instead.
