Egress & Secrets

Abstract. Everything else in Redoubt is about deciding. This chapter is about the one place where a decision turns into an act in the world: bytes leaving on a wire, a block written to a card, a key spliced into a request. The egress subsystem is the hardware the Monitor keeps for itself and lets nothing else touch, the network link to the ESP32, the microSD controller, the secret store, and the noise source that seeds our randomness. It specifies how each is reached, how a secret is used without ever being surrendered, and where the honest seams are: the ESP32 firmware sits inside the egress path, and wired Ethernet is a version-two upgrade, not a thing we have today. It closes with the sequence a real call follows from the agent's request to the wire and back.

Note to first-time readers.

A few pieces of hardware and one cryptographic idea recur below. Here is each in plain terms.

Egress
Anything leaving the trusted core toward the outside, a network packet, a file being saved. The word simply means "the way out," and this chapter is about owning it.
ESP32
A small, cheap, self-contained networking chip that speaks Wi-Fi. Redoubt uses it as its network card. It is a separate computer with its own firmware, which is exactly the caveat we keep returning to.
MMIO
Memory-mapped I/O. Hardware devices appear to the processor as special memory addresses; writing to the address commands the device. Because it looks like memory, the same PMP walls that protect memory can protect a device.
Secret injection
Using a key on the agent's behalf, pasting it into an outgoing request, without ever handing the key back to the agent. The agent gets the effect of the key, never its bytes.
TRNG
A true random-number generator: hardware that produces genuine unpredictability from a physical process, as opposed to a formula. Keys and session identifiers need this.

12.1Why the Monitor owns the exits

Recall the embassy guard of Chapter 9. The reason the guard's decisions mean anything is that he alone works the radio and holds the keys to the gate. If any clerk could walk over and transmit a cable directly, the guard's careful adjudication would be theatre. The security of the whole system rests on a physical fact: the dangerous hardware is reachable only through the one component we trust.

Egress is that hardware. The network link, the storage controller, the secret store, and the entropy source all live in a single machine-only region of the address map, EGRESS_MMIO at 0xF000_0000, plus the SECRETS region at 0x1002_0000, walled off by PMP entries that are written and locked at boot before any supervisor or user code runs (Chapter 3). From that instant a compromised Warden or a hostile driver that reaches for the ESP32's registers does not get a refusal from some software check; it gets a fault from the silicon, because the address is simply not theirs to touch.1

So the untrusted world can prepare an egress payload all it likes, format a packet, lay out a block to write, but it cannot send. The send is a Monitor action, reached only through the mediation ABI, and it happens only after the six checks have passed. This chapter is what lives on the far side of check six.

12.2Network: the ESP32 link

Redoubt has no Ethernet MAC of its own in version one. Its network card is an ESP32 module, reached over a link, UART or SPI, whose controller registers sit inside EGRESS_MMIO, and which is therefore M-owned like everything else in that region. A user-mode network driver may assemble the payload in its own compartment, but when it wants that payload to actually leave, it must ask the Monitor, which applies the Net capability check, injects any secret the policy directs, and only then drives the link.

Now the honest part, and it is important enough that we will not bury it. The ESP32 runs its own firmware, a closed module we did not write and do not measure. That firmware is in the egress path. Concretely: once the Monitor hands vetted, secret-injected bytes to the ESP32, what the ESP32 does with them, how it forms the TLS session, whether its own stack has bugs, is outside our trusted base. We can guarantee that nothing reaches the ESP32 except through the Monitor's checks. We cannot guarantee the ESP32 itself is flawless, and we do not claim to.2

This is a real limitation, and the roadmap addresses it head-on. Version two moves to a wired-Ethernet board (an ECPIX-5 or Colorlight class device) where the Monitor owns the MAC directly in the FPGA fabric, removing the closed firmware from the trusted path entirely. Until then, the ESP32 buys us a working network on cheap, available hardware, and we are precise about what that costs. It is worth saying plainly that this seam does not widen the agent's authority, a hijacked agent still cannot get the Monitor to send to a disallowed host or leak a secret; the ESP32 caveat is about the integrity of the pipe, not about who may use it.

12.3Storage: LiteSDCard

Storage is simpler and cleaner than the network, because there is no third-party firmware in the way. A microSD card is driven by the LiteSDCard controller, whose MMIO also lives in the machine-only egress region. Block reads and writes are Monitor actions gated by File capabilities, and a File capability is not "you may use the disk", it is far narrower.

Gate on a File capabilityWhat it constrains
path prefixthe capability names an allowed prefix, e.g. /corpus/; a PATH TypedArg not under it fails the predicate with DENY_ARG
moderead, write, or both, a read-only corpus capability cannot be turned into a write
result labelfile contents returned to a caller are stamped UNTRUSTED (Chapter 10)

A small filesystem index lives in the Monitor's private data region so the path check is done against a structure the untrusted side cannot rewrite. The path itself is a typed PATH argument checked with the PREFIX predicate operator, so the same anti-parser-mismatch discipline from the wire protocol (Chapter 6) applies: the Monitor checks the path exactly as it will use it, with no re-parsing step where a checker and a doer could come to disagree about what /corpus/../secrets means.3

12.4Secrets: used, never surrendered

Keys are the thing most worth stealing, so the secret store is the most carefully guarded path in the whole design. The governing principle is one sentence: the Monitor will use a secret on your behalf, but it will never give it to you. This is the same bargain a phone's secure element strikes, software receives the use of a key, never the key material.4

The lifecycle of a key

  • At boot. Secrets are loaded once, from an M-only area of QSPI flash, into the SECRETS region. The temporary buffer used during the load is wiped the instant the copy is done, so the plaintext exists in two places for as short a time as we can arrange.
  • At rest. Keys live in SECRETS (region #3 of the memory map), reachable only from machine mode. No supervisor or user load instruction can read a byte of it; the attempt faults.
  • In use. Exactly one piece of code, the injector, part of the perform step, reads a key. It holds the plaintext only for the moment it takes to splice the secret into an outgoing request (as an HTTP Authorization header, say), then wipes its working copy.
  • Never. There is no ABI opcode, and no code path, that copies key bytes into a response. A capability of type Secret permits injection at a named site and nothing else; its secret_ref is an index the Monitor resolves internally, never a value the host can read back.

The mechanics of injection matter because they are where a careless design would leak. The agent's request references a secret only by capability, it says, in effect, "make this call, and put credential number 2 where the policy says it goes." It never names the value, never sees the value, and cannot ask for the value. The Monitor looks up the site from the capability's secret_ref, reads the key from SECRETS, writes it into the outgoing bytes after the flow check has cleared the call, sends, and scrubs. The result that comes back is labeled UNTRUSTED and contains no trace of the key. Between "look up" and "scrub," the plaintext lives on the Monitor's own stack in machine-only memory and nowhere else.

One subtlety we are watching: the injection should ideally be constant-time, so that the length or content of a secret cannot be inferred from how long the splice takes. That belongs to the broader side-channel question the project sets aside for version one, but it is flagged here because the secret path is exactly where such a leak would hurt most.

12.5One call, from request to wire

Here is the whole egress path in motion. The agent, on the untrusted host, wants to call an API that needs a credential it does not hold. It issues a tool call; the request is framed and delivered; the Monitor decides, injects, and sends; the answer comes back stamped untrusted. Watch where the secret appears and where it does not.

Two things about this picture repay a second look. First, Warden, the supervisor-mode microkernel, is on the path but decides nothing; it schedules the request to the Monitor and relays the answer, and if it were fully compromised the security property would still hold, because it never touches the egress hardware or the secret. Second, the secret's entire existence as plaintext is confined to the Monitor's activation box on the right of the diagram. It is read from SECRETS, spliced, sent, and wiped, all within machine mode. Nothing to the left of the Monitor's lifeline, not Warden, not the Endpoint, not the host, ever holds it.

12.6The TRNG: randomness you can trust

Several parts of Redoubt need genuine unpredictability: randomising capability handles so they cannot be guessed, seeding session identifiers, and any future key generation. A formula-based pseudo-random generator is not enough here, because its output is predictable to anyone who learns its seed. Redoubt therefore uses a hardware entropy source: a ring oscillator built in the FPGA fabric, whose jitter is a physical process no attacker can compute ahead of time.

Raw physical entropy is never trusted blindly, though, because entropy sources fail, they can get stuck, or degrade with temperature, and a silently failing noise source that keeps handing out the same "random" value is worse than no source at all. So the TRNG output passes continuous health tests drawn from NIST SP 800-90B: the Repetition-Count Test, which trips if a value repeats too many times in a row, and the Adaptive-Proportion Test, which trips if one value dominates a window.5 If either test fails, entropy-consuming operations block rather than proceed on suspect randomness. A stalled key generator is safe; one running on a stuck source is not. This treatment of the entropy source as a first-class, isolated, self-checking element follows the same instinct as Baochip's high-assurance TRNG design.6

12.7Edge cases and failure modes

  • The ESP32 errors or stalls. The send is bounded by a timer. If the link does not complete in time the Monitor abandons the attempt and returns ERR_EGRESS (0x20) or ERR_TIMEOUT (0x21) to the caller, never a half-finished action. Retrying is the untrusted caller's business, not the Monitor's.
  • The SD card is absent or write-protected. A storage action against missing or read-only media returns ERR_EGRESS; the capability check has already passed, so this is a hardware condition, reported as one.
  • The TRNG health test fails mid-operation. Entropy consumers block. This is a deliberate availability sacrifice: we would rather stall than issue a guessable handle.
  • A secret injection where the send then fails. The plaintext is wiped in the same path whether the send succeeded or errored; there is no error branch that skips the scrub.
  • An impossible fault touching egress hardware. If the Monitor trips over a protection it itself set while reaching the egress region, that is a Monitor bug, and it halts rather than continue in a possibly corrupt state (Chapter 9). A halted Redoubt sends nothing, which is safe.

12.8The invariants it maintains

  1. No effect reaches the network or storage hardware except from the Monitor's perform step, after all six checks have passed.
  2. Secret bytes never appear in a response, in the return path, or anywhere the untrusted side can read; plaintext exists only in machine-only memory, only during injection.
  3. Every egress result is labeled UNTRUSTED before it crosses back to the host.
  4. The load buffer for secrets, and the injector's working copy, are wiped on every path, including error paths.
  5. Randomness is issued only from a TRNG whose health tests are currently passing.
  6. Every egress operation is bounded by a timeout; a slow or stuck device cannot freeze the Monitor.

12.9Alternatives rejected

The exits are where hardware reality bites hardest, so several tempting shortcuts were declined.

Let a driver drive the ESP32 directly for speed. Give the user-mode network driver raw access to the link and skip the trip through machine mode. This is faster and it also demolishes the entire guarantee: a compromised driver could then send anything anywhere and inject or read secrets. The send has to be a Monitor action or the wall means nothing.

Ship wired Ethernet in version one. It is the right destination, the Monitor owning the MAC in fabric removes the ESP32 firmware from the trusted path. But it needs a different, more expensive board and considerably more FPGA work, and version one's job is to demonstrate the mediation architecture on cheap, available hardware. We took the ESP32 with eyes open and wrote the caveat down rather than pretending the seam is not there.

Hand the agent a short-lived token instead of injecting. Rather than splice a secret the agent never sees, mint a scoped token and let the agent use it. Sometimes reasonable, but it moves a credential, even a narrow one, onto the untrusted host, where a hijacked agent can spend it however the token allows and can exfiltrate the token itself. Inject-only keeps every credential on the trusted side of the boundary, which is the stronger position.

Return secrets to trusted callers "just this once." Add an ABI that reads a key, guarded by a special capability. Every such door is a door, and the moment one exists the invariant "secret bytes never leave" becomes "secret bytes never leave except when they do," which is not an invariant. There is no read-secret opcode, by design.

Use a software PRNG seeded once at boot. Cheaper than a hardware source and free of health-test complexity. Also predictable to anyone who recovers the seed, and with no way to notice degradation. For handles and keys that must resist guessing, a checked physical source is worth its cost.

12.10Open questions

  • The exact M-owned link protocol to the ESP32, and how much of it is the Monitor's versus a user-mode driver's, the boundary is drawn in principle but the wire details are unsettled.
  • Timeout values: how long to wait on the network link versus the SD controller before returning an error. These want measurement on real hardware, not a guess.
  • Whether secret injection must be constant-time in version one, or whether that can wait with the rest of the side-channel work.
  • How secrets are provisioned into the M-only QSPI area in the first place, and whether that provisioning step needs its own attested ceremony.
  • Whether the version-two wired-Ethernet MAC should be accompanied by the Monitor owning a TLS implementation, or whether TLS stays outside the trusted base with only the transport owned.
