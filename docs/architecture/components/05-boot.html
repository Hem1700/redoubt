Boot & Root of Trust

Abstract. Every guarantee Redoubt makes rests on one assumption: that the Monitor which starts running after a reset is the exact Monitor we wrote, not a substitute an attacker slipped in. This chapter explains how that assumption is earned rather than merely hoped for. It walks the machine from power-on to the first mediated tool call, one step at a time, the FPGA loading its circuit, a tiny boot ROM weighing the Monitor against a known fingerprint and halting if they differ, the Monitor raising the hardware walls before anything untrusted can run, seeding its secrets and its randomness, compiling the policy, and finally handing control down to the layers above. It sets out why the order of those steps is itself a security property, how the boot leaves behind a tamper-evident record that a remote party can check, and, plainly, the one link in the chain that version 1 does not yet secure.

Note to first-time readers.

This chapter leans on a few ideas that sound more forbidding than they are. Here is each in plain language; no hardware background is assumed.

Root of trust
The one thing you decide to trust without checking, because everything else is checked by it. You cannot verify infinitely far down, so somewhere the regress has to stop. The art is making that starting point as small and as fixed as possible.
Bitstream
An FPGA is a blank field of logic gates; a bitstream is the file that wires them into a specific circuit, here, our RISC-V processor and its surrounding hardware. On power-up the chip reads the bitstream from a small flash memory and becomes that circuit.
Measurement
Computing a cryptographic hash of a piece of software before running it, a short fingerprint that changes completely if even one byte of the software changes. To "measure" the Monitor is to fingerprint it and compare against the fingerprint we expect.
Boot ROM (BROM)
A very small program, fixed in the hardware and unchangeable at runtime, that runs first after reset. Its only job is to measure the next thing and refuse to continue if the measurement is wrong.
PMP
Physical Memory Protection: machine-mode-only registers that fence off regions of memory from less-privileged code. It is the wall the whole design leans on, specified in Chapter 3.

5.1What a root of trust actually is

Suppose someone hands you a sealed letter and swears it is genuine. You could check the seal, but only if you already trust the stamp that made it. You could check the stamp against a registry, but only if you trust the registry. Verification always leans on something you did not verify, and at some point the leaning has to stop against a surface you simply accept. That surface is the root of trust.

For a security system the whole game is choosing that surface well. A good root of trust is small, so there is little in it to be wrong; fixed, so an attacker cannot quietly edit it; and first, so that everything after it is measured before it gets to act. Redoubt's root is two tiny things taken together: a boot ROM baked into the hardware, and an expected fingerprint of the Monitor stored alongside it. The boot ROM cannot be rewritten while the machine runs, and the fingerprint is a fixed constant. Between them they answer a single question, is the software about to run in machine mode really ours?, and they refuse to let the machine proceed if the answer is no.

Notice what this buys and what it does not. It does not stop anyone from putting different software on the flash chip; nothing in version 1 can. What it guarantees is that if different software is there, the machine will notice and stop, rather than running the impostor as though it were trusted. A halted Redoubt does nothing, and doing nothing is safe. A Redoubt that boots the wrong Monitor would hand an attacker the keys and the network in one motion, so refusing to boot is exactly the right failure.

5.2The boot sequence, step by step

From the instant power arrives to the first tool call the agent can make, the machine passes through five stages. Each hands to the next only after it has done its own job completely. The diagram traces the path; the paragraphs below walk it slowly.

Stage 0, the FPGA becomes a computer

Redoubt is not a fixed chip with a processor etched into it. It is a Lattice ECP5 FPGA, a blank canvas of programmable logic. When power arrives the ECP5 reads a bitstream out of a small QSPI flash memory and configures itself into the circuit that bitstream describes, in our case a VexRiscv RISC-V core, memory controllers, the OLED and network links, and the random-number source, all wired together by LiteX (Chapter 4 covers that hardware in detail). Only once this configuration finishes is there a processor at all. The very first instruction the new processor executes lives in the boot ROM at address 0x0000_0000.

This stage is also the honest weak point of version 1, and §5.7 says so at length. For now the thing to hold onto is that the bitstream is loaded before any measuring happens, because there is nothing to do the measuring until the circuit exists.

Stage 1, the boot ROM weighs the Monitor

The processor starts in machine mode, the most privileged level, running the boot ROM. The boot ROM is deliberately minute, under three hundred lines of code, because it, too, is part of the trusted base and every line in the trusted base is a line that must be right. It does exactly one interesting thing. It reads the Monitor image out of its code region and computes a BLAKE2s-256 hash of it: a 32-byte fingerprint.1 Then it compares that fingerprint, byte for byte, against H_expected, a constant compiled straight into the bitstream, sitting in on-chip block RAM where runtime code cannot rewrite it.

If the two fingerprints match, the boot ROM jumps into the Monitor. If they differ by so much as a single bit, it halts. Not "logs a warning and carries on", halts, permanently, until the next reset. There is no third option and no override, because an override is precisely the door an attacker would aim for.

Stage 2, the Monitor raises the walls and prepares itself

Now our code is running, and running in machine mode, which is the only mode that can configure the hardware walls. Its first act, before it does anything else at all, is to program the PMP entries that fence the secrets and the egress hardware off from every less-privileged mode, and then set the lock bits so those entries cannot be changed again until reset (the register-level detail is Chapter 3). Section 5.3 explains why this has to come first and why "first" is not a stylistic preference but a security property.

With the walls up, the Monitor prepares the rest of its world in a fixed order: it loads the secrets from their machine-only flash area into the machine-only SECRETS region and wipes the temporary buffer it used; it starts the ring-oscillator random-number generator and runs its start-up health tests; it compiles the policy manifest into the flat decision tables the Monitor will consult on every request (Chapter 8); it builds the initial capability space for the first session (Chapter 7); it installs its trap vector so that later ecalls land in the right place; and it writes the opening entry of the audit hash-chain so attestation has a genesis to build on.

Stage 3, control drops to the untrusted layers

Only when all of that is done does the Monitor execute an mret, the instruction that returns from machine mode down to supervisor mode, landing in the Warden microkernel. This is the first moment any code below machine mode runs on this boot. The Warden schedules and starts the compartments, the Endpoint that speaks USB, the network and storage drivers, all in user mode. From here on the machine is live: an agent on the host can frame a request, the Endpoint can deliver it, and it will ecall up into the Monitor along the path Chapter 6 describes. The dashed line in Figure 5-1 shows that later return trip; it is not part of boot, but it is where boot was leading.

5.3Why the ordering matters: no unguarded window

It would be easy to read the previous section as a checklist where order is a matter of taste. It is not. The single most important property of the whole sequence is that the walls go up while only the Monitor is running. Between the boot ROM's approval and the mret to the Warden, nothing untrusted executes, not one instruction. So there is never an interval in which the secrets and the network are reachable and some untrusted code is alive to reach them.

Call that missing interval the unguarded window, and picture how a careless design might open one. Suppose the Monitor started the Warden first, "to get the system responsive," and locked the PMP a few milliseconds later. In those milliseconds a subverted Warden could read every key out of the SECRETS region and hand it to the host before the wall it was meant to sit behind ever existed. The attack needs no cleverness; it just needs the window. We close it by construction: locking the PMP is step (a), the very first thing the Monitor does, and nothing that could abuse the openness runs until step (e).

The lock bit earns its own emphasis here. Programming a PMP entry is not enough on its own, because a later machine-mode bug, or, in the threat model's stretch case, a machine-mode fault an attacker induces, might reprogram it. Setting the lock makes the entry immutable until the hardware resets, so even the Monitor cannot loosen it afterward. We are willing to give up our own ability to change the rule in exchange for the certainty that no one else can either. (Chapter 3 discusses the Smepmp variant that also denies the region to machine mode itself; where it is unavailable, the locked-rule fallback still keeps the region unreachable from the Warden and below.)

This "measure, then lock, then descend" shape is not ours; we borrowed it. It is the same discipline a measured boot follows on a phone or a server's TEE, where each stage vouches for the next before surrendering control, and privilege only ever narrows as you go.2 We have simply pointed it at one small target and refused to let it grow.

5.4Measurement: what BLAKE2s buys us

The comparison in stage 1 rests on a cryptographic hash, so it is worth being precise about what such a hash does and does not promise. A hash reads an arbitrary amount of data and emits a short, fixed-size digest. The property we rely on is that it is infeasible to find two different inputs with the same digest, and that changing any bit of the input scrambles the whole output unpredictably. So if the Monitor image the boot ROM sees produces the same 32 bytes as the image we hashed when we built the system, we can be confident to a cryptographic certainty that the images are identical.

We use BLAKE2s specifically, and the choice is not arbitrary. BLAKE2s is fast, has a small and simple implementation, which matters when the code doing the hashing is itself inside the trusted base and counted against a line budget, and it is the same primitive the audit log uses for its hash-chain (Chapter 12) and that the Monitor uses elsewhere, so there is only one hash to review, not three.

at power-on, in the boot ROM:

    H        := BLAKE2s-256( bytes of MON_CODE region )
    if H != H_expected:          # H_expected is baked into the bitstream
        halt forever             # no log, no retry, no fallback image
    else:
        jump into the Monitor    # now trusted to run in machine mode

One subtlety deserves a beginner's attention: what exactly gets hashed. It is the Monitor's code image, the thing that must be exactly ours. It is not the Monitor's live data, which changes every boot and could never match a fixed constant, and it is not the policy manifest, which an operator is meant to change. Getting the boundary of "the measured thing" right is half of doing measured boot correctly; hash too little and you leave something unmeasured that an attacker can swap, hash too much and the machine refuses to boot every time anything legitimately varies.

5.5Measured boot and attestation

Measuring the Monitor protects this machine from booting an impostor. But there is a second, outward-facing use for measurement: letting someone else, who is not standing at the machine, gain justified confidence about what it is running. That is attestation, and Redoubt offers a modest form of it.

Two facts combine to make it work. First, the boot only proceeds if the Monitor measured correctly, so the mere fact that a Redoubt is running mediations at all already implies its Monitor matched H_expected. Second, from its genesis entry onward the Monitor keeps a tamper-evident audit log: every decision it makes is recorded, and each entry is hashed together with the hash of the entry before it, forming a chain (the structure is specified in Chapter 12). Because each link depends on all the links before it, you cannot quietly delete or edit a past entry without breaking every hash that follows.

The head of that chain, the single hash summarising everything logged so far, can be read out over the wire with the ATTEST_READ opcode (0x52440020), the read-only member of the mediation ABI catalogued in Chapter 6. A verifier who knows what the head hash should be, or who simply records it and watches that it only ever advances, can detect truncation or tampering of the log. It is not a full remote-attestation protocol with signed quotes and a challenge nonce; version 1 exposes the raw chain head and leaves the signing envelope to a later revision. What it does give, honestly, is a cheap and checkable witness that the record has not been rewritten.

host                          Redoubt (Monitor)
  |  ecall a7=ATTEST_READ  ---> |
  |                             |  read head of audit hash-chain
  |  <---  status=ALLOW, 32 B  <-|  (h_n = BLAKE2s over the whole chain)
  |                             |
  compare h_n to the last value you saw; it must only ever move forward

5.6Secret provisioning

The Monitor is useless without its secrets, the API keys and credentials it injects on the agent's behalf, but the moment those secrets exist in memory is a delicate one, so provisioning gets its own short, strict routine. At build or personalisation time the keys are written into a machine-only area of the QSPI flash, a region the PMP map keeps out of reach of supervisor and user code. During stage 2 the Monitor copies them into the SECRETS region of RAM, which is likewise machine-only, and then immediately wipes the temporary buffer it used to move them so no stray copy lingers on the stack.

From that point the secrets obey the use-only discipline described in the Monitor and Capabilities chapters: exactly one part of the Monitor ever reads a key, and only to splice it into an outgoing request at the final performing step, wiping its working copy straight after. There is no boot-time path, and no ABI, that copies a key toward the host. Provisioning is the one time raw key bytes travel across memory, which is exactly why it happens while only the Monitor is running and behind walls that are already locked.

Version 1 provisions from flash because it is simple and enough to prove the architecture. A sturdier scheme, deriving per-device keys from a hardware secret so that dumping the flash of one unit does not compromise a fleet, or provisioning over an authenticated channel after boot, is a natural version-2 improvement and is flagged among the open questions.

5.7The honest caveat: bitstream authenticity

Here is the part it would be dishonest to bury. Everything above assumes the bitstream loaded in stage 0 is ours, that the boot ROM doing the measuring, and the H_expected it measures against, are the ones we put there. Version 1 does not verify that assumption. The ECP5 loads whatever bitstream sits in the QSPI flash, and an attacker with physical access who can reflash that chip could install a bitstream whose boot ROM measures nothing, or whose H_expected is the fingerprint of their own Monitor. The root of trust, in other words, is rooted in the flash, and version 1 does not defend the flash.

We state this plainly rather than gesture past it, for two reasons. First, it bounds the claim correctly: Redoubt's guarantees hold against a fully compromised host and even a subverted Warden, the software adversary, but not yet against an attacker who can physically rewrite the board's boot flash. Second, the fix is understood, just deferred. FPGA families and companion secure elements can verify a bitstream's signature before loading it, anchoring trust in a key that cannot be reflashed, and moving to such a part (or adding an external verifier) is the planned version-2 upgrade. It sits alongside the other physical-tampering and fault-injection concerns that version 1 explicitly leaves out of scope.3 Calling it done now would be a lie; calling it a known, scoped gap is the truth.

5.8Failure modes and edge cases

A boot process is judged as much by how it fails as by how it succeeds. The interesting cases:

  • Measurement mismatch. The Monitor image does not match H_expected. The boot ROM halts and the machine never leaves stage 1. This is the designed response to a tampered or corrupted Monitor, and it is also, incidentally, what a bit-rotted flash chip triggers, a corrupted image is indistinguishable from a malicious one, and both deserve a halt.
  • TRNG health-test failure at start-up. If the random-number generator fails its NIST SP 800-90B start-up tests, it is not producing trustworthy entropy.4 Any operation that consumes randomness blocks rather than proceed with weak randomness; boot does not paper over a broken entropy source.
  • Interrupted provisioning. Power lost midway through copying secrets leaves a partially populated SECRETS region, but since nothing untrusted has run yet and the walls are already up, no attacker can observe the half-state. The next clean boot repeats the copy from flash from scratch.
  • An impossible fault during Monitor init. If the Monitor trips over a protection it just set, a bug, not an attack, it stops, exactly as it does at runtime (Chapter 9). A confused Monitor is more dangerous than a halted one, so it never tries to soldier on through an inconsistent state.
  • A wrong-but-well-formed policy manifest. Measurement covers the Monitor's code, not the policy, so a mis-authored manifest will compile and boot happily. Boot cannot catch a policy that is valid but too permissive; that is the policy compiler's and the operator's problem, discussed in Chapter 8. It is worth naming so no one mistakes a green boot for a correct policy.

5.9Invariants the boot establishes

Boot exists to hand the running system a set of guarantees it can then rely on. These are the ones a successful boot must have made true by the time the Warden first runs:

  1. The machine-mode software that is running is bit-for-bit the Monitor we built, or the machine halted.
  2. The PMP entries protecting SECRETS and the egress hardware are programmed and locked before any supervisor- or user-mode instruction executes.
  3. Secrets reside only in the machine-only SECRETS region; the buffer used to load them has been wiped.
  4. The random-number generator has passed its start-up health tests, or entropy-consuming operations are blocked.
  5. The policy tables and the initial capability space were built once, by the Monitor, from the manifest, and are not rebuilt afterward.
  6. The audit hash-chain has a genesis entry, so every later decision extends an unbroken chain.
  7. The trap vector is installed, so the first tool call arrives at the Monitor and not at unowned code.

5.10Alternatives rejected

Several other boot designs were considered and set aside. The reasons are as instructive as the choice.

A signature check instead of a plain measurement. The boot ROM could verify a digital signature over the Monitor rather than compare a hash to a baked-in constant. Signatures allow the Monitor to be updated in the field without re-baking the bitstream, which is genuinely nice. But they drag a public-key verifier, and key-management questions about which keys are trusted and how they are revoked, into the boot ROM, the smallest and most sacred piece of the trusted base. For version 1 a fixed hash is smaller, simpler, and has nothing to misconfigure. Signatures become attractive precisely when we also solve bitstream authenticity, so the two are deferred together.

A multi-stage bootloader. Conventional systems chain a first-stage loader to a second stage to the OS, each measuring the next. That flexibility is exactly what we do not want here. Every extra stage is more trusted code and another link that can be attacked. Redoubt collapses the chain to the shortest thing that works: ROM measures Monitor, Monitor runs. There is no second-stage loader to compromise because there is no second stage.

Lock the PMP lazily, after the system is up. Tempting for boot speed, and fatal for the reasons §5.3 lays out: it opens the unguarded window. Rejected outright. Locking is the Monitor's first act and nothing untrusted precedes it.

Fall back to a recovery image on measurement failure. Many devices boot a backup image if the primary fails to verify. That is sensible for availability and wrong for us: a recovery path is a second thing an attacker can aim to trigger and then subvert, and Redoubt values a safe halt over continued availability. If the Monitor does not measure correctly, the right outcome is a machine that does nothing until a human intervenes.

Store H_expected in the same flash as the Monitor. Convenient, and it would let an attacker who rewrites the Monitor rewrite the expected hash to match. We put H_expected in the bitstream's on-chip block RAM instead, so that within version 1's software threat model it cannot be edited independently of the bitstream. (That it can be edited by reflashing the bitstream is the §5.7 caveat, and the honest limit of this choice.)

5.11Open questions

Loose ends, named so no one mistakes this chapter for finished:

  • Bitstream authenticity, the §5.7 gap. Which secure-element or signed-configuration part anchors trust below the flash in version 2, and what it costs in board complexity.
  • Whether to move from a fixed-hash measurement to a signed, field-updatable Monitor once a hardware key store exists, and how updates interact with the audit chain's continuity.
  • Per-device secret provisioning: deriving keys from a hardware unique secret so that compromising one unit's flash does not compromise a fleet, versus the simpler shared-flash scheme of version 1.
  • Whether attestation should graduate from a raw chain-head read to a signed quote over a verifier's nonce, and where the signing key would live.
  • Exact boot-time budget for TRNG conditioning before first use, balancing start-up latency against entropy confidence.4
