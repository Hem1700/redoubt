Threat Model & Trust Tiers

Abstract. A security claim means nothing until you name the enemy, the prize, and the exact sentence you are willing to defend. This chapter does all three. It states what the attacker is assumed to be able to do — five capabilities, up to and including taking over the operating system that runs beneath the guard — and lists what is actually being protected. It then works a concrete attack all the way through: an agent, fully hijacked, trying to steal an API key, and shows every branch of that attack running into a specific, named mechanism that stops it. It gives the trust tiers as a table, states the formal security property in one careful sentence, and ends with an honest list of the attacks Redoubt does not stop, so no one mistakes the scope. It assumes only Chapter 1.

Note to first-time readers.

This chapter uses a few security-modeling terms. Here they are plainly, so the argument reads without a glossary at your elbow.

Threat model
An explicit statement of who the attacker is, what they can do, and what they are after. Its value is its honesty: a defense is only as good as the threat model it is measured against, and a threat model that quietly leaves out the hard cases is a comfort, not a guarantee.
Adversary capability
One specific power we grant the attacker for the sake of argument. We list ours as A1 through A5. Granting a capability does not mean it is easy; it means we refuse to assume it away.
Trusted computing base (TCB)
The set of parts that must be correct for the promise to hold. Everything else may fail arbitrarily. The whole design is an effort to make this set as small as possible.
Attack tree
A picture of an attacker's goal at the top and the alternative ways to reach it branching below, so you can check that every branch is blocked, not just the obvious one.
Complete mediation
The property that there is no path to the protected thing that skips the guard — no side door, no back door, no forgotten window.

2.1The stance: assume the inside is already lost

Most systems draw their trust boundary around the outside and defend it: keep the attacker off the machine, and everything on the machine is friends. Redoubt cannot work that way, because the attacker is not trying to get in — the attacker is already the thing we are running. The agent's reasoning is influenced by whatever it reads, and it reads attacker-controlled material as a matter of course. So we move the boundary inward and make a deliberately pessimistic assumption, then build only what survives it.

The agent is compromised. The tools are hostile. The operating system beneath them may be subverted too. Given all of that at once, the security property must still hold. If a design only works when some of those are friendly, it is not our design.

The rest of this chapter makes that stance precise. What, exactly, can the attacker do? What is the prize? And what is the one sentence that stays true regardless?

2.2Adversary capabilities

We grant the attacker five capabilities, labelled A1 through A5 so later chapters can point at them. They are ordered from the ordinary to the extreme; the last one is deliberately more than any real attacker is likely to have, because a guarantee that holds at A5 holds everywhere below it.

#CapabilityWhat it means in practice
A1Full agent hijackThe attacker controls the agent's goals and can make it emit any tool call — any tool, any arguments, any order — via prompt injection, direct or hidden in content the agent reads.1
A2Malicious toolsThe host-side tools and MCP servers are untrusted: a tool's description can lie, and its code can do anything. "Tool poisoning."2
A3Host compromiseArbitrary code runs on the host with full control, including the USB driver that talks to Redoubt. The entire computer the agent lives on is the attacker's.
A4Compartment compromiseThe Endpoint and the egress drivers — Redoubt's own user-mode compartments (T2) — may be fully controlled.
A5Warden compromise (stretch)The supervisor-mode microkernel (T1) itself may be subverted. The property must still hold. This is the one that forces the guard below the operating system.

A5 is the demanding one and the reason the whole architecture looks the way it does. If we only had to survive a hijacked agent (A1), a software guard on the host might do. Because we insist on surviving a subverted kernel, the guard has to sit somewhere the kernel cannot reach — a more privileged processor mode, behind a hardware wall — which is the subject of Chapter 3. Everything else is downstream of taking A5 seriously.

One capability we do not grant is worth naming here so the model stays honest: we assume the attacker cannot physically open the device and probe its wires, and cannot rewrite the FPGA's configuration. Those are real attacks; they are out of scope for the first version, and §2.7 says so plainly rather than burying it.

2.3What we are protecting

Name the prize before defending it. Redoubt protects four assets, in rough order of how badly you would miss them.

  • Secrets. API keys, tokens, and credentials the agent needs to do its work but must never be able to steal or leak. These are the thing most worth stealing, and the design goes to the most trouble for them: the Monitor will use a key on the agent's behalf and never hand it over (Chapter 12).
  • Egress integrity. The guarantee that nothing leaves — no network request, no file written — except an action that was actually permitted. Exfiltration is a leak out this door; so is a destructive write.
  • Authority. The agent's granted permissions themselves. An attacker who could widen a capability, or forge one, would not need to leak anything directly — they could simply grant themselves the power to. The capability system (Chapter 7) makes authority unforgeable and only ever narrowable.
  • The audit trail. The tamper-evident record of what was decided. If an attacker could quietly erase evidence of an attempt, containment would be silent and unprovable. The log is hash-chained so truncation and tampering are detectable (Chapter 9, §9.3; Chapter 13).

Notice what is not on the list. We do not promise the agent will finish its task, or that it cannot be made to waste its own time. Availability of the agent to its owner is explicitly not an asset we defend (§2.7). A Redoubt that refuses everything is annoying but safe, and safe is the priority.

2.4An attack, followed down every branch

Abstractions are easy to wave at, so let us fix a real goal and try genuinely hard to reach it. The agent has been prompt-injected (A1). Its assigned task involved calling a legitimate service, so it holds a web capability — permission to make an HTTPS request to api.example.com, with an API key that the Monitor will inject on its behalf. The attacker's goal is to get that key out.

There is not one way to try this; there are several, and a serious threat model has to show that all of them fail, not just the first that comes to mind. The tree below lays the goal at the top and every branch beneath it, with the exact mechanism that severs each branch. This is the diagram to study if you read only one thing in the chapter.

The branches, in words, because the picture rewards a little narration:

A — send it somewhere the attacker controls. The obvious move: POST the key to evil.tld. The capability names one allowed host, and the Monitor checks the request's host field against that allowlist before anything leaves. evil.tld is not on it. Denied, reason DENY_ARG. Crucially, the check runs on the structured host field the action will actually use, not on a re-parsed string, so the old tricks that slip a different host past a naive filter — a sneaky %2e, a userinfo @, a trailing dot — have nothing to work on.3

B — hide it in a request to the allowed host. Cleverer: the attacker aims at the real api.example.com, which passes the host check, but tucks the key into the request body. This is where a second, independent net catches it. Values carry information-flow labels; the API key is labelled SECRET, and the flow check refuses to let a SECRET value enter a sink the policy has not cleared for it. Denied, reason DENY_FLOW. Two different checks catch two different attacks, which is the point of having both.

C — just ask for the key. Simplest of all: call the Monitor and request the secret directly. There is no such call. Secrets are use-only: the Monitor will splice a key into an outgoing request where the policy says to, but no interface anywhere returns key bytes to the caller. The branch has no first step.4

D — manufacture the authority. If you cannot use the capability to leak, forge a better one. But a capability is an unforgeable record the host never holds directly — the host holds only an opaque handle, an index, and an invented index resolves to an empty slot (DENY_NO_CAP). Nor can authority be widened: the only way to make a new capability from an old one narrows it, and there is no operation anywhere that adds a right. Granting yourself a fresh Secret capability is not a hard operation; it is an absent one.5

E — go around the guard. The deepest attack: stop asking, and drive the network chip yourself. This is where A5 earns its keep. Suppose Warden is fully subverted and tries to write to the network controller's registers. Those registers live at addresses that the hardware permission settings mark reachable only from machine mode, and Warden runs in supervisor mode. The write does not get refused by a check; it faults, because the address is not accessible from where the instruction runs. There is no software path to bypass because no software is consulted. This branch, and only this branch, is what forces the guard onto separate, more-privileged hardware — everything in Chapter 3.

2.5Trust tiers

The attack tree already leaned on the idea that different parts of the system are trusted for different things. Here is that sorting made explicit. Redoubt places every piece of software into one of three tiers by privilege, plus the host, which is off the device entirely. What matters in the table is the "trusted for" column: it says what has to be correct, and by omission, what may fail without breaking the promise.

TierComponentCPU modeIn the TCB?Trusted for
T0Monitor + boot ROM + PMP configurationMachine (M)yesThe security property, the secrets, the egress. This is the whole trusted base.
T1Warden microkernelSupervisor (S)noLiveness and scheduling only. A subverted Warden (A5) cannot break the property.
T2Endpoint, egress driversUser (U)noNothing security-relevant. They frame and format; they never decide.
—Host: LLM, agent, toolsoff-devicenoNothing. Conceded to the attacker in full (A1–A3).

Read down the "in the TCB" column and the design goal is right there: exactly one "yes." The guarantee rests on T0 alone. Everything in a "no" row is permitted to be arbitrarily hostile. That is not a hope about how well those parts are written; it is a claim the hardware wall of Chapter 3 is built to make true. The reason the tiers map onto CPU privilege modes — M above S above U — is that the mode boundary is exactly the wall we can enforce in silicon: a more privileged tier can fence memory off from a less privileged one, and never the reverse.6

2.6The security property, stated once and carefully

Everything above can be compressed into a single sentence that either holds or does not. This is the sentence the entire book is trying to earn.

Security property.

For every execution, and for every external effect e that actually occurs on the egress hardware, there exists a capability c in the active session's capability space such that c is bound to the tool of e, the policy predicate of c holds on the arguments of e, and the information-flow rule of c permits the labels of e. This holds for arbitrary behaviour of the host, the compartments, and even a compromised Warden.

Unpack it slowly, because every clause is doing work. "For every external effect that actually occurs" means the property is about what happens, not about what was asked — an attacker may request anything (A1); the claim is only about what gets out. "There exists a capability" means nothing happens by ambient authority; every effect is backed by a specific, held grant. The three conditions on that capability — right tool, arguments satisfy the predicate, labels satisfy the flow rule — are exactly the three checks the attack tree showed severing branches A, B, and E's software cousins. And the last clause is the hard promise: this is true even when Warden, the operating system, is the attacker's.7

This is the classical reference-monitor guarantee — complete mediation, tamper-proof, small enough to verify — instantiated for a new mediated operation (a typed tool call) and a new adversary (a hijackable agent).1 It is enforced structurally: the effect is impossible without the Monitor's involvement, because the egress hardware sits in a machine-only memory region that lower tiers cannot address. It does not rest on trusting any software above T0. That structural enforcement, rather than a pile of careful checks, is what lets the property survive A5.

Notice one thing the property does not say. It does not adjudicate the agent's intent. It never asks "did the agent mean well?" — an unanswerable and attacker-influenced question. It asks only whether the concrete, structured effect is covered by a held capability. That restraint is deliberate; judging intent is the AI-reviewing-AI trap Chapter 1 rejected.

2.7Out of scope — stated, not hidden

An honest threat model is as clear about what it does not stop as about what it does. Redoubt v1 makes no claim against the following, and it is better to say so loudly than to let a reader assume coverage that is not there.

  • Microarchitectural and timing side channels. A determined attacker might infer a secret from how long an operation takes, or from cache effects, rather than by reading it. Even formally verified systems have had confidentiality claims broken this way.8 Redoubt does not defend against it in v1; some mitigation (constant-time secret injection) is an open question in Chapter 9.
  • Physical and fault-injection attacks. Opening the case, probing wires, or glitching the power to skip a check. We assume the device is physically in the owner's hands.9
  • FPGA bitstream authenticity. Redoubt trusts that the logic loaded onto the chip is the logic we designed. Verifying the bitstream itself against tampering is a v2 root-of-trust problem (Chapter 5 notes where this bites).
  • ESP32 firmware integrity. The network chip's own firmware sits in the egress path and is a closed module we do not audit. A wired-Ethernet successor that lets the Monitor own the network controller directly is a v2 upgrade (Chapter 12 is candid about this caveat).
  • Host-side poisoning of the agent's own memory. If the attacker corrupts what the agent remembers across sessions, that is within the conceded host (A3); Redoubt bounds what the agent can do, not what it believes.
  • Multi-agent collusion. Several agents combining their separate authorities to achieve together what none could alone. Interesting and out of scope for v1.
  • Availability and self-denial-of-service. Nothing stops a hijacked agent from wasting its own allotted work or getting itself into a state where it accomplishes nothing. A stuck or useless agent is safe, and safety is what we defend; usefulness is not a security asset.

None of these are dismissals. Each is a real attack that a complete system would eventually address; each is named so that the guarantee of §2.6 is read against its true boundary and not a wished-for one. Chapter 13 returns to this list when it assesses coverage against the OWASP agentic top ten.10

2.8Alternatives considered and rejected

The threat model could have been drawn differently, and a few of the roads not taken are instructive.

Trust the operating system (drop A5). If we assumed Warden stays honest, the guard could be an ordinary privileged process and the whole hardware story would vanish. We refused, because kernels are exactly the layer that gets compromised, and a guarantee that evaporates on a kernel bug is the kind of guarantee this project exists to avoid. Keeping A5 is what makes the promise worth having.

Include physical attacks in v1. Tamper-resistant packaging and fault-injection countermeasures are real engineering, and a truly high-assurance device needs them. They are also a large, specialized effort orthogonal to the novel part — the agent reference monitor — so v1 scopes them out openly rather than doing them badly.

Model the attacker as external. The conventional threat model keeps the adversary off the machine. Adopting it would have been comfortable and wrong: our adversary is the workload. The whole value of the design comes from taking that seriously.

Promise availability. We could have added "the agent completes its task" to the protected assets. We declined, because defending availability against a workload you have already conceded is nearly impossible, and conflating it with the containment guarantee would weaken the claim that actually holds. Better a narrow promise kept than a broad one broken.

2.9Open questions

Loose ends in the model itself, so the boundary stays honest as the design firms up:

  • Exactly which OWASP agentic items are in scope for v1. Goal hijack, tool misuse, and exfiltration are clearly core; memory poisoning and multi-agent collusion are deferred, but the line deserves a firmer justification than "later."
  • How to characterize a realistic attacker's side-channel budget, so that the v1 exclusion is a measured decision rather than an omission — and which mitigations are cheap enough to pull forward.
  • Whether A4 and A5 should be split further. "Compartment compromise" lumps the Endpoint together with the egress drivers, though they sit at different points in a request's path and may warrant separate treatment.
  • What the trust story is for the ESP32 link precisely — how much of it the Monitor can own today versus what must wait for the wired-Ethernet successor.
