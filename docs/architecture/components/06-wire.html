Wire Protocol & the Tool-Call ABI

Abstract. Between the untrusted host, where the AI agent lives, and the Monitor, which decides what the agent may do, there is a single serial cable and a precisely defined language spoken across it. This chapter specifies that language from the wire up: the USB serial transport; the framing that turns a stream of bytes into discrete, integrity-checked messages; and, the part that carries the security weight, the way a tool call's arguments are encoded as typed values rather than as text. It explains why that typing choice quietly closes a whole family of real-world bugs, lays out the request and response formats byte by byte, tabulates the small set of operations the Monitor exposes and the codes it answers with, and pins down the deliberately humble role of the Endpoint compartment that shuttles these frames: it moves bytes and checks nothing that matters. The chapter is written to be read whether or not you have met a serial protocol before.

Note to first-time readers.

A few terms recur below. Here is each in plain language; no networking or low-level background is assumed.

Transport
The physical way bytes get from one place to another, here, a USB cable that presents itself as an old-fashioned serial port. The transport carries bytes and understands nothing about their meaning.
Framing
A serial line is just an unbroken stream of bytes with no natural "start" or "stop". Framing is the trick of marking where one message ends and the next begins, so the reader can chop the stream into whole messages.
Checksum (CRC32)
A short number computed from a message's bytes and sent alongside it. Recompute it on arrival; if it differs, the message was corrupted in transit. It catches accidental damage, not a determined forger.
TLV
Tag-Length-Value: a simple, self-describing way to encode a piece of data as a small tag saying what it is, a length saying how big it is, then the bytes themselves. Easy to parse without guessing.
ABI
Application Binary Interface: the exact, machine-level contract for calling a piece of code, which register holds the operation number, which holds the argument pointer, what comes back. The Monitor's ABI is the list of things you can ask it to do and how you ask.

6.1What this protocol has to accomplish

Redoubt splits the world in two. On one side is the host: the language model, the agent, the tool code, the USB driver, everything we assume an attacker owns. On the other is the Monitor, which holds the keys and the network. The only thing connecting them is a serial cable. So every tool call an agent wants to make has to be reduced to bytes, pushed across that cable, and reconstructed on the far side into something the Monitor can judge. This chapter is about those bytes.

Getting the encoding right matters more than it might seem, because the wire is a boundary between a place we distrust completely and a place we trust absolutely. Whatever crosses it is attacker-controlled until proven otherwise. The design's answer is to make the messages as simple, as bounded, and as unambiguous as we can, simple because complex parsers are where bugs breed, bounded because the Monitor must never be made to allocate or loop without limit, and unambiguous because, as §6.4 shows, ambiguity about how to read a value is itself an exploitable flaw.

Three layers stack up, and it helps to keep them apart. The transport is USB serial; it moves raw bytes. The framing layer turns that byte stream into discrete, integrity-checked frames. And inside each frame rides the payload, a request or a response, whose arguments are themselves typed values. We take them from the bottom up.

6.2Transport: USB CDC-ACM serial

The host talks to Redoubt over USB, using the CDC-ACM class, the standard that makes a USB device appear to the operating system as a plain serial port. On the ULX3S board this rides the on-board USB-serial bridge. The choice is pedestrian on purpose. A serial port is about the simplest interface a computer offers: an ordered stream of bytes in each direction, nothing more. It needs no complicated driver stack inside Redoubt, and, importantly, the entire USB stack lives on the untrusted host and in the untrusted Endpoint compartment, never in the Monitor.

What the transport gives us is modest and worth stating exactly: bytes arrive in order, and mostly arrive intact. What it does not give us is any notion of where a message starts or stops, any guarantee against corruption, and above all any trust. A serial port will happily deliver whatever an attacker chooses to send. Everything protective is built in the layers above.

6.3Framing: COBS and a CRC32

To carve the byte stream into messages we use a delimiter: a single reserved byte value, zero, that marks the end of every frame. Read bytes until you hit a zero, and you have exactly one frame. This is trivial to implement and self-synchronising: if a reader ever loses its place, the next zero re-aligns it on a clean boundary.

There is one snag with using zero as a delimiter, what if the message itself contains a zero byte? We solve it with Consistent Overhead Byte Stuffing, COBS, a small reversible transform that removes every zero from the payload while adding a tightly bounded, predictable amount of overhead.1 After COBS encoding, the only zero in a frame is the delimiter at its end, so the framing is never confused by the data it carries. COBS is a good fit here precisely because its worst-case overhead is small and fixed, which keeps buffer sizes bounded, a recurring requirement on the trusted side.

Inside each frame, before COBS is applied, the bytes are laid out like this:

Frame (before COBS encoding):

  len : u16     length of payload, in bytes
  ver : u8      protocol version
  type: u8      frame type (request / response / ...)
  payload[len]  the request or response (see 6.5)
  crc32: u32    IEEE CRC-32 over ver..payload

  then the whole thing is COBS-encoded and a 0x00 delimiter appended

The CRC32 is a checksum over everything from ver through the end of the payload. On receipt the reader recomputes it and compares. If either the COBS decode fails or the CRC does not match, the frame is corrupt, and the rule is blunt: drop it. The frame is not partially processed, not repaired, not acted upon. A dropped-frame counter ticks up, and a request that never fully arrives simply never happens, which, from a security standpoint, is a perfectly safe outcome.

What error handling does and does not promise

Be clear about the CRC's job. It catches accidental corruption on the wire, a flipped bit, a dropped byte. It does not, and cannot, stop a deliberate attacker, who can recompute a valid CRC over whatever malicious payload they like. That is fine, because the CRC is not a security control. Integrity against a hostile host is not the framing layer's job at all; it is the Monitor's, enforced by re-deriving every security-relevant fact from the typed payload and checking it against policy. The framing layer's only duty is to hand the Monitor whole, uncorrupted frames or none, so the Monitor is never made to parse a half-message. A malformed or truncated frame that does reach the Monitor is answered with DENY_MALFORMED (§6.7); a garbled one that fails CRC never gets that far.

6.4Typed arguments, and why not text

Now the heart of the chapter. A tool call has arguments, the URL to fetch, the path to read, the method to use. The tempting way to carry them is as text: a string like https://api.example.com/v1/data, which the Monitor would parse to pull out the host and scheme it needs to check. We deliberately do not do this. Arguments cross the wire as typed values, encoded in TLV form, with the security-relevant fields already broken out.

The reason is a bug class worth understanding, because once you see it you cannot unsee it. It arises whenever two pieces of code parse the same string and quietly disagree about what it means. The checker reads a URL one way and decides it is safe; the code that actually acts on the URL reads it a slightly different way and reaches somewhere else entirely. The classic instance is a host allowlist fooled by an encoded character, a %2e standing in for a dot, an @ or a backslash placed so the checker sees one host and the fetcher connects to another. This is the engine behind a large fraction of real server-side request forgery and path-traversal vulnerabilities, and it is not a bug in any one parser; it is a bug in trusting text at a boundary where two parsers meet.2

Redoubt refuses to play. Instead of shipping a URL as a string, the host sends it already decomposed into its parts, scheme, host, port, path, each as its own field. The Monitor then re-derives the security-relevant fields from that structured form and checks policy against exactly the value the performing step will use. There is no re-parsing of a string on the trusted side, so there is no second parser to disagree with a first. The ambiguity that powers the whole bug class simply has nowhere to live. (The host does the initial parse, but the host is untrusted, so its parse is treated as a claim the Monitor re-derives, not as truth.)

The encoding is TLV: a one-byte tag naming the type, a two-byte length, then the value.

TypedArg = tag:u8 | len:u16 | value[len]

  tag 0x01  URL     value = { scheme:enum8, host, port:u16, path }
  tag 0x02  PATH    a filesystem path, as structured components
  tag 0x03  ENUM    a small choice from a fixed set (e.g. method GET)
  tag 0x04  INT     a little-endian integer
  tag 0x05  BYTES   an opaque byte string (e.g. a request body)
  tag 0x06  LABELSET an information-flow label set (Chapter 10)
TagTypeWhat it carriesWhy it is its own type
0x01URLscheme, host, port, path, separatelylets the Monitor read host directly; the anti-%2e case
0x02PATHa filesystem path in structured formpath-prefix checks without traversal ambiguity (../)

0x05BYTESan opaque blob, e.g. a bodynever interpreted by the Monitor, only labelled and length-checked

Two guards apply to every TypedArg on arrival, and they are cheap. The tag must be one the Monitor knows; an unknown tag is a malformed request. And the length must fit within the request's declared bounds, an argument that claims to run past the end of the buffer is malformed too. Both failures land on DENY_MALFORMED before any policy is consulted.

6.5Request and response layout

With framing and argument encoding in hand, the payload itself is straightforward. A request names the session it belongs to, a request id the caller uses to match up the reply, the capability handle it is exercising, the tool it wants, then its typed arguments and their labels:

Request  = magic:u32 ('RDBT')
         | session_id:u16
         | req_id:u16
         | cap_handle:u16
         | tool_id:u16
         | n_args:u8   | args:TypedArg[n_args]
         | n_labels:u8 | in_labels:u8[n_labels]

Response = req_id:u16
         | status:u8            (reason code, 6.7)
         | n_labels:u8 | out_labels:u8[n_labels]
         | result:BYTES?        (present only on ALLOW)

A few fields carry more weight than their size suggests. The magic word 'RDBT' is a cheap sanity check that lets the Monitor reject obvious garbage before doing anything else. The cap_handle is an opaque index the host holds, not a capability itself, just a number naming a slot in the session's capability space; forging it or running it out of range resolves to an empty slot and a denial (Chapter 7). The req_id is echoed back verbatim so the host can pair a response with the request that prompted it, since several may be in flight from the host's point of view even though the Monitor handles them strictly one at a time. On the way back, status is the verdict and result appears only when that verdict is ALLOW, a denial carries no body, and in particular a secret the Monitor injected never travels back in result.

The whole request is bounded: at most eight arguments, a few hundred bytes total. Those limits are not arbitrary generosity withheld; they are what lets the Monitor use fixed-size buffers with no allocation and no unbounded loop, which is a property the trusted code depends on (Chapter 9).

6.6The mediation ABI

Framing and payloads describe how bytes are shaped. The ABI describes what the host can actually ask for. When a request reaches the Endpoint compartment, it makes a RISC-V ecall that traps up into the Monitor in machine mode, with the operation number in register a7, a pointer to the request in the shared buffer in a0, and its length in a1. The Monitor dispatches on a7. The set of legal operations is small on purpose, a short list is a small attack surface, and anything outside it is refused immediately, before a single table is touched.

Opcode (a7)NameWhat it does
0x52440001MEDIATEThe main event: judge one tool call against its capability and policy, and, if allowed, perform it (Chapter 9's pipeline).
0x52440010SESSION_OPENBegin a new agent session, allocating a fresh, empty capability space seeded from the manifest.
0x52440011REVOKEBump the session's epoch, invalidating every capability it ever issued in one O(1) step.
0x52440012SESSION_CLOSETear a session down and release its slot.
0x52440020ATTEST_READReturn the current head of the audit hash-chain, so an external party can check the log has not been rewritten (Chapters 5 and 12).

Notice what is not in this table. There is no opcode that reads a secret, and none that drives the network or storage hardware directly. Those actions happen only inside the MEDIATE pipeline, after every check has passed, and they are internal to the Monitor, there is no side door that reaches them. The entire surface an attacker can probe is these five numbers, and four of the five do housekeeping; the security decision lives wholly in MEDIATE.3

the handoff, in registers:

  a7 = MEDIATE (0x52440001)
  a0 = pointer to the Request in the shared buffer
  a1 = length of the Request
  -- ecall traps into the Monitor (machine mode) --
  a0 = status   (a reason code from 6.7)
  a1 = length of the Response written back

6.7Reason codes

Every mediation ends in exactly one code. One means yes; the rest explain a no or an error, and the Monitor is careful to say which no, both so the host can react sensibly and so the small display and the audit log can record a precise reason.

CodeNameMeaning
0x00ALLOWEvery check passed; the action was performed.
0x10DENY_NO_CAPNo usable capability at that handle, empty, out of range, or the wrong type.
0x11DENY_TOOLThe capability is not bound to the tool that was requested.
0x12DENY_ARGAn argument failed the capability's typed predicate (e.g. host not on the allowlist).
0x13DENY_FLOWThe information-flow check refused it, e.g. a secret bound for a public sink (Chapter 10).
0x14DENY_MALFORMEDThe request was ill-formed: bad bounds, unknown tag, too many args, bad magic.
0x15DENY_REVOKEDThe capability's epoch is stale; its session was revoked.
0x16DENY_QUOTAA rate or resource limit for the session was exceeded.
0x20ERR_EGRESSThe action was allowed but the egress hardware failed to carry it out.
0x21ERR_TIMEOUTThe egress hardware did not answer within the bounded wait.
0x2FERR_INTERNALThe Monitor detected an inconsistency in itself, a bug, not a policy outcome.

The codes fall into three natural bands, and the leading digit signals which. The 0x0 band is success. The 0x1 band is a policy denial, the request was well enough formed to be judged, and the answer was no; these are normal, expected, and logged. The 0x2 band is an error rather than a verdict: the machinery, not the policy, is at fault. The distinction matters to a caller, because a DENY means "you may not," which no amount of retrying will change, while an ERR_TIMEOUT means "the wire was slow," which retrying might. Retrying is the untrusted caller's business; the Monitor never retries on its own (Chapter 9).

6.8The Endpoint does framing only

It is worth being emphatic about the Endpoint compartment, because it is easy to over-trust the code that sits closest to the wire. The Endpoint runs in user mode, in the untrusted tier, and its whole job is clerical: pull bytes off the serial port, run COBS and the CRC to recover whole frames, place a request into the shared buffer, make the ecall, and hand the response back out. It decides nothing. It reads no policy, resolves no capability, touches no secret. If the Endpoint were entirely replaced by hostile code, the security property would not budge, because the Endpoint has no authority to misuse, it only moves bytes the Monitor will independently re-check.

This is the same discipline the whole architecture runs on: push everything that can be pushed out of the trusted base, and let the trusted base re-derive anything it depends on. The Endpoint is a courier with a sealed envelope. It can lose the envelope, delay it, even forge a new one, but it cannot make the Monitor honour a request that policy forbids, because the Monitor checks the contents itself and trusts the courier for nothing.

6.9Edge cases and failure modes

  • Corrupt frame. COBS decode fails or the CRC does not match. The frame is dropped and a counter incremented; no partial processing. A request that was in that frame simply never happened.
  • Truncated or oversized request. A frame decodes cleanly but the payload lies about its size, runs past the buffer, or exceeds the argument or byte limits. The Monitor answers DENY_MALFORMED; it never reads beyond the declared bounds.
  • Unknown tag or unknown opcode. A TypedArg tag the Monitor does not recognise, or an a7 outside the five legal opcodes, is refused at once, DENY_MALFORMED, without consulting any table.
  • Duplicate or replayed req_id. The wire itself does not prevent a hostile host from resending a frame. Each MEDIATE is judged fresh against current policy and the session's current epoch, so a replayed request is simply re-decided; a revoked session's replays all fail DENY_REVOKED. The req_id is a matching convenience for the host, not a security token.
  • Response never collected. If the host never reads a response it asked for, nothing on the Monitor side is stuck: it handled the request to completion, wrote the answer, and moved on. Liveness of the host's own bookkeeping is the host's problem.

6.10Invariants the wire layer maintains

  1. The Monitor acts only on whole, CRC-valid frames; a corrupt frame produces no effect at all.
  2. No security-relevant value is trusted as host-parsed text; the Monitor re-derives every field it checks from the structured TypedArg form.
  3. Every request is bounded, at most eight arguments and a fixed byte ceiling, so parsing needs no allocation and no unbounded loop.
  4. The only ways into the Monitor are the five ABI opcodes; there is no opcode that reads a secret or drives egress directly.
  5. The Endpoint holds no authority: replacing it with hostile code cannot cause an effect that policy forbids.
  6. An injected secret never appears in a response payload.

6.11Alternatives rejected

Carry arguments as text and parse them in the Monitor. This is the obvious design and the wrong one, for the whole of §6.4: re-parsing a string on the trusted side re-creates the checker-versus-doer disagreement that powers SSRF and traversal bugs. Typed arguments cost a little encoding effort on the host and buy the elimination of an entire vulnerability class. Easy trade.

Use JSON (or another rich text format) for the payload. Human-readable and familiar, but a general text parser inside the trusted base is a large, subtle, bug-prone thing, exactly what the line budget exists to keep out, and it re-opens the parser-mismatch problem at the format level. A flat, fixed, self-describing binary layout is parsed with a few bounds checks and nothing more.

Let the CRC or a MAC stand in for authenticating the host. A CRC catches accidents, not adversaries, and even a cryptographic MAC over the frame would only prove the host said something, not that what it said is permitted. Authenticating the sender is beside the point when the sender is assumed hostile; the Monitor's answer is to check the request against policy regardless of who sent it. So we keep the CRC for what it is good at, corruption, and rest security on mediation, not on the wire.

A richer ABI with many fine-grained opcodes. More opcodes would let the host do more directly, and each is more surface to probe and more trusted code to get right. We keep exactly five and route every decision through MEDIATE, so there is one place to audit and no side doors.

A more capable transport (raw USB bulk, or the network itself). Faster, and heavier: a real USB stack or network stack in the path is thousands of lines we would either have to trust or carefully distrust. A plain serial line is almost nothing, keeps the whole USB stack outside the trusted base, and the mediation is not throughput-bound anyway. Speed is a version-2 concern if it is a concern at all.

6.12Open questions

  • The exact canonicalization rules the Monitor applies when re-deriving URL and PATH fields, how much normalisation is safe, and where to draw the line so nothing ambiguous survives.2
  • Whether the protocol version field should ever negotiate, or whether a single fixed version is healthier for a security boundary that prizes having no optional behaviour.
  • The precise ceilings, maximum body size, maximum in-flight requests the host may usefully pipeline, once the FPGA's real buffer budget is known.
  • Whether ATTEST_READ should eventually return a signed quote rather than a raw chain head, and how that interacts with the boot-time attestation story of Chapter 5.
  • How DENY_QUOTA's limits are defined and surfaced, per session, per tool, per unit time, which touches the availability questions version 1 leaves out of scope.
