Privilege & Isolation (RISC-V PMP)

Abstract. Everything Redoubt promises rests on one claim: that a hijacked agent, a hostile driver, and even a compromised operating system cannot reach the Monitor's memory, its secrets, or the wires to the outside world. This chapter shows how the claim is made true, and made true by the silicon rather than by good behaviour. It explains the three privilege levels of a RISC-V processor from first principles, then the one feature that does the real work — Physical Memory Protection — down to the layout of a single configuration byte. It gives the exact table of memory regions and the permissions each privilege level receives, explains why those permissions are locked shut at boot before any untrusted code has run, traces the lineage of the idea through Keystone and Sanctorum, and says plainly why the more familiar virtual-memory hardware was not chosen for the wall that matters most. No hardware background is assumed.

Note to first-time readers.

This chapter leans on a few terms from processor design. Here is each one in plain language before we use it in earnest.

Privilege level (mode)
A setting inside the processor that decides how much a running program is allowed to do. RISC-V has three, and the processor is always in exactly one of them. Higher levels can do everything lower ones can, and more; lower levels cannot reach up.
Register / CSR
A register is a tiny, extremely fast storage slot inside the processor. A control and status register (CSR) is a special one that configures how the processor behaves. Some CSRs can only be written from the highest privilege level, which is the whole point of this chapter.
Physical address
The literal, numbered location of a byte in memory or of a hardware device, before any translation or renaming. Think of it as the street address rather than a nickname.
PMP
Physical Memory Protection: a set of machine-only registers that mark ranges of physical addresses as readable, writable, executable — or forbidden — for the less-privileged levels. It is the load-bearing wall of the whole design.
Fault (trap)
When a program attempts something the processor forbids, the instruction does not quietly succeed or fail; the processor stops it and jumps to a designated handler. A blocked memory access raises an access fault. Nothing sensitive is read in the attempt.

3.1Three rings of authority

Picture a building with three floors, and a rule enforced by the structure itself rather than by a sign on the wall: someone on the ground floor can never climb to the floors above, no matter what they try. RISC-V processors work like this. At any instant the processor is running at one of three privilege levels, and each is strictly more powerful than the one below.1

  • Machine mode (M) is the top floor. Code here can touch every register, every device, and every byte of memory. It is the first thing that runs after reset, and it is the only level that can configure the protection hardware. Comparable to root, except that no software above it can override it, because there is no software above it.
  • Supervisor mode (S) is the middle floor, where a conventional operating-system kernel lives. It can manage the programs beneath it and set up virtual memory for them, but it operates only within the bounds machine mode has granted.
  • User mode (U) is the ground floor. Ordinary programs run here with the least authority. When a user program needs something it cannot do itself, it must ask a higher level.

Redoubt maps its trust tiers straight onto these levels, and this is the single most important sentence in the chapter. The Monitor — the only fully trusted component, the subject of Chapter 9 — runs in machine mode. The Warden microkernel, which schedules work and passes messages but is trusted for nothing security-relevant, runs in supervisor mode. The compartments that speak USB and drive the network and storage hardware run in user mode, and the AI agent itself does not run on Redoubt at all; it lives on a separate host computer we assume is entirely in enemy hands. The threat model behind this arrangement is the business of Chapter 2; here we take it as given and build the wall it demands.

The reason the mapping matters is subtraction. Because the Monitor sits a full privilege level above the operating system, the ugliest thing an attacker can plausibly achieve on this device — taking over the whole S-mode kernel — still leaves them on the middle floor. They can wreck scheduling, corrupt messages, deny service. They cannot reach the top floor, and the top floor is where the keys are.

3.2Why a wall, and not a promise

It would be far simpler to write, somewhere in the operating system, a function that checks each request and refuses the dangerous ones. Most systems do exactly that. We cannot, and the reason is worth stating bluntly: we have promised that the guarantee survives a takeover of that very operating system. A check written in software that an attacker controls is a check the attacker can delete. Any defence that lives at the same privilege level as its adversary is not a defence; it is a suggestion.

So the isolation has to come from somewhere the attacker's code cannot reach — from a level above it, enforced by the hardware on every single access, with no instruction sequence that can turn it off. That is a strong requirement, and RISC-V happens to answer it exactly. The mechanism is Physical Memory Protection, and the rest of this chapter is mostly about it.

A useful way to hold the distinction: the operating system's memory management (the MMU, which Chapter 4 covers) is configured by the operating system, so it can never protect anything from the operating system — it cannot wall a room off from the person holding its only key. PMP is configured only from machine mode, one level up, so it can. That difference is the reason the whole project is possible.

3.3PMP, the load-bearing wall

Physical Memory Protection is a bank of entries inside the processor. Each entry describes one range of physical addresses and says who may read, write, or execute within it. On our 32-bit core the ISA allows up to sixty-four such entries; we need only a handful. Two kinds of register make up each entry.1

  • An address register, pmpaddr, that pins down where the range sits. On RV32 it holds bits [33:2] of a physical address — addresses are word-aligned, so the bottom two bits are implied, which is how a 32-bit register can name a range in a slightly larger physical space.
  • A configuration byte, packed into a pmpcfg register, that says what is permitted and how the address is to be interpreted. Four of these bytes ride in each 32-bit pmpcfg register, so a single CSR configures four entries at once.

The whole of the protection lives in that one configuration byte, so it repays a close look. Its eight bits are laid out like this:

Reading the address: TOR versus NAPOT

The two A bits decide how the address register is interpreted, and the choice has real consequences for how tidy the memory map can be.

NAPOT — naturally-aligned power-of-two — encodes a range whose size is a power of two, folded cleverly into the address bits themselves. It is compact, costing a single entry per region, but it can only describe ranges of 8, 16, 32 … bytes that begin on an equally-sized boundary. Regions of awkward size must be rounded up to the next power of two, which either wastes address space or forces the whole map to be laid out around the alignment.

TOR — top of range — is the one we use for the large regions. A TOR entry has no size of its own; its range runs from wherever the previous entry's address ended up to its own address. Entries are read in order, so entry i covers [pmpaddr[i-1], pmpaddr[i]). This lets a region be any size at all, aligned however the memory map finds convenient, at the cost of caring about the order of the entries. For a map with regions of assorted sizes — a small boot ROM, a larger code area, a secrets vault of a few kilobytes — TOR keeps the table readable, and a table a person can read is a table a person can audit. That is worth more to us than the entry we would save with NAPOT.2

The rule the processor follows

On every load, store, or instruction fetch by S-mode or U-mode code, the hardware walks the PMP entries in order and stops at the first whose range contains the address. That entry's permission bits decide the outcome; if none match, the access is denied by default. Deny-by-default is exactly the posture we want, because it means a region we simply forgot to describe is closed, not open. The check happens in hardware, in parallel with the access, on every access, with nothing for software to skip. In the language of the reference-monitor tradition this is complete mediation for memory: there is no path around it.5

3.4The lock bit, Smepmp, and the honest fallback

There is a subtlety that a careful reader will already be circling. PMP normally constrains only S and U mode; machine mode, being the top floor, is exempt. But the Monitor runs in machine mode, and the Monitor has bugs like all software. If a defect in the Monitor's own code could read the secrets region by mistake, "machine-only" would be a weaker promise than it sounds. We would like the secrets and the egress hardware to be off-limits even to the Monitor except through the one narrow routine that is supposed to touch them.

The lock bit is the first tool for this. Setting L=1 does two things: it makes the entry apply to machine mode as well, and it freezes the entry until the next hardware reset. Once locked, no code at any level — the Monitor included — can rewrite that rule or turn it off. This is what guarantees that a supervisor-mode takeover cannot re-map the trusted regions: the rules were locked before the supervisor ever ran, and locked means locked until reboot.

The lock has a coarse edge, though. A locked rule enforces its permission bits on machine mode too, which is fine for a read-only region but clumsy when the Monitor genuinely needs read-write access to, say, its own data area while still denying that area to everyone below. The clean answer is an ISA extension called Smepmp,3 which adds a mode where a rule can read "reachable from machine mode, denied to everything else" without dragging in the all-modes lock semantics. Where Smepmp is available on the VexRiscv build we choose, we use it for the secrets and egress regions and get the precise thing we want.

And where it is not? We say so, and we fall back. If the chosen core lacks Smepmp, the S- and U-visible regions are protected with ordinary L=1 locked rules, and the secrets and egress regions are simply not described by any S/U-reachable entry at all — they remain reachable only through the Monitor's own code path, which is still unbypassable by the supervisor and user tiers even if it is not additionally fenced off from a Monitor bug. That is a real, honest reduction in defence-in-depth against our own code, and it is recorded as an open item rather than papered over. The wall against the untrusted tiers stands either way; what varies is only the extra belt-and-braces against a fault in the trusted tier.6

3.5The regions, and who may touch them

Here is the whole map. Every row is a contiguous range of physical addresses; every entry is a PMP rule that governs it. The addresses are the canonical ones for the project and do not change between chapters.

A few of these rows carry the entire security argument, so it is worth walking them slowly. Rows 0 through 4 belong to the trusted world and are shut to S and U completely. SECRETS holds the keys; EGRESS_MMIO is not memory at all but the control registers of the network, storage, and randomness hardware — the actual wires out. Because those two rows deny both lower levels, there is no load or store any supervisor or user program can issue that reaches a key or drives the network chip. Not "no permitted" load; no such load exists that the hardware will complete. Row 5 hands the Warden its own supervisor-accessible arena. Row 6 is the single shared mailbox, the one region both the Monitor and the untrusted user tier may read and write, and it is deliberately small and dumb: it carries requests in and answers out, and nothing of value lives there. Row 7 onward gives each user-mode compartment a private patch of SDRAM it can scribble in without seeing its neighbours.

3.6Locked before anyone else wakes

A wall built after the burglars are inside is decoration. The ordering of boot is therefore not a detail; it is part of the guarantee, and Chapter 5 tells the full story. What matters here is the sequence around PMP. When the processor comes out of reset it begins in machine mode, running the boot ROM, with no untrusted code anywhere in the machine. The boot ROM measures the Monitor image and refuses to continue if it has been altered. The Monitor then runs, and among the very first things it does — while it is still the only software in existence on the chip — it programs every pmpaddr and pmpcfg entry from the table above and sets the lock and Smepmp bits. Only after the wall is standing and sealed does it hand control down to the Warden with an mret, dropping the processor to supervisor mode.

The consequence is precise. By the time a single instruction of supervisor or user code executes, the protection is already locked and cannot be undone until the next reboot. There is no window — not one cycle — in which the trusted regions are exposed to code we do not trust. A later takeover of the Warden (the stretch adversary of the threat model) inherits a processor whose PMP entries are frozen; it can no more re-map the secrets than it can rewrite the past.

3.7A denied access, step by step

To make the abstraction concrete, follow one hostile load all the way to its fault. Suppose the Warden has been fully compromised — the worst case we still claim to survive — and the attacker's code, running in supervisor mode, tries to read an API key directly out of the secrets region rather than going through the Monitor at all. It executes a plain load from an address inside SECRETS.

supervisor code executes:   lw  t0, 0(a0)      # a0 = 0x1002_0100, inside SECRETS
processor checks PMP:       walk entries in order
                            entry 3 covers [0x1002_0000, 0x1002_4000) — match
                            entry 3 permits: M only; current mode = S
                            → not permitted
result:                     no bytes are read; a load access-fault is raised
                            control traps to the Monitor's fault handler (§9.9)
                            the Monitor treats this as hostile, logs it, does not serve it
outcome:                    the attacker learns nothing; the key never left the region

The important word is no bytes are read. The access does not read the key and then discard it; the load never completes at all. There is nothing to leak, because leaking requires a completed read, and the hardware refused before completion. Contrast this with a software check, which must first fetch the value in order to decide what to do with it — a difference that matters enormously the moment side channels enter the picture, which is exactly why the hardware boundary is the one we rely on.

3.8Edge cases and failure modes

A mechanism is only as trustworthy as its behaviour at the corners. These are the ones we have thought hardest about.

  • Too few entries. The ISA allows sixty-four PMP entries but a given core need not implement them all; VexRiscv's PmpPlugin is configured with a chosen count. Our map needs seven or eight, so we require a build with at least eight and verify the number at boot. A core that reports fewer is a build error, not a runtime surprise.
  • Overlap and ordering. Because TOR ranges are defined relative to the previous entry and matched first-hit, an entry written out of order can silently shadow another. The map is generated from a single table and its ordering is asserted in a test, so a hand-edit that reshuffles rows fails the build rather than the field.
  • A region left undescribed. Deny-by-default saves us here: an address covered by no entry is refused for S and U. The failure mode of forgetting a region is therefore a program that cannot reach memory it needs — loud and immediate — never a region left quietly open.
  • The lock genuinely locks. Once L=1 is set, even legitimate reconfiguration is impossible until reset. This is a feature that will, someday, bite a developer who wanted to adjust the map at runtime. The answer is that the map is not meant to change at runtime; if it needs to, that is a new boot, by design.
  • A fault the Monitor itself trips. If the Monitor, through a bug, touches a region a locked or Smepmp rule denies even to it, the processor faults into the Monitor's own handler. That is treated as an internal error, and the Monitor halts rather than limping onward in a possibly corrupt state (§9.9). A stopped Redoubt is safe because it does nothing; a confused one is not.

3.9Invariants

These are the properties the isolation layer must uphold at all times. The test plan probes each, and a future formal model would establish them properly.5

  1. No S-mode or U-mode access to SECRETS or EGRESS_MMIO ever completes.
  2. The PMP entries covering the trusted regions are locked before any S/U instruction executes.
  3. Once locked, no code at any privilege level modifies those entries before the next hardware reset.
  4. An address described by no entry is denied to S and U (closed by default).
  5. The Monitor's code region is executable but not writable; its data region is writable but not executable. No region is both.
  6. The number of implemented PMP entries meets the map's needs, checked at boot.

3.10The lineage of the idea

None of this is invented here, which is the most reassuring thing one can say about a security mechanism. Placing a small, maximally-privileged monitor beneath the operating system and using hardware to keep the OS out of it is a pattern with a track record. On RISC-V specifically, the Keystone framework builds trusted execution environments around exactly such an M-mode security monitor, and uses PMP to carve enclave memory out of reach of a potentially malicious operating system.4 Sanctorum is a lightweight security monitor in the same spirit, studied precisely for how small and checkable such a component can be.4 Further afield, Apple's SPTM is a monitor more privileged than the iPhone kernel, so that even a full kernel compromise cannot rewrite the page tables it guards.7 Redoubt takes this well-worn shape and points it at one narrow, novel job: mediating an AI agent's tool calls. We are reusing a proven wall, not prototyping a new kind of brick.

3.11Alternatives rejected

Several other ways to build the wall were considered and set aside. The reasons are as much a part of the design as the choice itself.

Rely on the MMU instead of PMP. This is the tempting one, because the memory management unit is the isolation hardware everyone already knows, and with the optional Sv32 support in our core it is right there. But the MMU is configured by the supervisor-mode operating system through page tables the supervisor owns. A compromised operating system simply rewrites those tables and grants itself whatever it likes; the MMU cannot wall anything off from the very code that programs it. It is the wrong tool for a boundary whose whole purpose is to survive an OS takeover. The MMU is genuinely useful one level down — for keeping user-mode compartments from reading each other — and Chapter 4 keeps it for exactly that. It is simply not the wall around the trusted world.

Enforce the boundary in software in the operating system. Simpler, one boundary rather than two — and fatally, a single bug in that software is a total bypass, on the exact component we promised could fall. A check that lives at the attacker's own privilege level is not enforcement.

Give the agent no privilege separation and sandbox it in the host instead. Host-side sandboxes are software the host controls; the whole premise is that the host is compromised. Any boundary that lives on the untrusted computer inherits its untrustworthiness. The boundary has to be on the other side of the wire.

Use NAPOT everywhere to save PMP entries. We have entries to spare and regions of untidy sizes. Forcing every region to a power of two and its alignment would either waste address space or contort the memory map into something no reviewer could hold in their head. Legibility of the map is worth an entry or two; TOR buys it.

Wait for the v2 hardware mediation gate. The long-term plan (Chapter 13) is a custom RTL peripheral on the egress bus that enforces capabilities in silicon, so that not even a compromised Monitor could bypass it. That is the right destination, and it is deferred deliberately: PMP plus a measured, minimal M-mode monitor is a proven, buildable v1, and shipping something real that we can attack teaches more than perfecting something we have not yet built.

3.12Open questions

Honest loose ends, so no one mistakes this for settled:

  • Whether the specific VexRiscv build we settle on implements Smepmp, or whether the L=1 fallback of §3.4 is what actually ships. This changes how much the trusted regions are fenced off from a Monitor bug, though not from the untrusted tiers.6
  • The exact number of PMP entries to request from PmpPlugin, once the compartment count for v1 is fixed — the map needs seven or eight today, but the compartment rows may grow.
  • Whether to enable the Sv32 MMU in the Warden for v1 multi-compartment isolation, or to run PMP-only at first and add the MMU once the base is solid. (Carried jointly with Chapter 4.)
  • The precise sizes of MON_DATA and SECRETS, which depend on how much block RAM the fitted design actually leaves free — a number we will not know until the SoC is placed and routed.
