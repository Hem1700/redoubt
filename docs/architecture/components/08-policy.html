Policy & the Compiler

Abstract. A capability points at rules; this chapter is about the rules and where they come from. Redoubt's policy is a small declarative manifest, a human-written statement of what an agent may do, compiled ahead of time into fixed tables the Monitor reads at run time. The manifest language is deliberately total: it has no loops, no recursion, no callbacks, and cannot express open-ended computation, so a policy always terminates and can always be audited by reading it. We give the grammar, the compiled forms the Monitor actually evaluates, predicate clauses over typed fields, the eight comparison operators, the interned constant pool, and the flow rule, and then compile one real capability from source all the way to the bytes, so you can see a manifest become a Cap, a predicate table, and a flow table. We finish with quotas, and with the road not taken: a flexible, Turing-complete policy language, and why a reference monitor must never have one.

Note to first-time readers.

A little vocabulary, defined plainly, before we start.

Manifest
The human-authored policy file. It lists, per agent, which tools may be called and under what conditions. You read it top to bottom and you know exactly what the agent can do.
Predicate
A condition on a tool call's arguments, "the host must be one of these," "the path must start with /corpus/." A call is allowed only if its predicate is satisfied.
Total language
A language in which every program is guaranteed to finish. It buys that guarantee by giving up the ability to loop forever, which, for a policy, is exactly the ability we want gone.
Compile
To translate the readable manifest, once and ahead of time, into compact tables of numbers the Monitor can evaluate quickly and without parsing anything at run time.
Interning
Storing each distinct constant (a hostname, a path prefix) exactly once in a shared pool and referring to it everywhere by a small index, so the tables stay small and comparisons become integer compares.

8.1What a policy is for

The capabilities of the previous chapter are the run-time currency of authority, but somebody has to mint them, and they have to say something specific: not merely "may use the network" but "may call http.request, over HTTPS only, to api.example.com only, with the API key injected and never in the body." That specificity is the policy. The manifest is where a human writes it down, in a form they can read and reason about, and the compiler is what turns that writing into the tables the Monitor consults on every call.

The split matters. We want the thing a person audits to be legible prose-like source, and the thing the Monitor evaluates to be rigid, tiny, and fast. Those are different shapes, so we keep them as two artefacts and translate once, at build or boot time, between them. The manifest is the truth a human signs off on; the compiled tables are its faithful, checkable projection into bytes.

One consequence sets the tone for the whole chapter: because the tables are written once, at boot, into the Monitor's machine-only data region and never touched again, the policy is immutable for the life of a boot. There is no run-time "policy update" path into the trusted component, no code that mutates the rules while an agent is running, and so no such code to get wrong. Changing policy means producing a new manifest, recompiling, and rebooting. For a reference monitor, that rigidity is a feature, not a limitation.

8.2Why the language is total

The single most important decision in this chapter is a decision about what the policy language cannot do. It cannot loop. It cannot recurse. It cannot call out to a function you supply. It cannot compute in any open-ended sense. It can only check conditions. In the theory of computation this makes it a total language, every policy is guaranteed to finish, and we chose that on purpose, for three reasons that all point the same way.

It always terminates. The Monitor evaluates policy on the hot path of every tool call, in machine mode, with no scheduler above it to preempt a runaway. A policy that could loop forever could freeze the guard, and a frozen guard is a denial of service against the very thing that is supposed to keep working. A total language cannot loop forever, so evaluation is bounded by construction, the Monitor chapter's promise that "every request finishes in a bounded number of steps" rests partly here.

It is auditable. A human is meant to read a manifest and know what it permits. That is only possible if reading it is enough, if there is no hidden control flow, no callback that does who-knows- what, no data-dependent loop whose behaviour you have to simulate in your head. A total language of plain conditions can be understood by reading it, because reading it is the same as running it in your mind to completion.

It is small to evaluate. No loops and no recursion means no stack growth, no iteration count that depends on input, no allocation. Policy evaluation is a fixed walk over compiled clauses, which is why it fits inside a 2,500-line trusted base with room to spare. This is the same instinct the Monitor chapter states as an alternative it rejected, "a flexible policy language with loops and callbacks", and this chapter is where that instinct is made concrete.1

Total does not mean weak. It means bounded. The manifests we need, allowlists of hosts, path prefixes, method sets, numeric ranges, length limits, are all expressible as conjunctions of simple conditions, and none of them wants a loop. Giving up loops costs us nothing we actually use, and buys us termination and auditability outright. That is a rare bargain, and we take it.

8.3The manifest grammar

Here is the language, as EBNF. It is small enough to read in one sitting, which is the point.

manifest   = "session" STRING "{" { capability } "}" ;
capability = "capability" IDENT "=" captype "{" { clause } "}" ;
captype    = "net" | "file" | "secret" | "tool" ;
clause     = "tool"   "=" STRING
           | "arg" IDENT ":" argtype "where" predicate
           | "secret" IDENT "inject-as" injsite
           | "result" "label" "=" label
           | "deny-if" flowcond
           | "quota"  quotaspec ;
argtype    = "url" | "path" | "enum" | "int" | "bytes" ;
predicate  = clause_expr { ("and" | "or") clause_expr } ;   // no general computation
clause_expr= field op operand ;
op         = "==" | "in" | "prefix" | "suffix"
           | "host in" | "scheme ==" | "range" | "len <=" ;
label      = "PUBLIC" | "SECRET" | "TRUSTED" | "UNTRUSTED" ;

Read it as a shape. A manifest names a session and lists capabilities. A capability has a type and a handful of clauses. A clause either binds the tool, constrains an argument with a predicate, arranges for a secret to be injected, labels the result, states a flow denial, or sets a quota. A predicate is a conjunction (or disjunction) of the simplest possible comparisons between one typed field and one operand. That is the entire language. There is nowhere in this grammar to write a loop, because there is no production that refers back to itself through anything but a bounded list, and there is nowhere to call arbitrary code, because there is no production for a function body. The absence is the design.

The EBNF here is illustrative and still being finalised, the exact surface syntax is an open item (§8.9), but the compiled forms it targets are fixed, and those are what the Monitor actually depends on. We turn to them now.

8.4What it compiles to

The compiler's output is three things: a set of Cap records (the sixteen-byte capabilities of Chapter 7), a predicate table, and a flow table. All three live in the machine-only data region, and all three are indexed by the small reference fields inside a Cap (pred_ref, flow_ref, secret_ref). Chapter 7 described the Cap; here are the two tables it points into.

The predicate table

A capability's argument rules compile to a small array of clauses, each a triple:

Clause = (field_selector, op, operand_ref)

The field_selector names which typed field of which argument the clause tests, the host of a URL, the scheme of a URL, the path of a file argument, an integer's value, a byte string's length. Because arguments cross the wire already typed (the TypedArg encoding of Chapter 6), the selector picks out a structured field directly; there is no re-parsing of text, and so none of the parser-mismatch bugs that arise when the checker and the doer disagree about how to read a string.2 The op is one of exactly eight comparison operators. The operand_ref is an index into the interned constant pool (below), except for operators whose operand is a small immediate.

opTests that the selected field…Operand
EQequals a constant exactlypool ref
IN_SETis a member of a constant setpool ref (set)
PREFIXbegins with a constant byte/char sequencepool ref
SUFFIXends with a constant sequencepool ref
HOST_IN_SET(URL host) is a member of a host allowlistpool ref (set)
SCHEME_EQ(URL scheme) equals a scheme constantpool ref / enum
RANGE(integer) lies within [lo, hi] inclusivepool ref (pair)
LEN_LE(byte/string length) is at most a boundimmediate

Evaluation is a fixed loop over a capability's clauses: for each clause, select the field, apply the operator against the operand, and require every clause to pass (a conjunction; disjunctions compile to a small OR-group within the same fixed bound). The loop is capped, no more than MAX_ARGS (8) arguments and MAX_CLAUSES (64) clauses in total, so the worst case is a known constant and there is no way for a manifest to make evaluation take longer than that cap.3 That two of these operators, HOST_IN_SET and SCHEME_EQ, are dedicated to URL fields is not redundancy with IN_SET and EQ; it is a promise that the host and scheme the Monitor tests are the ones re-derived from the structured URL, not whatever a re-parse of a raw string might yield.

The interned constant pool

Every distinct constant a manifest mentions, a hostname, a path prefix, a scheme, a numeric range, an allowlist, is stored exactly once in a shared pool in the machine-only region, and referred to everywhere by a small index. This is interning. Two capabilities that both allow api.example.com share one pool entry and two references to it, not two copies of the string. The payoff is threefold: the tables stay compact enough to fit the FPGA's memory; a clause comparison against an interned set is an integer-indexed lookup rather than repeated string work; and the subset check that derivation depends on (Chapter 7, §7.6) reduces to comparing indices and set memberships in the pool, which the compiler can do cheaply and certainly.

The flow table

Separate from arguments entirely, the flow table holds each capability's information-flow rule, selected by flow_ref. A flow rule answers a different question from the predicate: not "are the arguments allowed?" but "would this call move data in a forbidden direction, a secret toward a public sink?" A rule records the sink's confidentiality ceiling and whether the capability is permitted to carry a SECRET-labelled value into the effect at all. The Monitor evaluates it as the fifth pipeline check, after arguments pass. The mechanism and the lattice behind it are Chapter 10's subject; the compiler's job is only to lay each capability's rule into this table and point flow_ref at it. A deny-if body carries SECRET clause in the manifest is exactly what compiles to such a rule.

8.5A capability compiled, end to end

Let us do the compilation the figure summarises, by hand, so nothing is hidden. Here is the source, the same web capability the Monitor chapter uses in its worked attack:

session "researcher" {
  capability web = net {
    tool   = "http.request"
    arg url    : url  where scheme == "https" and host in {"api.example.com"}
    arg method : enum where method in {"GET"}
    secret API_KEY inject-as header "Authorization"
    result label = UNTRUSTED
    deny-if body carries SECRET
    quota  { calls_per_session = 200 }
  }
}

The compiler processes this in five passes, and each pass produces something concrete.

Pass 1, intern the constants. It walks the source collecting every literal and places each, once, into the constant pool: the scheme "https" at pool#0, the host set {api.example.com} at pool#1, the method set {GET} at pool#2. If another capability in the same manifest also allowed "https", it would reuse pool#0 rather than adding a second entry.

Pass 2, lower each predicate to clauses. The url argument's predicate has two conjoined conditions; the method argument's has one. They become three clause triples, laid into the predicate table at the next free row, say row 4:

predicate_table[4] = [
  (url.scheme, SCHEME_EQ,   pool#0),   // scheme == "https"
  (url.host,   HOST_IN_SET, pool#1),   // host in {api.example.com}
  (method,     IN_SET,      pool#2),   // method in {GET}
]   // conjunction: every clause must hold

Pass 3, build the flow rule. The result label = UNTRUSTED and deny-if body carries SECRET clauses compile to one flow-table row: the sink may not carry a SECRET-labelled value, and whatever comes back is stamped UNTRUSTED. Say it lands at flow_table[1].

flow_table[1] = { carry_secret: false, sink_ceiling: PUBLIC, result_label: UNTRUSTED }

Pass 4, resolve the secret. secret API_KEY inject-as header "Authorization" binds this capability to secret-store slot 0 and records the injection site (an Authorization header). The slot index becomes the capability's secret_ref; the injection site is stored beside the secret so the performing step knows where to splice it. The key bytes themselves never enter any of these tables, only the reference does.

Pass 5, emit the Cap and check the quota. Finally the sixteen-byte capability is assembled and installed into the session's cspace at the slot the manifest assigns; the host will receive that slot number as its handle:

Cap {
  ctype      = 1,              // Net
  rights     = (method-gate bits),
  tool_id    = id("http.request"),
  pred_ref   = 4,             // -> predicate_table[4]
  flow_ref   = 1,             // -> flow_table[1]
  secret_ref = 0,             // -> secret store slot for API_KEY (inject-only)
  aux        = 0,
  epoch      = session.epoch, // 7 at mint time
}

That is the whole capability, and it is worth pausing on how little the Monitor now has to do at run time. When the agent calls http.request, the Monitor resolves the handle to this Cap (Chapter 7), confirms tool_id matches, walks the three clauses of predicate_table[4] against the typed URL and method, checks flow_table[1], and, only if all of that passes, performs the call with the API_KEY injected. No parsing, no string juggling, no open-ended work; three clause evaluations and two table lookups. The readable manifest and the fast, bounded run-time check are the same policy, seen from two ends of the compiler.

And the attack from the Monitor chapter, replayed against these exact tables: a request to evil.tld fails clause c1 (HOST_IN_SET) and returns DENY_ARG carrying the failing clause index; a request to the real api.example.com with the key smuggled into the body passes all three clauses and then dies at flow_table[1]'s carry_secret: false with DENY_FLOW. Two tables, two independent nets.

8.6Quotas

A predicate answers "is this call shaped correctly?" but says nothing about "how many times?" An agent whose every individual call is legitimate can still do harm by making the legitimate call ten thousand times, draining a rate-limited API, filling storage, running up a bill. Quotas are the manifest's answer to that, and they are deliberately simple.

A quota clause attaches a small counter to a capability: a maximum number of calls per session, and, where it makes sense, a cap on total bytes moved. The counters live beside the capability in the machine-only region and are decremented at the performing step; when a counter reaches zero the Monitor returns DENY_QUOTA and the call does not happen. Because the counters are per-session and reset only when a fresh session installs fresh capabilities, there is no way for an agent to reset its own quota, the reset is on our side of the wall, tied to session lifecycle (Chapter 11).

Quotas are coarse on purpose. They are not a full rate-limiter with token buckets and time windows; that would drag a notion of wall-clock time and refill policy into the trusted base. A monotone counter that only ever decreases within a session is enough to bound the damage a busy-loop of legitimate calls can do, and it costs almost nothing to evaluate. Finer rate control, if we ever need it, belongs outside the Monitor. The exact set of quota dimensions is still being settled (§8.9).

8.7Failure modes and what the compiler refuses

A good deal of policy safety comes from things the compiler rejects before they ever reach the Monitor. Because compilation happens ahead of time, off the trusted hot path, it can afford to be thorough, and a rejected manifest simply never boots.

  • Over-budget tables. If a manifest's predicates exceed MAX_CLAUSES, or its capabilities exceed a session's cspace, or its constants overflow the pool's reserved size, the compiler fails the build rather than truncating. The Monitor never has to cope with a table that is too big; it is guaranteed one that fits.
  • A derivation that is not a narrowing. Any capability declared as a derivation of another is checked, at compile time, to be a genuine subset, stricter predicate, no wider rights, same tool (Chapter 7, §7.6). A "derivation" that would widen authority is a compile error. The Monitor is thereby handed only legitimate narrowings and never has to verify subset containment itself.
  • A dangling reference. Every pred_ref, flow_ref, secret_ref, and pool index the compiler emits is one it also populated; there are no forward references to fill in later and no way for a Cap to point at a table row that does not exist.
  • An unknown tool or argument type. Tool names and argument types are checked against the tool catalogue at compile time; a manifest naming a tool the catalogue does not define does not compile.
  • A malformed constant. A host that is not a valid host, a range whose low exceeds its high, a length bound that does not fit, caught in the interning pass, not discovered at run time on attacker-controlled input.

The theme is the same as everywhere in Redoubt: push the hard, fallible work to a place where a mistake is a failed build rather than a run-time surprise inside the trusted component. The Monitor's copy of the policy is, by the time it runs, already known to be well-formed, in-budget, and internally consistent.

8.8Alternatives rejected

The central choice here, a total language, is best understood against the thing we refused.

A flexible, Turing-complete policy language. The obvious "powerful" design is to let policy be real code: a scripting language, or embedded Lua, or WebAssembly, or callbacks into host-supplied functions, so that a policy author can express any condition they can imagine. It is seductive, and it is wrong for a reference monitor, for reasons that compound. Such a language can loop forever, so evaluation on the hot path is no longer bounded and the guard can be made to hang. It cannot be audited by reading, because its behaviour is data-dependent in ways you must execute to discover, so the property "a human can read the policy and know what it permits" is lost. It is far more code to implement safely, blowing the TCB budget on an interpreter that is itself a large attack surface. And a policy that calls out to host-supplied code has handed part of the decision back to the untrusted side, which is the exact thing the whole architecture exists to prevent. Every one of those is fatal on its own. We do not have a fast version of this; we have no version of it, by design.1

Interpret the manifest at run time in the Monitor. A softer variant: keep the declarative language, but parse and evaluate the manifest text directly inside the Monitor, skipping the compile step. This spares us a compiler but puts a parser for a text format on the trusted hot path, reading structured input on every boot and turning source into decisions at run time. Parsers are a classic bug reservoir, and this one would sit inside the TCB. Compiling ahead of time moves all of that out: the Monitor consumes fixed binary tables, not source, and the only parsing it does is of the tiny, typed request.

Regular expressions for string arguments. Tempting for URL and path matching, and genuinely expressive. But general regex engines can backtrack catastrophically, the "ReDoS" failure, which reintroduces the unbounded-evaluation problem we just spent the chapter avoiding, and a non-backtracking engine is still more machinery than we want in the trusted base. The eight fixed operators cover the cases we actually have (prefix, suffix, set membership, exact match) with evaluation that is obviously bounded and obviously correct. If a manifest wants something the operators cannot express, that is a signal to reconsider the tool's argument type, not to add a regex engine.

Mutable, hot-reloadable policy. Being able to update policy without a reboot sounds operationally nice. It also means code inside the trusted component that mutates the decision tables while agents are running, with all the concurrency, consistency, and "what was in effect at the moment of the call?" questions that follow. We chose immutable-per-boot instead: policy changes by recompiling and rebooting, the tables are written once and never again, and there is simply no mutation path to reason about. For a component this small and this trusted, a reboot is a cheap price for removing an entire class of state.

8.9Open questions

The honest loose ends:

  • The concrete surface syntax and the binary format of the compiled predicate and flow tables are not yet frozen; the grammar in §8.3 is illustrative. This is the same open item the main specification records.4
  • The exact URL and path canonicalisation rules the Monitor re-derives, how much normalising the compiler bakes into the constant pool versus what the Monitor does at check time, need pinning down so the checker and the performer cannot disagree.
  • The set of quota dimensions (calls, bytes, anything else) and whether any of them should span sessions rather than reset per session.
  • Whether disjunction (or) inside a predicate stays, or whether we restrict manifests to pure conjunctions of clauses to make the subset check for derivation even simpler.
  • Whether the compiler should emit a signed, measurable artefact so the boot measurement (Chapter 5) can attest the exact policy in force, not just the Monitor image.
