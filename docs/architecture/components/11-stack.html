Warden, Compartments & Sessions

Abstract. Below the Monitor, and above the untrusted host, sits a thin layer of software that keeps the lights on: the Warden, a small supervisor-mode kernel that schedules threads and shuttles messages, and the user-mode compartments it runs — the one that speaks USB to the host, and the drivers that format network and storage traffic. None of it is trusted to make a security decision. This chapter says what each piece does, what it is deliberately forbidden from doing, and how a request travels from a compartment through the Warden and into the Monitor. It then specifies the session: the bounded container for a single agent run, its capability space and epoch, the five states it moves through, the quotas that cap it, and the one-instruction move that revokes everything it was ever granted. The chapter closes on the question that justifies the whole arrangement — why a Warden that has been completely taken over still cannot reach past the Monitor.

Note to first-time readers.

This chapter sits one level down from the Monitor (Chapter 9). A few terms recur; here is each in plain language, no hardware background assumed.

Supervisor mode
The middle of the RISC-V processor's three privilege levels, between the all-powerful machine mode (where the Monitor lives) and the ordinary user mode. A traditional operating-system kernel runs here. In Redoubt the Warden runs here — powerful enough to schedule and move data, but walled off by hardware from the machine-only regions above it.
Microkernel
A kernel stripped to the smallest set of jobs that genuinely need privilege — scheduling threads, passing messages between them, switching address spaces — with everything else (drivers, protocol stacks) pushed out into unprivileged programs. The Warden is a microkernel of this kind, and an unusually spare one.
Thread
A single flow of execution the kernel can pause and resume. The Warden gives each compartment one or more threads and decides, moment to moment, which gets to run.
Compartment
An isolated user-mode program with its own slice of memory. Redoubt's compartments are the Endpoint (which talks USB to the host) and the network and storage drivers. They can prepare and format data; they cannot act on the outside world by themselves.
Session
One agent run, wrapped in its own container: a private set of capabilities and a counter called an epoch. When the run ends — or is cut short — bumping that counter cancels every permission at once.

11.1Where the Warden sits, and what it is for

The Monitor decides; something still has to do the mundane work of keeping a computer running. Threads must take turns on the one processor. A driver that has formatted a packet must get that packet to the part that can send it. When the host pokes the USB port, something must wake up and read the bytes. None of that is a security decision, but all of it has to happen, and reliably, or the device is simply a brick.

The Warden is the piece that does it. Think of it as the building's facilities manager rather than its security guard. The manager assigns offices, routes the internal mail, and keeps the corridors moving; the guard at the one door (the Monitor, Chapter 9) decides what may actually leave the building. The two jobs are kept firmly apart on purpose. The manager holds no keys to the vault and cannot open the front gate, so it does not matter, to the security property, whether the manager is honest.

The Warden runs in supervisor mode. It has exactly three responsibilities, and we resist adding a fourth:

  1. Scheduling — deciding which thread runs next, and making sure no thread can seize the processor forever.
  2. Message passing — carrying a fixed-size message from one compartment to another, by value, with no shared writable memory between them.
  3. Address-space setup — arranging, once, the memory each compartment may touch, optionally using the processor's virtual-memory hardware for finer separation.

What it is trusted for is narrow and worth stating flatly: liveness, and nothing else. If the Warden is correct, requests get scheduled, messages arrive, and the device stays responsive. If the Warden is wrong — or hostile — the worst it can do is refuse to run things, scramble the internal mail, or lie to a compartment. It cannot make the Monitor allow an action the policy forbids. The security property (Chapter 2) is stated to hold even when the Warden is fully compromised, and §11.9 is where we make good on that.

11.2Trusted for liveness, not for the verdict

This is the distinction the whole chapter turns on, so it is worth slowing down. There are two very different kinds of "trust" one can place in a component, and conflating them is how monolithic systems end up with a kernel that must be perfect.

To trust a component for safety is to rely on it never to permit something bad. The Monitor is trusted this way: if it says no, the action does not happen; if it has a bug that says yes when it should say no, the guarantee is broken. That is why the Monitor is tiny and why it is the only thing in the trusted base.

To trust a component for liveness is only to rely on it to keep making progress. The Warden is trusted this way and no further. A Warden bug can wedge the scheduler or drop a message; the device then does less than it should, or nothing. That is a denial of service, which v1 explicitly does not defend against (Chapter 2, and §11.12). What such a bug cannot do is cause an unauthorised effect, because the Warden never touches the decision or the egress hardware. It can stop the guard from being asked; it cannot answer for him.

The seL4 project draws the same line and makes it precise: their proofs establish that the kernel enforces isolation and authority correctly, while availability is treated separately. Redoubt borrows the discipline but not the burden — we do not need to prove the Warden correct at all, because it holds no authority to misuse.1

11.3Threads and the scheduler

There is one processor, and several things that want to run: the Endpoint waiting on USB, a network driver formatting a payload, a storage driver assembling a block write. The Warden gives each a thread and takes turns among them.

The turn-taking is plain round-robin. Runnable threads sit in a ring; the Warden runs the one at the front for a fixed slice of time, then moves it to the back and runs the next. There is no priority maths, no dynamic reordering, no attempt to be clever about which thread "deserves" the processor. Plain is a feature here: a scheduler you can describe in two sentences is a scheduler whose behaviour you can predict, and there is no scheduling trick an attacker can play to starve the system in a way that matters, because starving the system is merely the denial of service we already declined to defend.

The important part is the word fixed. Each thread runs against a hardware timer. When the slice expires, the timer raises an interrupt, the processor jumps back into the Warden, and the running thread is preempted whether it wished to yield or not. This is what keeps a single compartment — say a network driver that has been taken over and thrown into an infinite loop — from freezing every other compartment. It runs out its slice and is set aside.

Warden thread table (fixed at boot; sizes illustrative):
  threads[ THREADS_MAX ]      each: { state, saved_regs, sp, asid, quantum_left }
    state ∈ { Ready, Running, Blocked-on-send, Blocked-on-recv, Dead }
  run_ring                    indices of Ready/Running threads, round-robin
  tick_hz                     timer frequency; quantum = N ticks

scheduler step (on timer interrupt or on block):
  save current thread's registers into its slot
  if current still Ready: move it to the back of run_ring
  pick front of run_ring; if empty, idle (wait for interrupt)
  restore that thread's registers; set its asid; mret to it

One subtlety belongs to the Monitor, not the Warden, and is worth flagging so the boundary stays clear. While the Monitor is actually running a request, it runs to completion without interruption (Chapter 9, §9.5). The timer preemption described here governs the compartments and the Warden itself; it does not reach up into a machine-mode request in flight. The Warden schedules the world around the Monitor, never inside it.

11.4Message passing: synchronous rendezvous

Compartments need to talk. The storage driver has formatted a block and wants it written; the Endpoint has a framed request from the host and needs it relayed. In a conventional kernel this is done with shared memory and a pile of locks, which is exactly the kind of concurrency machinery that breeds subtle bugs. The Warden refuses that tempting complexity and uses the simplest scheme that works: a synchronous rendezvous.

The picture is a face-to-face handoff rather than a mailbox. A sender that calls send blocks until a receiver calls recv; a receiver that calls recv first blocks until a sender arrives. When the two meet, the Warden copies the message — a small, fixed-size buffer — from the sender's memory into the receiver's, register by register or through a bounded kernel buffer, and then both threads are made runnable again. That is the entire mechanism.

Three properties fall out of this design, and each one removes a class of trouble:

  • Bounded. A message has a maximum size, fixed at build time. There is no growing queue and no allocator, so message passing cannot exhaust memory and cannot be made to run for an unbounded time.
  • Copy-by-value. The bytes are copied from sender to receiver. Neither party retains a reference into the other's memory once the call returns.
  • No shared writable pages. Two compartments never map the same writable region. This is the one that matters most for safety: it means a compromised driver cannot reach into a peer's address space and rewrite its data mid-flight, and it means there is no shared buffer for the classic time-of-check-to-time-of-use race in which one party edits a message after another has inspected it.

The one place where memory is shared at all is SHARED_REQ (§11.6), the mailbox the Monitor reads requests from — and even there the Monitor copies the request into its own private memory before acting on it, precisely so the untrusted side cannot alter it after the checks begin. Sharing is the exception, tightly scoped, and never trusted.

11.5Address spaces

Each compartment must be confined to its own memory. The load-bearing wall for this — as everywhere in Redoubt — is PMP, the machine-only Physical Memory Protection that the Monitor programs and locks at boot (Chapter 3). PMP alone is enough to keep user-mode compartments out of the Monitor's regions, out of the secrets, and off the egress hardware. That protection is not something the Warden provides or can weaken; it is already in force before the Warden's first instruction runs.

What the Warden may add, on top of PMP, is finer separation between compartments, using the processor's virtual-memory unit in its Sv32 configuration.4 Sv32 gives each compartment its own page table, so compartment A's addresses simply do not name compartment B's memory. The Warden assigns each compartment an address-space identifier and switches page tables as it schedules.

Two things about this are deliberate. First, the MMU is optional: whether v1 ships with Sv32 on, or runs PMP-only with a handful of per-compartment PMP entries, is an open configuration question (Chapter 3, and §11.12). Second, and more important, the MMU is configured by the Warden, which means a compromised Warden can reconfigure it. That is precisely why the MMU is not the wall that protects the Monitor. The MMU keeps honest compartments apart from each other; the PMP keeps everyone apart from the trusted base. Resting the real boundary on the machine-only mechanism, and using the supervisor-configurable one only for the lower-stakes job, is the same reasoning the Monitor chapter gives for rejecting an MMU-based design (Chapter 9, §9.11).

11.6The ecall relay

Now the piece that connects this chapter to the last one. A compartment cannot call the Monitor's functions directly — the Monitor lives in machine mode, unreachable by a mere procedure call. The only way up is the same doorbell the whole system is built on: the ecall instruction, which traps the processor into machine mode. The job of the relay is to get a compartment's request into the one place the Monitor reads from, and then ring that bell.

The place is SHARED_REQ, the buffer at 0x4000_0000 that is readable and writable by both the Monitor (M) and user mode (U). It is the mailbox. Here is the round trip, told plainly:

relay(request):
  1. the Endpoint has a framed, typed request in its own compartment memory
  2. it (or the Warden on its behalf) copies the request bytes into SHARED_REQ,
     entirely within region #6 (0x4000_0000 .. 0x4000_1000)
  3. it sets the ABI registers:
        a7 = REDOUBT_MEDIATE   (0x5244_0001)   # or SESSION_OPEN / REVOKE / CLOSE / ATTEST_READ
        a0 = pointer into SHARED_REQ
        a1 = request length
  4. ecall                                       # traps to M-mode; the Monitor takes over
  -- the Monitor runs its six checks (Chapter 9) and performs or denies --
  5. on return:
        a0 = status     (0x00 ALLOW, or a DENY_/ERR_ code — Chapter 9, §5.4)
        a1 = response length written back into SHARED_REQ
  6. the relay reads the response out of SHARED_REQ and hands it back to the compartment

Notice what the relay does not do. It does not inspect the request's meaning, does not consult the policy, does not touch a capability. It marshals bytes and rings the bell. If a compromised Endpoint fills SHARED_REQ with the most malicious request it can compose, the relay carries it faithfully to the Monitor — and the Monitor's checks are exactly where such a request is meant to die. That is the design working as intended, not a hole. The relay is a courier, and a courier that cannot read the letters is a safer courier.

The five opcodes the relay can carry are the entire attack surface the Monitor exposes upward: MEDIATE (0x52440001), SESSION_OPEN (0x52440010), REVOKE (0x52440011), CLOSE (0x52440012), and ATTEST_READ (0x52440020). Any other value in a7 is turned away as malformed before a single table is consulted. The wire protocol that fills the request body — COBS framing, CRC32, the TypedArg TLVs — is the subject of Chapter 6; here we care only that structured bytes arrive in the mailbox.

11.7The compartments, and what each cannot do

Above the Warden, in user mode, run the compartments. There are two families, and the interesting thing about both is the ceiling on what they are permitted to accomplish.

The Endpoint — framing only

The Endpoint is the compartment that speaks to the host over USB. The host's tool shim sends bytes; the Endpoint receives them, removes the COBS framing, checks the CRC32, and hands the resulting typed request to the relay. In the other direction it takes a response and frames it back for the host. That is the whole of its job: it is a translator between the wire and the mailbox.

What it cannot do is decide anything. It never resolves a capability, never evaluates a predicate, never sees a secret. It cannot reach the network chip or the SD card, because those live behind PMP in the machine-only egress region. A completely subverted Endpoint — and we assume it can be subverted, it is directly exposed to a hostile host — is still only a source of bytes flowing into the Monitor's front door, where every byte is checked. It can produce malformed frames (dropped, counted) or well-formed but unauthorised requests (denied). It cannot manufacture authority it was not given.

The drivers — format, but never act

The network and storage drivers are the other family. A network driver knows how to lay out a payload the way the ESP32 link expects; a storage driver knows how to assemble the bytes of a block write for the SD controller. This is genuine, useful work, and it is exactly the sort of fiddly format-handling code we want out of the trusted base, where a bug in it would be catastrophic.

The line the drivers cannot cross is the difference between formatting a send and performing one. A driver may prepare, in its own compartment memory, the precise bytes of an outbound packet. It cannot transmit them. The actual send is a Monitor action: it is the Monitor that owns the ESP32 link and the SD controller MMIO (both in the M-only egress region, Chapter 12), the Monitor that applies the capability check, and the Monitor that injects any secret the policy directs (Chapter 12, §on secrets). The driver hands a formatted payload up through the relay and asks; the Monitor checks and, only if the check passes, acts.

The consequence is worth stating in one sentence, because it is the point of the whole tier: a compromised driver can produce any bytes it likes, but it cannot cause those bytes to leave the device unless a valid capability and a passing predicate say they may.

11.8The session: a bounded agent run

Everything above has been about the machinery that runs continuously. The session is the unit of work that runs on top of it: one agent doing one job, for a bounded stretch of time, with a bounded set of powers, after which it can be wiped out completely and instantly.

A session is not much, structurally, and that is the intent. It is a small record holding a capability space, an epoch counter, and a set of quotas. Up to eight may be live at once.

struct Session {                       // held in MON_DATA, machine-only
  state     : enum  { Created, Provisioned, Active, Draining, Destroyed }
  epoch     : u16                       // bumped to revoke everything at once
  cspace    : [Cap; 32]                 // this run's capabilities (Chapter 7)
  quotas    : { egress_bytes, requests, wall_time, open_files }
  spent     : { egress_bytes, requests, ... }   // counters checked each request
}
sessions : [Session; 8]                 // SESSIONS_MAX = 8

The capability space and the epoch

The capability space is the session's set of powers: an array of 32 capability slots, each a 16-byte record (Chapter 7 specifies the record in full). A fresh capability space is entirely empty — no ambient authority, nothing granted by default. The manifest for the run installs exactly the capabilities it is meant to have, and not one more.

The epoch is the clever, cheap part. Every capability carries the epoch of the session that issued it. Every time the Monitor resolves a capability during a request, it checks that the capability's epoch still equals the session's current epoch. Equal means live; unequal means stale, and a stale capability is refused (DENY_REVOKED). This one comparison is the mechanism behind instant revocation, which we come to below.

The state machine

A session moves through five states in a fixed order, with two ways out of the running state. The transitions are triggered by the session opcodes the relay carries, by the quota checks the Monitor runs, or by an explicit revoke.

Created

A slot in the eight-entry session table is allocated and zeroed. The capability space is all-empty; the epoch is initialised. Nothing can be authorised yet, because there is nothing to authorise with.

Provisioned

The run's manifest is compiled into the capability space: the exact capabilities this agent is meant to hold are written into the slots, each stamped with the session's epoch. Quotas are set from the manifest. After this step the session's powers are fixed for its lifetime — capabilities may only be narrowed from here (attenuation, Chapter 7), never widened.

Active

The run proceeds. This is the state in which MEDIATE requests flow: each one resolves a capability out of this session's space, checks its epoch, and — if the quota counters permit — runs the six checks. Every request that performs an effect debits the relevant quota.

Draining

The run is ending normally, or has hit a quota ceiling. No new work is accepted, but requests already in flight are allowed to finish so the device is not left in a half-written state. This is the graceful shoulder between running and gone.

Destroyed

Terminal. The capability space is wiped, the quotas cleared, the slot returned to the pool for reuse. A destroyed session cannot be reactivated; a new run gets a fresh slot with a fresh epoch.

Quotas

Left unbounded, even an authorised agent can do damage by volume — a million allowed requests, a gigabyte of allowed egress. Quotas cap the run along a few axes: total egress bytes, total requests, wall-clock time, and open files. The Monitor keeps a spent-counter beside each limit and checks it as part of mediation; crossing a ceiling returns DENY_QUOTA (0x16) and moves the session into Draining. Quotas are about the volume of authorised action, which the capability checks alone do not bound — a distinct concern from whether an action is permitted at all.

Instant revocation

Here is the move the whole session design exists to make possible. Suppose a run must be cut off immediately — the operator hits the stop, or a monitor upstream decides the agent has gone wrong. How do you cancel dozens of capabilities that may be scattered across the space, some of them derived from others, without walking a tree or searching a list?

You bump one number. The REVOKE opcode increments the session's epoch. That is the entire operation — constant time, no traversal, no allocation. From the very next request, every capability in that session fails its epoch check, because each was stamped with the old epoch and the session now carries a new one. All of them, at once, dead. The host may still be holding capability handles; they now resolve to nothing.

revoke(session_id):
    sessions[session_id].epoch += 1     # O(1); every prior cap is now stale
    move session to Draining/Destroyed
# next MEDIATE using any old handle:
#   cap.epoch (old) != session.epoch (new)  ->  DENY_REVOKED (0x15)

This is a coarser instrument than seL4's capability-derivation-tree revocation, which can revoke a precise subtree and leave the rest standing.2 We chose the coarse version deliberately: for Redoubt the natural unit of revocation is the whole run, and per-session teardown is what an operator actually reaches for. Buying that with a single increment, rather than a tree walk in the trusted base, is a trade we take gladly. Where a finer grain is genuinely needed, one can provision a capability in its own short-lived session and revoke that.

11.9Why a compromised Warden still cannot breach the Monitor

This is the claim the chapter has been building toward, and the one a sceptical reader should press hardest. The threat model (Chapter 2) lists a subverted Warden as an assumed adversary — stretch case A5 — and insists the security property holds anyway. Why does it?

Because the Warden's power is bounded by hardware it cannot touch, not by its own good behaviour. Walk through what a fully hostile Warden could try:

  • Read the secrets directly. The secrets sit in an M-only PMP region. A load from supervisor mode to that address does not return zeros or ask permission — it faults. The Warden cannot read what the silicon will not address for it (Chapter 3).
  • Drive the egress hardware directly. The ESP32 link and the SD controller MMIO are likewise in an M-only region. A store from the Warden to those addresses faults. There is no send it can perform on its own.
  • Rewrite the Monitor's code or tables. The Monitor's code is M:RX and its data M:RW, both locked at boot before the Warden ever runs. A locked PMP entry cannot be modified until the hart resets (Chapter 3). The Warden cannot patch the guard.
  • Forge a capability. Capabilities live in machine-only memory; the host and the Warden hold only opaque handles, which are indices. A forged or out-of-range handle resolves to an empty slot and is denied. The Warden cannot mint authority (Chapter 7).
  • Feed the Monitor a malicious request. This one it can do — and it changes nothing. A hostile Warden relaying the nastiest request it can compose is simply exercising the Monitor's front door, where the six checks live. An unauthorised request is denied; that is the mediation working, not failing.
  • Reconfigure the MMU to remap memory. The MMU is supervisor-configurable, so yes, the Warden can rearrange virtual addresses. But the MMU sits below PMP in the hardware's checking order for the regions that matter: PMP is applied to physical addresses and is machine-only. Remapping cannot make an M-only physical region reachable from supervisor mode.

The list is exhaustive in the sense that matters: every avenue to an unauthorised effect either faults on a machine-only boundary or lands harmlessly at the Monitor's checked entry. What remains to the Warden is the power to not do its job — to wedge, to drop, to stall. That is denial of service, which we have said from the start v1 does not defend against. The trade is stark and honest: we give up availability under a Warden compromise, and we keep the security property. For a device whose entire reason to exist is to contain a hostile agent, that is the right side of the trade.

This is the same architectural bet Apple makes with SPTM and the Keystone/Sanctorum systems make on RISC-V: put the small, must-be-correct thing in a mode more privileged than the large kernel, and let the kernel be as untrusted as it likes.3 Redoubt's contribution is not the pattern but the target it is aimed at — the tool calls of an AI agent.

11.10Invariants this tier maintains

The properties the Warden-and-sessions layer must always uphold, each a candidate for a test in the containment suite (Chapter 13):

  1. No compartment ever holds a writable mapping of another compartment's memory, nor of any M-only region.
  2. Every message crossing between compartments is copied by value and is no larger than the fixed maximum.
  3. A preempting timer always returns control to the Warden within one quantum, so no compartment can hold the processor indefinitely.
  4. A capability resolves successfully only if its epoch equals its session's current epoch.
  5. A session in Draining or Destroyed accepts no new authorising request.
  6. Revocation is constant-time and total: after a REVOKE, no capability of that session ever authorises again.
  7. No action the Warden or a compartment takes, in any state, can read a secret, drive egress, or alter the Monitor's code or tables.

11.11Alternatives rejected

The shape of this tier is the result of turning down several plausible designs. The reasons are as much a part of the specification as the choices.

Fold scheduling and IPC into the Monitor. One fewer component, one fewer boundary. But a scheduler and a message system are hundreds of lines of exactly the stateful, concurrent code that the trusted base must not contain. Keeping them in the Warden, outside the TCB, is what lets the Monitor stay under 2,500 lines and lets us not have to trust the scheduler at all.

Asynchronous IPC with queues. Message queues are more flexible and can smooth bursts. They also bring buffers to size, allocation to manage, and back-pressure to reason about — a standing invitation to memory-exhaustion and ordering bugs. Synchronous rendezvous needs none of it, and the workload here (a handful of compartments handing off small requests) does not want the flexibility.

Shared-memory IPC for speed. Copying a message costs cycles that a shared page would save. But a shared writable page between compartments is the seedbed of both cross-compartment corruption and time-of-check races. For a security device the copy is cheap insurance, and the messages are small.

Rest compartment isolation on the MMU alone. The MMU can separate compartments finely, and we use it for that. But it is supervisor-configurable, so it cannot be the wall that protects the trusted base from the Warden itself. PMP has to be the primary boundary; the MMU is a refinement on top, never the foundation.

Per-capability revocation trees in the Monitor. seL4-style derivation trees give surgical revocation, but they put a graph structure and a recursive walk into the trusted base. Redoubt's revocation unit is the session, so a single epoch bump does the job in constant time with no tree to maintain. We accept the coarser grain to keep the Monitor small.

Priority scheduling to protect responsiveness. Priorities would let us favour, say, the Endpoint over a busy driver. But priority schemes add state and invite priority-inversion puzzles, and responsiveness is a liveness concern we have already declined to guarantee under compromise. Plain round-robin is easier to reason about and enough.

11.12Open questions

Honest loose ends in this tier, so the draft is not mistaken for finished:

  • Whether v1 enables the Sv32 MMU for per-compartment isolation, or ships PMP-only with a small number of per-compartment entries. This mirrors the SoC-level open item in Chapter 3.
  • The exact fixed message size for rendezvous IPC, and whether a small number of message classes (control versus bulk-payload handoff) is worth the added surface.
  • Concrete quota defaults — egress bytes, request count, wall-time — which want measurement on real workloads before they are set.
  • Whether eight concurrent sessions is the right ceiling, or whether the FPGA's memory comfortably affords more once the tables are sized (this interacts with the Monitor's open question on table sizes, Chapter 9).
  • Whether Draining needs a timeout of its own, so a compartment that never finishes its in-flight work cannot pin a session slot open forever.
